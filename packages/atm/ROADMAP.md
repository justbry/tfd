## 0.8.0 design: bookable items, paid bookings, codes

Design note, written before the code (2026-11-05); built and released as 0.8.0 (what was fixed after the review is in the last paragraph). Version: there is no 0.7.0: the number was never released (it was reserved for the stored-inputs design, PR #65), so this work was released as **0.8.0**, and the stored-inputs work is planned as **0.9.0**. atm owns the rules; `buzz-school` stores rows and talks to Stripe (what it must change goes in `UPGRADING.md`, "Moving to 0.8.0"). Types are in `src/types.ts` (the section "Bookable items", "A one-time payment for a booking", "Gift codes"); function stubs in `src/billing/{bookable,booking-pay,codes}.ts`; everything is exported from `index.ts`.

**What is built, in three parts (one PR each).**
- **A. `bookable.ts`.** `Billing` = `free | included {featureId, credits, tierIds?} | price {amount, currency} | included_or_price`. `validateBilling(input, menu)`; `quoteBooking({billing, menu, policy, grants, tierId?, available?, now})` returns a `BookingCost` (`free`, `credits`, `price`) or a typed refusal. `holdBooking`, `confirmBooking`, `releaseBooking`, `cancelBooking`, `noShowBooking`, `expiredHolds`, `settleExpiredHold`: each takes the subject's rows and revision like `handleStripeEvent` and returns `{ rowChanges, events, booking }` or a refusal, so the caller writes one transaction. Engine mapping: hold is `track` with a `lock` (`overageBehavior: "reject"`, `enforceOverdueBlock: true`), confirm is `finalize` with `finalValue: null`, release is `finalize` with `0`; `commandOrg(policy)` is on every command, so the row that lapses soonest is drawn first (and given back to the same row on a release). Events come from `mutationToEvents` with `lowCreditThreshold: policy.lowCreditThreshold`: `credit.held`, `credit.released` or `credit.spent`, and `credit.low` / `credit.depleted` when a spend crosses the threshold or zero. Ids are made from the booking id (`bk:<id>:hold`, lock `bk_<id>`), never from a clock or a random number.
- **B. `booking-pay.ts` and `handle.ts`.** `bookingCheckoutParams` (payment mode, one inline `price_data` line, metadata `b4u_school`, `family_id`, `booking_id`, `b4u_kind: booking` on the session and the payment intent, no invoice creation). `handleStripeEvent` maps `checkout.session.completed` (payment mode, paid), `checkout.session.expired` and `charge.refunded` of a booking's charge to `StripeEventResult.booking` (`paid`, `expired`, `refunded`, `partly_refunded`); the caller confirms, frees or cancels the booking. A refund names a charge, not a booking, so the caller passes `bookingIds` (payment intent or charge id to booking id), learnt from the `paid` outcome, as it does `invoiceIds` today.
- **C. `codes.ts`, `menu.ts`, `stripe-menu.ts`, `normalize.ts`.** `Menu.codes` (member codes, percent off tiers only; `policy.memberCode` stays and means the same for one code); `menuToStripe` makes a coupon restricted to the tier products and a promotion code per code; `checkoutParams` sets `allow_promotion_codes` or, with `code`, `discounts`; invoice lines carry `discount`, and credits never follow it. `dollarGiftOps` returns `GiftStripeOp`s (a fixed-amount coupon, a promotion code with `max_redemptions` 1 and `expires_at`). `createSessionGiftCode` and `redeemSessionGiftCode` (credits as a new grant, once, with an expiry; Stripe is not involved).

**Stored state, compatible with 0.6.0.** `GrantsState` gains two optional keys, `bookings` (by booking id: state `held | spent | released | paid | refunded`, the cost, `startsAt`, `expiresAt`, the open lock row, the payment) and `redeemed` (by code id). Both are absent until used and a rule that does not touch them leaves the state byte-for-byte as it found it (`tests/billing-state-compat.test.ts`); adding them to `EMPTY_GRANTS_STATE` would make every old state look changed to the handler. The lock row is kept in `bookings[id].lock` because the engine's rows keep only an open lock's ids and `finalize` needs the whole row. `Menu` gains optional `codes`, `BillingPolicy` gains `cancelCutoffHours`, `noShow` and `lateCancel` (a stored policy without them gets the defaults), `InvoiceLine` and `BillingInvoice` gain optional `discount`. `StripeEventInput` gains `bookingIds`, the result gains `booking`, a refusal reason `unmatched_booking`, `CheckoutInput` gains `code`. Nothing is removed or renamed.

**New policy fields and defaults** (`resolvePolicy` over `DEFAULT_POLICY`): `cancelCutoffHours` 24, `noShow` `spend`, `lateCancel` `spend`. A hold's expiry action is `confirm` when `noShow` is `spend`, else `release`.

**Rules added after the review of the booking commands (2026-11-05).**
- *What a release gives back.* Every release (`releaseBooking`, a cancel, a late cancel or a no-show that releases, an expired hold that releases) gives each row the units the lock took from it, except: units a refunded or lost-dispute invoice is owed (below) are taken back (`credit.adjusted`); units of a row that has lapsed (`expires_at` at or before the call) or is gone lapsed while held (`credit.expired`, and the row is not refilled, so the cron's lapse of it agrees in either order); units of a tier or add-on row that has reset since the hold (the hold records each such row's due reset, `BookingRecord.resetsAt`) are last cycle's, so they do not go to the new cycle: they come back as a rollover lapsing when last cycle's leftovers do (`next reset at the hold + rollover months`), within the row's rollover cap less the rollovers it already holds, and the rest lapse (`credit.expired`); a row with no rollover lapses them all. Units that do not come back are left off the lock the `finalize` settles (the engine never puts them back) and the events book them as released, then expired or adjusted (`payload.withheld`, read back by a replay).
- *Refunds and disputes while credits are held.* A full refund or a lost dispute takes back the invoice's unused credits as before; what it cannot take because an open booking holds it is recorded in the invoice's record (`InvoiceRecord.owed`, by row id, absent when nothing was held) and taken back by the release that frees it. A confirm spends it (it was used) and clears what is owed.
- *A cancel after the start.* `cancelBooking` at or after `startsAt` is refused as `session_started` (settle it with `noShowBooking`); a cancel between the cutoff and the start is the late cancel.
- *`labels.booking`* on every event of a booking command is the caller's booking id (it was the lock id `bk_<id>`); a replay reads it from the event.
- *Quotes for credits given outside the membership.* The membership's status and `tierIds` limit the tier's and recurring add-ons' credits only: a holder with a pack, a session gift or a redeemed gift code of the feature is quoted credits whatever the membership (`available`, when given, still decides).

**Decisions taken for the open questions** (the owner was asked once; these hold unless changed):
1. Default cancel cutoff 24 hours; a no-show spends the held credits; a late cancel spends them too (a cutoff with no cost is no cutoff).
2. One item can be included for some tiers and priced for others: `included_or_price` with `tierIds` (credits for those tiers, the price for the rest and for non-members).
3. Codes do not stack: one code per checkout (Stripe's own rule for `allow_promotion_codes`), and a member code is not combined with a dollar gift. A discount never reduces the credits granted.
4. Who may create codes is the caller's decision, not atm's: atm has no users. The recommended rule for `buzz-school` is school owners and admins only (the same Cedar check as menu editing); atm only validates what it is given.

**Not built here.** Referral codes (both sides rewarded): the ledger has `referral.qualified` and `referral.rewarded` events but no code table. Rules needed: a referrer's code, one reward each side per first paid invoice of the referred family, no self-referral (same holder or same payment method), a reward as credits through the session-gift path, a reward held until the referred invoice is not refunded. About 200 to 400 lines once the owner picks the reward; tracked in "Referral codes and reconciliation" below.

## 0.9.0 design: B4 Uni's revenue share, in the ledger and invoiced after

Design note (2026-11-05), written before the code. Some schools pay B4 Uni a share of what they collect. Two ways to take it were weighed: **out of the transaction** (Stripe Connect, below, "Later") and **booked in the ledger and invoiced after**. The owner chose the ledger first, because it works with the schools that already pasted a restricted key, needs no new onboarding and leaves a record that `reconcile` can check. Decisions (the owner, 2026-11-05): the share is a **percentage of gross** (the amount collected, before Stripe's fee), it applies to **memberships and paid bookings**, it is computed **on the amount collected** (what the customer paid after discounts, `amountPaid`; a discount lowers the share, a gift code redemption that collects nothing owes none), and the rate is **negotiated per school**.

**What is built, in two PRs.**
1. **Money lines for a paid booking (built in 0.9.0).** A booking's one-time payment books no `payment.succeeded` or `payment.refunded` today (no invoice, and `reconcile` pairs those events with invoices), so it would escape the share. The handler books them from the `booking` outcome (income account `income:billing:booking`), and `reconcile` pairs a booking's payment and refund by payment intent or charge instead of by invoice. Detail: `docs/financial-reports.md`, "The money lines". Open after it: real Stripe was not run (the booking fixtures are `stripe trigger` objects) and a lost dispute on a booking's charge is not mapped.
2. **The share (built in 0.9.0; what is not built is below).** A new policy field `revenueShare: { percent: number } | null` (default `null`: no share; `percent` from 0 to 100 with at most two decimals, so a rate such as 2.5 works), set per school in its `catalog/policy.json` like any policy field. For each payment the handler books (`payment.succeeded`, from an invoice or a booking), it makes a `share.accrued` event: `share = round(amountPaid x percent / 100)` in whole cents, half up, never above the amount paid; postings `expenses:billing:b4uni-share` +share and `liabilities:b4uni` -share (the school's books: it owes B4 Uni). The rate in force, the base and the share are written into the event's payload, so a statement never depends on today's policy and a rate that changes later leaves older payments as they were. A refund makes a `share.reversed` in proportion: the share left after a refund is `share - round(share x refunded so far / paid)`, computed from the running total so that rounding never drifts and a full refund reverses exactly what was accrued. A `share.settled` event (the school paid B4 Uni's invoice: `liabilities:b4uni` +amount, `assets:clearing:b4uni-payments` -amount) is for the caller to record. `shareStatement({ events, month, school })` is a pure report: one row per payment (collected, rate, share, refunds reversed), the totals and what is owed for the month, from the log alone; B4 Uni turns it into an invoice outside atm (a Stripe invoice on B4 Uni's own account, or a bank transfer). The existing `share.charged` (an organization's monthly total) is left as it is.

**Built in PR 2.** `policy.revenueShare`, `share.accrued` / `share.reversed` / `share.settled` (types, envelope enum, payload schemas, postings), the rules in `src/billing/share.ts` (`shareOf`, `shareAfterRefund`, integer arithmetic), the handler's events for an invoice and a booking with the share kept on `InvoiceRecord.share` / `BookingRecord.payment.share`, `shareStatement` and `atm share`, the journal, replay and `reconcile` (which ignores the share). Detail: `docs/financial-reports.md`, "Revenue share"; the steps for a caller: `UPGRADING.md`. Open after it: real Stripe was not run (the tests use recorded-shape events), and the items below.

- [ ] **Not built: a lost dispute reverses nothing**; the share stays until the school asks (a `payment.disputed` on a charge with a share could reverse it in proportion to the disputed amount, as a refund does).
- [ ] **Not built: collecting statements.** B4 Uni invoices from `shareStatement` outside atm and records the payment as a `share.settled`; atm does not charge the school.
- [ ] **Not built: Stripe Connect** (taking the share out of the transaction), below, "Later".

**Not in this design (open, with recommended defaults).** A lost dispute reverses the share on the disputed amount (recommended; not built in v1: the share stays until the school asks). Exclusions by kind (gifts, packs) and a rate per tier are not offered: one rate per school. Collecting an unpaid statement is B4 Uni's business (a card or ACH on file, or the contract); atm records and reports. The family service must pass the rate through `policy`, call the new functions and send the statement to its invoicing.

**Compatibility.** `BillingPolicy` gains `revenueShare` (a policy stored without it has none: no share). Two new event types, `share.accrued` and `share.reversed` (and `share.settled`), join the ledger's closed list: a log reader built before this release rejects a log that holds one, as with `money.skipped`. A school with no `revenueShare` makes none, so its log is unchanged.

## Signed receipts and sealed months (milestone 1)

Built on `dev`, not released (README "Receipts and seals"). Every `payment.succeeded` and `payment.refunded` gets an Ed25519-signed receipt the family keeps (`receiptOf`, `signReceipt`, `verifyReceipt`, `checkReceiptAgainstEvents`), and every closed month a signed seal chained to the one before it (`sealOf`, `signSeal`, `verifySeals`), with `tfd keys new`, `tfd receipt`, `tfd verify receipt`, `tfd seal` and `tfd verify seals`. A receipt is a pure function of its event, so nothing is stored. The canonical form of an event (`canonicalize`) is now part of the receipt format and frozen as canonical v1 by `tests/golden/receipt/`.

- [ ] **Owner decision before release: erasure must not rewrite events.** If a `subject.erased` ever edits stored payloads (to remove `billing_email`, say), every receipt and seal over those events breaks. Choose one: personal data stays out of hashed fields, or erasure deletes keys rather than editing events, or receipts and seals hash `redacted` instead (receipt v2). Check what the family service does today first.
- [ ] **Owner decisions:** the key id format (`trifold-YYYY-MM` is the default); whether a refund and the payment it refunds appear together on a receipt; whether disputes ever get a receipt (now none: a dispute is between the family and its bank); whether the seal waits 7 days after the month ends (the KPI spec's close rule).
- [ ] `buzz-school`: one platform key (`tfd keys new`), the private PEM as a secret and `keys.json` at `/.well-known/trifold-keys.json`; `receiptOf` + `signReceipt` when the family service writes a payment or refund, attached to the payment email and offered in the portal as "Signed receipt"; a monthly `tfd seal` cron after the close, and again when late events arrive; the latest seal per month published to the school's finance admin (and the CPA if wanted). Backfill: `tfd receipt` over history, and seal each closed month oldest first.
- [ ] Known limits, for later milestones: the open month is not sealed until it closes, and an event inserted into a sealed month later reads as a late event (it is listed in `unsealedLate`, not hidden); closing both needs a hash chain over every event written in the webhook transaction. One platform key: rotation works through `key_id` (old keys stay in `keys.json`), a revocation list with dates is not built. Stripe matching (daily, against balance transactions) is not built, so a receipt does not prove Stripe moved the money: say "signed receipts and sealed books", not "triple-entry accounting". Not planned here: per-school keys, a key service, an itemised receipt, PDF or email, a verify web page, receipts for credit events, co-signing, a transparency log.

## Lower priority, after 0.3.0

### Simulation or what-if

- [x] **MRR** (new, expansion, contraction, churned, net new): built. The handler books an `mrr.changed` from the subscription facts Stripe sends (an invoice's recurring lines, a subscription event's priced items, its end), in an `MRR` commodity that the atm fold, hledger and DuckDB each add up (`src/billing/mrr.ts`, `docs/scenarios.md`). Old logs hold no `mrr.changed`: their MRR starts at the next invoice the handler sees.
- [ ] **ARR and logo churn** are not built: ARR is 12 x `mrr` and could be a combine KPI if the spec grows a scale; logo churn needs a count of `mrr.changed` events with `movement: churned`, which hledger can count only while the event has postings (it does). Also open: a `money.skipped` event has no postings, so a hledger journal cannot count it. (detail: docs/scenarios.md#dropped-and-why)

### Revenue share out of the transaction
- [ ] **Take the share out of the transaction (Stripe Connect), later.** Schools connect through Connect (OAuth, in place of a pasted restricted key) and charges become **direct charges** with an application fee: `application_fee_percent` on a subscription (the fee follows each renewal), `application_fee_amount` on a one-time Checkout (`payment_intent_data[application_fee_amount]`, so a paid booking, a pack or a gift). Revisit when more than a few schools pay a share or when collecting statements becomes a cost.

## Decisions taken
- 2026-11-05: PII stripping and a raw input store for usage events are punted; atm stores no raw usage payload and no redacted copy. (docs/usage-metering.md#usage-events-as-a-ledger-source-spike-2026-11-05-decision-pending-on-whether-to-build)
- 2026-11-05: a usage ledger event is an allowlist of the mapping's declared fields (no prompt or message text); `personal` stays a denylist backstop plus the drift check. (same section)
- 2026-11-05: the R2 layer for usage events uses typed quantities as real columns for the hot fields and a manifest written beside the data. (same section)
- 2026-11-05: WAIT on usage events: do not build them until one AI or API product commits as a design partner (or a customer needs per-call credit spending with overage billed through Stripe meters); the spikes, mapping schema and write path stay documented. Build the hosted membership-billing service and the family-service integration first. (detail: docs/pricing-and-positioning.md#decision-wait-on-usage-events-2026-11-05)
- 2026-11-05: usage events, IF built, are written by each gateway worker to a local append-only file (fsynced, not SQLite), closed at about 1,000 to 5,000 events or about 30 seconds, uploaded with a create-only PUT and deleted after success; the daily job dedupes by `idem` and writes Parquet. (detail: docs/usage-metering.md#gateway-write-path-decision-2026-11-05)

- **Usage events as a ledger source** (three spikes, 2026-11-05; reports in `docs/spikes/usage/`). Decision (2026-11-05): wait; revisit when a design partner commits (docs/pricing-and-positioning.md). The Trifold engine stays the credit wallet; Stripe or a separate job prices and invoices.

  - Spike 3, the `track` path as a usage wallet: partly feasible; correct and race-free if the gateway batches, with a hard per-call ceiling; overage is not reportable yet.
