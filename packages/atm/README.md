# The Trifold engine

The Trifold engine runs Autumn's balance engine (`@autumn/balance-engine`) as a local CLI, `tfd`, and as a TypeScript library. It runs one engine command against a subject and returns what the engine decides; it reads and writes nothing else. Trifold is the product and the managed service; this package is its engine. Below, "the engine" alone means Autumn's balance engine inside it.

**The old name.** `atm` is the same command as `tfd` and keeps working. The package is named `tfd` (`import … from "tfd"`, `"tfd/worker"`) and its releases are `tfd-v<version>` with `tfd-<version>.tgz` (through 0.10.0 they were `atm`); a caller that keeps the dependency key `atm` keeps `import … from "atm"`. The code still carries the name `atm` until the later rename steps: the directory `packages/atm`, identifiers inside the code, the SQL tables `atm_*` and the log prefixes `atm: …` (they say `tfd` from the next release, `UPGRADING.md`). In the rename window the environment variables are `TFD_*` with the old `ATM_*` names still read, and every `Atm*` type has a `Tfd*` name (`TfdEvent`; `AtmEvent` is a deprecated alias). So the names below say `atm` where the code does. Some of them never change: `docs/frozen-identifiers.md` lists them, with the reasons.

**Scope.** The Trifold engine handles credits and flat subscriptions: it grants credits from paid fixed-price invoices (tiers, add-ons, gifts) and a `track` spends them. It does not price metered usage or invoice it, and it does not deliver webhooks or email. What is planned or ruled out is in `ROADMAP.md`; what shipped, release by release, is in `CHANGELOG.md`; findings and reference detail are in `docs/` (`docs/README.md`).

Commands it runs: `check`, `finalize`, `confirmExpiredLock`, `reset`, `recalculateBalance`, `track`, `updateBalance`, `deleteBalance`. Not run: `evict`, `initialize` and `applyBillingPlan` take a `SubjectState` (and a catalog or entities), not a subject.

## CLI

```bash
bun install                      # at the repository root
bun run --cwd packages/atm tfd run --subject subject.json --command check.json
```

- `--subject`: a `WorkerFullSubject` (customer, entity, products, entitlements, pools, usage windows, open locks).
- `--command`: an engine command with its `type`, validated by the engine's own parser.
- Either may be `-` to read stdin. The result is printed as JSON; an error exits non-zero.

## Library

```ts
import { runEngineCommand, type AtmCheckResult } from "atm";

const decision: AtmCheckResult = runEngineCommand({ subject, command }); // command.type === "check"
```

- The result type follows `command.type`: `AtmCheckResult` for `check`, `AtmMutation` (row changes guarded by `revision.before`) for `finalize` and `confirmExpiredLock`, `AtmMutation | null` for `reset` and `updateBalance` (null when nothing moves), `AtmMutation` for `track` and `deleteBalance`.
- Inside this workspace, Bun imports the source (`exports` condition `bun`); anywhere else, the built files.

### Reading a school's folder and the ledger helpers (0.9.0)

What `tfd journal`, `tfd report` and the ledger code use, for a caller that reads a school's files or builds events itself. All run under Bun and Node.

```ts
import { readEvents, journalMonth, reportMonth, balancesOf, canonicalize, localDate, decimalToUnits } from "atm";

const { events, files } = await readEvents(root, "sch_vol"); // sorted by id, one event per idem
const run = await journalMonth({ root, school: "sch_vol", month: "2026-03" }); // run.written: [] on a second run
const { reports } = await reportMonth({ root, school: "sch_vol", month: "2026-03", report: "credits", format: "csv" });
```

- `readEvents(root, school)`: the school's events under `<root>/schools/<school>/events`, a repeated `idem` dropped, with each file's key, sha256 and line count.
- `journalMonth({ root, school, month })`: `tfd journal`. Returns a `JournalRun` (`build`, `written`, `unchanged`); throws when the school has no events.
- `reportMonth({ root, school, month, report?, format? })`: `tfd report`. Journals the month, then runs hledger. Returns a `ReportRun` (`journal`, `reports`, `skippedNonUsd`). Needs `hledger` on PATH; throws `HledgerError` (before writing anything) when it is missing or fails. `REPORT_NAMES` lists `income-statement`, `balance-sheet` and `credits`; the types are `ReportName`, `ReportChoice` and `ReportFormat`.
- `balancesOf({ states, holds, catalog, asOfMs })`: the Trifold engine's own balance fold (`avail` and `held` per holder and feature), the list `replayEvents` returns as `balances`. `catalog` is the `menuCatalogRows` output.
- `canonicalize(value)`: JSON with sorted keys and `undefined` dropped, the bytes an event's line and hash are made from. For a sha256 of them, `sha256Hex(utf8(canonicalize(value)))`.
- `localDate(ms, tz)`: `YYYY-MM-DD` of an instant in an IANA zone. `decimalToUnits("130.00", 2)`: a posting's amount as whole units (`13000n`).
- `duckdbDdl(envelope)`: DuckDB `CREATE TABLE` text from the envelope JSON Schema (`schema/envelope.v1.json`).
- `appendToOutbox(db, events, env)`: the one insert into `ledger_outbox` (the handler, `recordEngineCommand` and `recordLapse` all use it). For events a caller built with `ledgerEvent` (a payment or payout that is not an engine command) and wants shipped with the rest. It opens no transaction; an event whose `idem` the outbox already holds in that `env` is left alone; returns the rows inserted.
- Not exported: `reconcileFolder` (it reads a directory of Stripe CLI files; a library caller has `readEvents` and `reconcile`) and `bunSqlite` (its declaration imports `bun:sqlite`; `SqlDatabase` is public and "Logging the family service's own commands" shows the four-method adapter for `node:sqlite` and `better-sqlite3`).

### Reading the log from a Worker (`src/ledger/read.ts`, `summary.ts`, `views.ts`)

The read side for a reader with no disk and no database: an admin UI in a Cloudflare Worker over R2. Everything goes through a `Store` (`R2Store` there, `FolderStore` in tests), so none of it touches `node:fs` or `node:path`. Import them from the `atm/worker` subpath (`dist/worker.js` and `dist/worker.d.ts`; `src/worker.ts` under Bun), which re-exports `ledger/read.ts`, `ledger/summary.ts` and `ledger/views.ts` and their types. The main entry does not export them.

```ts
import { buildViews, membersOf, memberSummary, readEventsFromStore, writeViews } from "atm/worker";

const events = await readEventsFromStore(store, "sch_vol", { from: "2026-03-01", to: "2026-03-31" }); // range optional
const members = membersOf(events, new Date()); // { ok: true, asOf, members: { "family:fam_8k2": { plan, features: { visit: { available, held, used, nextExpiryAt } }, lastEventAt } } }
const built = buildViews(events, { school: "sch_vol", asOf: new Date() }); // { ok: true, views: { school, asOf, months, members, finance, contributions } }
if (built.ok) await writeViews(store, "sch_vol", built.views); // views/months/YYYY-MM.json, views/members/<sha256>.json, views/finance/…, views/kpi/contributions/YYYY-MM.json; `runViews(store, school, asOf)` does read, build and write in one call
```

- `readEventsFromStore(store, school, range?)`: lists `schools/<school>/events/` by day (following the store's cursor), reads each day's batches, and returns what `readEvents` returns for the same folder: a day with a `day.jsonl` is that file and its `late-*` batches, ids sort, and a repeated `idem` is dropped. `range` is an inclusive `YYYY-MM-DD` span of the `date=` partition (the school's local day).
- `membersOf` and `memberSummary` replay the log (`replayEvents`), so they need the catalog the log was written under: pass `{ catalog }` (`menuCatalogRows`) or have a `catalog.published` event in the log, whose menu is used. A log that cannot be replayed (a 0.3.0 log with a lost command, an event the engine decides differently, no catalog) comes back as `{ ok: false, error }` with `kind` `replay-gap`, `replay` or `no-catalog`, never as a throw.
- `used` is the net of the member's postings to `credits:spent:*` and `credits:forfeited` for the feature (a `credit.refunded` takes its units back); expired and released credits are not used. `nextExpiryAt` is the earliest expiry still ahead of `asOf` among rows that hold credits.
- `writeViews` writes canonical JSON and only the objects whose bytes change (`Store.putIfAbsent`, then `putIfMatch` on the ETag read), so a second run with the same `asOf` writes nothing. A member's object name is `sha256(<school>\0<key>)`, which a Worker computes with Web Crypto; the body carries the key. No view holds a name or an email.
- `readViewsFromStore(store, school)` is how a reader opens the views. `manifest.json` lists the SHA-256 of every object (`objects: { <key>: <hex> }`) next to `asOf` and `generatedFrom`; object keys are stable and overwritten in place, so the manifest is written last but is not a snapshot: during a run, after a run that died partway, or after an older run's late writes, an object can differ from it. The reader hashes the bytes it gets and answers `{ ok: false, error: "view-mismatch", key }` for one that does not match (a run is in flight: retry or fall back), `not-in-manifest` for a month or member the generation does not have, `no-manifest`, or `bad-manifest`. It returns values, it does not throw them. Use `reader.membersIndex()`, `reader.member(key)` and `reader.month("YYYY-MM")`.
- `R2BindingStore` (also from `atm/worker`) is the `Store` over a Worker's R2 binding (`new R2BindingStore(env.BUCKET)`): create-only and `If-Match` puts through R2's conditional puts, list pages by cursor, no S3 endpoint or keys. `tests/store-r2-binding.test.ts` runs the Store contract against it in Miniflare; `tests/ledger-read-dist-workerd.test.ts` loads the built `dist/worker.js` in workerd.
- `kpiDocument(rows, contributions, disclosure, audience, pinLocked, context)` (also from `atm/worker`, `src/ledger/kpi-document.ts`) is the KPI document of the ledger UI (`KpiDocument`): one per school, audience and PIN state, with the audience's detail, grain, delay, rounding, cell rules (`<10`, nearest 10, hidden amounts), embargo reasons and the PIN lock already applied from the disclosure (`KpiDisclosure`: size, the B4 Uni file, the school's override; `kpi-disclosure.ts` holds the rule functions). `rows` are the school's KPI export rows (`KpiDocumentRow`, month grain); `context` holds the school, currency, clock and, optionally, the plan order, gifts, per-day gross and the fixture preset. It is pure: no Ajv, no disk, no clock read. `packages/ledger-ui/gates/oracle.ts` is the independent implementation and stays there; `tests/kpi-document-oracle.test.ts` runs both on the 15 mart presets, the five audiences and both PIN states and requires `canonicalize`-equal documents (and the committed `provenance.json` hashes). `contributions` (`KpiContributions`: per cell and month, distinct holders and the largest holder's share) is accepted and not read yet: the oracle's cell rules count the period's paying members. `suppressKpis` and the evaluation it needs (`evaluateKpis`, `kpi-evaluate.ts`, `suppress-core.ts`) are exported too, split out of `scenario/kpis.ts` and `scenario/suppress.ts` (which re-export them) so the Worker does not reach Ajv.
- `audienceViews({ file, override, size, year, clock })` (also from `atm/worker`, `src/ledger/audience-views.ts`) is what each audience sees of a school's books at a clock: for each of the five audiences the `AudienceView` of the ledger UI's disclosure contract (grain, delay, rounding, small counts, cell rules, the period control's presets and periods, and the wording the UI prints), from the B4 Uni file and the school's override. `size` comes from `schoolSize(file, lastClosedYearIncome)`; `surfaceLocks({ file, override, audience, admin })` gives a View as row's lock panels. Pure: no Ajv, no disk, no clock read. `tests/audience-views.test.ts` requires `canonicalize`-equal views for every school of `packages/ledger-ui/src/fixtures/disclosure.json` (the default file only; overrides, the other clocks and the size bands are spec-only cases) and fails if `audience-view-types.ts` drifts from the UI's types.
- Not derivable from the events: the **quantity** a family bought (only the credits it granted), the **renewal date** of a subscription (no `plan.*` event carries a period end), and a booking's **start time** (the only time on a booking is `payload.command.lock.expiresAt` of its `credit.held`, when the hold lapses). Showing them needs the family service's rows or a new field on the events.
- Runtime: `atm/worker` needs the `nodejs_compat` flag in the Worker's config. `ledger/ids.ts`, `ledger/util.ts` and `store/store.ts` import `node:crypto`, `ledger/run.ts` reads and sets `process.env.TZ`, and the engine imports `node:util`; workerd without the flag fails at load with `No such module "node:crypto"` (and `process is not defined` for the `process.env` reads). Three tests keep this honest: `tests/ledger-read-hygiene.test.ts` walks the Trifold engine's import graph and fails on `node:fs`, `node:path`, `child_process`, DuckDB or Ajv (no exception: `billing/grants.ts` takes `commodityProblems` from `billing/commodity.ts`, not `billing/menu.ts`); `tests/ledger-read-bundle.test.ts` bundles `src/worker.ts` with esbuild (`@autumn/balance-engine` and `@autumn/shared` included), fails on Ajv, DuckDB, `node:fs`, `node:path`, `child_process`, `eval` or `new Function`, and pins the `node:*` built-ins left (`node:crypto`, `node:util`); `tests/ledger-read-workerd.test.ts` runs a Worker in workerd (Miniflare) over an R2 binding with `nodejs_compat`, compares its members and views with Node's, and records the error without the flag. The bundle is about 2.1 MB unminified (drizzle, zod, orpc and date-fns come in through `@autumn/shared`, which the engine imports).

## Billing

Pure rules for a school's menu, its Stripe facts, credit grants and storage rows. No I/O, no clock: every function takes its time and state as arguments, so the family service only does I/O around them (read rows, call Stripe, write rows) and the same input always gives the same output.

- Policy: `DEFAULT_POLICY`, `resolvePolicy` (a school's overrides over the defaults), `commandOrg(policy)` (the `org` for every command that draws; see Deduction order).
- Menu: `validateMenu`, `publishProblems`, `publicMenu`, `validTimeZone`, `MAX_TIERS`, `MAX_ADDONS`, `MAX_FEATURES`.
- Menu to Stripe: `menuToStripe` (idempotent steps that make Stripe match a menu), `checkoutParams`, `oneTimeCheckoutParams` (a gift or pack with no membership, with the paid invoice Stripe must make: see Invoices and receipts), `withPriceIds`, `toStripeForm`, `lookupKeyOf`, `portalConfigOf` (the billing portal for tiers sold in quantities: see Billing portal).
  - Quantities: a tier with `quantities` (1 to 6 unique whole counts from 1 to 50, ascending, e.g. `[1, 2, 4]` sessions a month) is sold in one of them, so a studio sells "Shine" at 1, 2 or 4 a month as one tier, not three (`MAX_TIERS` is 4). Its prices and grant amounts are per unit; a tier without `quantities` is sold one at a time. `checkoutParams` takes `quantity` (default 1): one of the tier's counts, else `{ reason: "quantity_not_offered", quantity }` (the family service answers 400 `fields: ["quantity"]`). The tier's line is at that quantity, add-ons at one, and the subscription's metadata says `quantity` unless it is the default 1 (informational: the item's quantity at Stripe is the truth). Lookup keys and Stripe prices are per unit, so changing a tier's `quantities` makes no `menuToStripe` step, and the member code takes its percentage off each unit. Credits follow paid invoices: a raise (same tier, more units) grants the extra units' share of the cycle left per `policy.upgradeGrant`, and needs the subscription update made with `proration_behavior: "always_invoice"` so Stripe bills it at once; a decrease grants nothing and takes effect at the next renewal (schedule it, so the lower count is not billed early), where the allowance refills at the new count and the rollover cap, one per row in the engine, follows the new lower count. A line with a quantity below 1 is dropped, never counted as 1. A yearly plan paid once grants twelve monthly allowances per unit.
- Stripe events to facts: `normalize`, `mappingFor`, `mappingLabels`, `MAPPINGS` (declarative mappings in `schema/mapping/`, bundled; regenerate the index with `bun schema/mapping/build.ts`), `resolveLines`, `resolveInvoice`, `resolveSubscriptionPlan`, `redactPersonal`, `subscriptionStatus`.
- Facts to credits: `menuCatalogRows`, `invoiceToCommands`, `refundToCommands`, `disputeToCommands`, `subscriptionToCommands`, `subscriptionEndedToCommands`, `EMPTY_GRANTS_STATE`, then `runOnState` to run the commands (an invoice makes an `applyBillingPlan`, which `runEngineCommand` does not run). A refund or dispute reads what each credit row holds from the subject (`subjectFromRows`), so it never takes a balance below zero and also takes back the rolled-over leftovers of the invoice it refunds. A canceled subscription stops the refills and lets its last cycle's unused credits lapse at their own expiry.
  - Every `customer.subscription.created/updated/deleted` also records `membership` in the grants state: the status (`subscriptionStatus`), the tier and interval the menu names for the subscription's price items (by lookup key, else price id; the checkout metadata goes stale after a portal change and is not read), the renewal or end date, and the event time. It grants nothing: credits come from paid invoices, so `tierId` and `interval` in the grants state move only with an invoice, and a change Stripe has made that no invoice has paid yet shows as `membership.tierId` differing from `tierId`. An older event than the one on record, or a replay, changes nothing. A subscription seen before its first invoice names the family in its metadata and makes a grants-only write.
  - By design (B4 Uni "Default billing rules"): a partial refund and an open dispute change nothing; only a full refund and a lost dispute take unused credits back.
- Storage rows: `subjectKey`, `subjectFromRows`, `rowChangesFromMutation`, `applyRowChanges`, `stateFromRows`, `rowsFromState`, `ROW_TABLES`, `assertRevision`, `StaleRevision`. The billing rules' `GrantsState` is one more JSON row of the subject (`GRANTS_TABLE`, `grantsFromRows`, `grantsRow`) under the same revision.
- **One entry point**: `handleStripeEvent({ event, eventId, menu, menuVersion, policy, policyVersion, rows, revision, catalog, now, priceIds, invoiceIds })` gives `{ rowChanges, events, refused? }` (`events` are the `credit.*` events, plus a `plan.changed` for each engine command that moved no credits, and the money lines below). The caller verifies the signature, dedupes on the event id, loads the subject's rows, calls it and writes `rowChanges` and `events` in one transaction. Replaying an event gives `rowChanges: null`; an event the Trifold engine cannot decide comes back `refused` with no rows and no credit events to write (for a paid invoice refused with `unmatched_line`, `tier_on_other_subscription`, `addon_only_subscription` or `rejected`, `refused.payment` holds its payment line, because Stripe has collected the money whatever the menu says: the reference handler appends it as it releases the claim, and the retry that is applied after the cause is fixed does not book it again; see `docs/financial-reports.md`) (among the reasons, `addon_only_subscription`: a paid invoice for a recurring add-on on a subscription that is not the member's tier subscription, or before the member has one; the Trifold engine grants a recurring add-on only on the tier subscription, so it would be paid and give no credits. Put the add-on on the tier subscription in Stripe: it is granted from that subscription's next invoice, and re-sending the refused invoice gives the same refusal). Two things a Stripe event (API `2025-10-29.clover`) does not carry are the caller's: `priceIds` (lookup key to Stripe price id, from publishing the menu: a line names its price by id only) and `invoiceIds` (payment intent to invoice id, from `invoice_payment.paid`: a charge or dispute does not name its invoice).
- **`env` (`"live"` or `"test"`).** `handleStripeEvent`, the grants functions (`invoiceToCommands` and the rest), `menuCatalogRows` and the reference handler's `WebhookDeps` take an optional `env`, default `"live"`; anything else throws. It is the middle part of the subject key (`<school>|<env>|family:<id>`) and `identity.env` on every command. A school with both a test and a live Stripe endpoint should pass it on each, with the same `env` to `menuCatalogRows`, so the two do not share a subject. Omitted, every row, key and event id is what it was. The handler also compares the event's `livemode` with `env` and refuses a mismatch (422 `livemode_mismatch`, before any claim, nothing written; an event with no `livemode` is not refused), so a test-mode endpoint must pass `env: "test"`. The handler's claim, invoice index and outbox are keyed by Stripe's ids and carry no env: Stripe ids differ between modes, so the two never meet, but one id delivered under both envs in one database is claimed once.
- **One API version.** The Trifold engine reads Stripe API `2025-10-29.clover` and refuses any other. An endpoint left on an older version sends invoice lines in another shape (`line.price.id`, `line.proration`); `handleStripeEvent` answers it `refused` as `unknown_mapping` with a message that names the endpoint's version (`event.api_version`) and the fix: recreate the endpoint with `api_version` `2025-10-29.clover`. It does not read a second shape: the pinned version's mappings are checked against that version's OpenAPI spec, and a second mapping would be unchecked. `describeNormalizeError` gives the same sentence for a `normalize` or `mappingFor` error.
- **Moving a caller that grants on its own** (B4 Uni's family service, with `school_memberships` and `school_credit_lots`): `grantsStateFromCallerRows({ membership, lots, menu, now })` returns `{ state, rows, events, revision }` for a member: the engine rows (the newest cycle's lots of each grant, raises included, as its refilling credit row, the leftovers of earlier cycles as rollovers with the caller's own expiry, one-time add-ons and admin adjustments as their own rows, a dropped add-on's lots as a retired row), the opening events that create the subject with those rows (append them with the rows, so the log replays), and the `atm_grants` row, whose `invoices` names every invoice the lots name, so replaying one grants nothing again. The row types are `CallerMembershipRow` and `CallerCreditLotRow`, mirroring the columns of migrations 0131 and 0134; the Trifold engine imports nothing of the caller's. The name is not `stateFromRows` (taken: the Trifold engine's rows to an engine state), and it returns the rows too, because a renewal runs the engine's reset on engine rows, which the grants state alone does not hold. It throws, naming each problem, rather than guess; see `UPGRADING.md` ("Moving an existing caller onto handleStripeEvent") for what it refuses and where the Trifold engine's rules differ from the caller's.
- Shapes: `schema/stripe/objects.clover.json` is Stripe's OpenAPI spec for the pinned API version, pruned to the objects the mappings read (`bun run stripe-spec <spec3.json>`). The tests check every mapping path and every synthetic event against it.
- **Money lines: what the handler's log holds beside the credits.** `handleStripeEvent` also makes the books' lines (USD only; another currency makes none, only a `money.skipped` marker, and the delivery is answered 200 `non_usd` instead of `applied`), each with the Stripe object's id as its idem (`stripe:in_...`, `stripe:evt_...`, `stripe:po_...`), so a second delivery makes the same line and the outbox's `(school, idem)` key drops it. An `invoice.paid` is a `payment.succeeded` (the invoice's `amount_paid` to `income:billing:membership:<tier>`, else `income:billing:addon:<add-on>`, else `income:billing:other`; a paid invoice with several lines books all of it under the tier). A `charge.refunded` is a `payment.refunded` for what that event refunded (`amount_refunded` less `previous_attributes.amount_refunded`), but only for a charge that names an invoice whose payment the books hold (an invoice handled before payments were booked, one that paid nothing or in another currency, and one a caller adopted have none, so their refunds make no line, except that a refund in another currency leaves a `money.skipped` marker); Stripe keeps its fee on a refund, so none is booked back. A `charge.refunded` delivers a Charge, which has no refund id (`re_...`) in API `2025-10-29.clover`, so the refund line is labelled with the Stripe event id (`payload.id` and idem `stripe:evt_...`) and its payload also names what ties it to Stripe's refund list: `charge`, `payment_intent` (when the charge has one), `invoice` (the one the handler resolved through the payment index) and `amount_refunded` (the charge's total refunded after this event, which `amount` was taken from). The four are optional in `schema/payload/payment.refunded.v1.json`; a log written before them stays valid. A booking's one-time payment (the paid `checkout.session.completed`, or `async_payment_succeeded`, of a session `bookingCheckoutParams` made) is a `payment.succeeded` too, for the session's `amount_total` to `income:billing:booking`, with `StripeEventInput.fee` read as for an invoice (the fee of the payment intent's charge; the same refusal for a fee that is not whole cents from 0 to the amount), idem `stripe:<payment intent id>` and payload `id` the payment intent, `booking` the booking id (also in `labels.booking`), `session` and `payment_intent`; its `customer` is the holder's id in the Trifold engine (`family:<id>`), as the session names no Stripe customer. A refund of a booking's charge is a `payment.refunded` for what that event refunded (`amount_refunded` less `previous_attributes.amount_refunded`, as for an invoice; one line per Stripe refund whatever the order the events arrive in, and a redelivery makes the same idem), while the booking's own record keeps the running total for its state and the share's reversal; the payload names the `booking`, and only a payment the books took is refunded in the books (`BookingRecord.payment.booked`, absent on a record made before this and on a non-USD payment, which leaves a `money.skipped` marker of kind `booking`, and its refund one of kind `refund`). A Stripe `payout.paid` is a `payout.paid` from `assets:stripe` to `assets:clearing:stripe-payouts` for the payout's `amount` (already net of fees), keyed by the payout id: it names no family and no school, so it is booked to `deps.schoolId` (give each school its own endpoint on the school's own Stripe account; a Connect endpoint would send every connected account's payouts to one school) and `input.school` carries it into `handleStripeEvent`. A dispute that moved money books a `payment.disputed` (and a `dispute.closed`) in USD, and in another currency only a `money.skipped` marker of kind `dispute` (`docs/financial-reports.md`, "Non-USD"). A `payout.failed` puts a paid payout back: it books a `payout.paid` with its sides swapped (`assets:stripe` up, `assets:clearing:stripe-payouts` down by the payout's amount, payload `failed: true`, idem `stripe:<payout id>:failed`, dated by the failure, fees untouched), once per payout however many events say so, and waits (409 `unmatched_payment`) until the payout's own `payout.paid` is booked; a payout that is paid again is a new `po_` id and books as any payout. `payout.created`, `payout.canceled` and `payout.reconciliation_completed` book no money line and are answered `ignored`.
- **The fee is the caller's, and optional.** No webhook event carries Stripe's fee: it is the `fee` of the charge's BalanceTransaction (`charge.balance_transaction`, an id), and an `invoice.paid` names neither the charge nor the transaction. So the fee is an input, which keeps `handleStripeEvent` pure: `StripeEventInput.fee` (cents), and for the reference handler the optional `WebhookDeps.paymentFee(event)`, called with the raw `invoice.paid` inside the transaction (it must answer from what the caller already holds, so read Stripe before calling the handler: the invoice's payment, its charge and that charge's `balance_transaction`, as the school's own account). With the fee a payment books gross, `expenses:billing:stripe-fees` and the net in `assets:stripe`; without it (no dependency, or it answers `null`) the payment books the gross with no fee line, its payload says `fee_known: false`, and `assets:stripe` runs higher than Stripe's balance by the fees. The fee is fixed at the first delivery of the invoice: a fee learnt later is not added (the payment is booked once, and a re-send is answered `duplicate`). Unreleased: a payment booked without a fee is no longer silent: the `200 applied` answer lists it in `body.feeUnknown`, `deps.warn` says it is booked gross, `tfd reconcile` counts such payments (`feeUnknown`) and `tfd report` prints a stderr note; the books themselves are unchanged (`docs/financial-reports.md`, "A payment booked without its fee"). A fee that is not a whole number of cents from 0 to the amount paid is refused (422 `bad_event`).

### Quantity raises without the grants state

`invoiceToCommands` needs the whole `GrantsState`. A caller that keeps its own credits (the family service uses only `runEngineCommand`) reads a raise of a tier's quantity with the same two pure functions `invoiceToCommands` calls, so the rule has one copy:

- `prorationPair(lines, isTierPrice)` returns `{ oldQuantity, newQuantity, start, end }` or `null`. `lines` are the invoice's lines (`InvoiceLine`, or anything with `proration`, `amount`, `quantity` and, in ms, `periodStart` and `periodEnd`); `isTierPrice(line)` picks the lines of the tier's price. Stripe's raise is a pair of proration lines: the credit line (negative) holds the OLD quantity, the charge line (positive) the NEW total, not the difference. With several pairs (a decrease made with `create_prorations` leaves an older one pending) the positive line that starts last is the raise, and its credit is the one that starts with it. `start` is when the raise took effect, `end` the end of the cycle. `oldQuantity` is null without a credit line, and the result is `null` without a charge line. It throws on a bad argument, on a non-finite `amount` or `periodStart` on any tier proration line, and on a bad `quantity`, `periodEnd` or period of the chosen charge and its credit; an older pair that is not the raise is not checked beyond that.
- `raiseUnits({ perUnit, oldQuantity, newQuantity, at, cycleStart, cycleEnd, policy })` returns the units to grant: (new - old) x `perUnit` x the share of the cycle left at `at`, rounded up, following `policy.upgradeGrant` (`prorated`, the default; `full`; `none`). A decrease or the same count gives 0; without a cycle (either end null) the whole difference. `perUnit` is the grant per unit for the cycle (a yearly plan on a monthly grant: twelve times it). Only `policy.upgradeGrant` is read. It throws an `Error` naming the field on bad input (a value that is not a finite number, a negative or fractional count or `perUnit`, or `cycleEnd` before `cycleStart`) instead of returning a wrong number. It cannot see a unit: `at`, `cycleStart` and `cycleEnd` must all be milliseconds, and a cycle in seconds is not detected. `invoiceToCommands` does not use these checks (it calls unchecked cores), so a malformed value in a Stripe event never makes the webhook throw.

`oldQuantity` for `raiseUnits` is the quantity your credits reflect, not the pair's `oldQuantity`. A decrease that waits for the renewal grants nothing, so after one Stripe's count is lower than the credits' count; a raise counted from Stripe's would grant units the member already holds.

```ts
import { DEFAULT_POLICY, prorationPair, raiseUnits } from "atm";

const pair = prorationPair(lines, (line) => line.priceId === tierPriceId);
if (pair?.start != null && pair.end != null) {
  const units = raiseUnits({
    perUnit: 2, // visits a unit grants a month
    oldQuantity: membership.creditQuantity, // what the credits reflect
    newQuantity: pair.newQuantity,
    at: pair.start,
    cycleStart: membership.cycleStart,
    cycleEnd: pair.end,
    policy: DEFAULT_POLICY,
  });
  // grant `units` (0 means nothing). Store pair.newQuantity as creditQuantity only when it is above the current
  // creditQuantity: a pair below it is a decrease (or a raise short of what the credits hold), and a decrease takes
  // effect at the renewal, where the refill sets creditQuantity to the renewal line's quantity.
}
```

### Invoices and receipts

A family that pays a school needs a document: an itemised, dated receipt (B4 Uni's Idaho tutoring brief: legal name, EIN and address of the seller, the child's legal name, subject, dates, hours, price, tax, how and when paid). The Trifold engine holds the rules only, so this is what it gives and what it leaves to Stripe and the caller. What Stripe does is read from its docs (Create invoices with Connect; Receipts and paid invoices), as read on 2026-11-05; nothing was created in a Stripe account.

- **A membership's Checkout already makes an invoice.** In subscription mode Stripe makes an invoice for the first payment and every renewal, with a hosted page and a PDF, so `checkoutParams` needs no `issuer` or `on_behalf_of`. For a direct charge the invoice is made on the school's own (connected) account, and Stripe's docs say direct-charge receipts use the connected account's customer emails, branding and public details. `issuer` and `on_behalf_of` are what a platform sets on invoices on the PLATFORM account (destination charges, separate charges and transfers) to print a connected account's branding and tax ID; B4 Uni sells by direct charge, so they do not apply. Not checked: a real connected account's invoice (the recorded payloads come from a plain sandbox account, `issuer.type` `self`). The school's EIN prints only if the school adds it to its Stripe account as a tax ID (a `us_ein` tax ID, with `settings[invoices][default_account_tax_ids]` set, per the Connect page); the caller or the school's setup does that, not the Trifold engine.
- **A payment-mode Checkout makes none.** A gift certificate or a pack bought on its own (`mode=payment`) makes no invoice unless `invoice_creation[enabled]=true`, and with none there is no `invoice.paid` event, so the Trifold engine has nothing to grant from. `oneTimeCheckoutParams({ schoolId, menu, addonIds, familyId, forProfileId?, menuVersion, returnUrls, invoice? })` returns the payment-mode parameters with `invoice_creation` on, or `{ reason }`: `no_addons`, `addon_not_found`, `addon_not_one_time` (the add-on repeats, so it goes on a membership's checkout). `checkoutParams` is unchanged and stays subscription-only (a tier is required and the output has no `invoice_creation`): the one-time sale is its own function, not a flag, because it is a different Stripe mode with different parameters. The invoice's `invoice_data.metadata` holds `b4u_school`, `family_id`, `menu_version`, `addon_ids` and `profile_id`: Checkout's session `metadata` does not reach the invoice, and `handleStripeEvent` finds the family on the invoice's own metadata. `invoice.description` and `invoice.footer` pass through to `invoice_data` when given. `withPriceIds` and `toStripeForm` take its result as they take a membership's. The invoice it makes is a `manual` invoice with no subscription, which the grants rules already credit (a gift or a pack). Stripe prices post-payment invoices for Checkout apart from Invoicing (see Stripe's pricing note on that page).
- **The links are on the fact.** `BillingInvoice` (from `invoice.paid`) carries `number`, `hostedInvoiceUrl` and `invoicePdf` (each `string | null`; absent on a fact built by hand), read by the declarative mapping from `number`, `hosted_invoice_url` and `invoice_pdf` (all in the pinned OpenAPI spec). The two URLs are bearer links: whoever holds one can open the invoice, which shows the customer's name. Show them only to the family the invoice belongs to, and keep them out of logs. They are not in the mapping's `personal` list, so the stored raw event keeps them (the raw event always held them).
- **Not built: an itemised receipt.** (`receiptOf` is now the signed receipt in "Receipts and seals" below: a proof of payment with no items, tax or student.) The Trifold engine does not know what the Idaho receipt needs: the subject and the hours of a session (a menu line has a name and a count, no subject or length), tax (the normalized invoice carries none; Stripe's `total_taxes` and each line's `taxes` are arrays, which a declarative mapping cannot sum), the per-student split of one family's invoice, and whether the receipt is for what was bought (an invoice) or what was delivered (a session on a date). The options are in `docs/receipts.md` ("Owner decision: the itemised receipt"); it waits on the owner.

### Billing portal

`portalConfigOf(menu, { products, prices })` returns the form fields for `POST /v1/billing_portal/configurations` (the flattened `features[...]` shape `toStripeForm` makes), or `null` when no tier is sold in quantities (the school's default portal then applies). `products` and `prices` hold the Stripe ids the publish made, by the menu's keys: `products["t:<tierId>"]` and `prices["t:<tierId>:<interval>"]`. The caller makes the request, stores the configuration's id, and passes it as `configuration` on every `POST /v1/billing_portal/sessions`.

- A **raise** is billed at once (`features[subscription_update][proration_behavior]=always_invoice`), so its paid invoice grants the extra units now; a **decrease** is scheduled for the renewal (`schedule_at_period_end` with `decreasing_item_amount`) and grants nothing. Without this configuration, Stripe bills a raise at the renewal and nothing is granted until then.
- Only the quantity can change (`default_allowed_updates=[quantity]`): one `products[]` entry for each public tier with more than one count in `quantities` and a published product, with its published prices and `adjustable_quantity` from its smallest to its largest count. A tier switch is not offered. A tier with one count, a tier that is not public, a tier with no product id and a tier with none of its prices published (Stripe requires `prices` on each product) are left out. Stripe takes the quantity as a range, not a list: a tier sold in `[1, 2, 4]` also lets a member pick 3 in the portal (`checkoutParams` refuses 3 as `quantity_not_offered`), and the credits follow the quantity per unit.
- Cancel is at the period end; the payment method and the invoice history are enabled. The configuration is marked `metadata[b4u_key]=portal`.
- Field names are from Stripe's API reference for portal configurations. The Trifold engine's pruned OpenAPI spec (`schema/stripe/`) holds only the objects the mappings read, so the request is not checked against it.

### Deduction order

A `track` takes from a holder's credit rows for one feature in this order (Autumn's engine, `balance-engine/src/deduction/deduct.ts`):

1. **Unlimited** rows.
2. **Rollovers**, soonest-expiring first, rollovers without an expiry last. A rollover is always spent before the row it came from, whatever the order below.
3. **Included** rows, in the order below.
4. **Overage** (only where the plan allows it).

`policy.deductionOrder` sets the order inside step 3. The caller puts `commandOrg(policy)` on every command that draws: `track`, `check`, `finalize`, `updateBalance` (the gap to a target balance, or the amount, is drawn like a `track`), `deleteBalance` (the usage moves to the rows left) and `recalculateBalance` (it redraws the usage); a caller that sends its own org config gets `engine` (the second line below), because the engine reads the setting from the command, not from the Trifold engine.

- `expiry` (default): the row whose unused credits lapse soonest goes first, then the oldest grant (`created_at`). A refilling row lapses at its `next_reset_at` (what is left rolls over within its `max`, or is lost); a one-off row (gift, pack, a cancelled plan's last cycle) at its `expires_at`; a row that never lapses goes last. The engine keeps its earlier groupings (listed balances, entity level, boolean, credit systems, unlimited) and reorders only within each.
- `engine`: Autumn's own order. Rows that refill (have a `next_reset_at`) first, then the shorter reset interval, then soonest `expires_at` (none last), then add-ons after the main plan, then prepaid before pay-per-use, then oldest first. `reverse_deduction_order` (off in `commandOrg`) flips the first two steps; under `expiry` it has no effect.

So a gift that lapses before the tier's next reset is spent first under `expiry` and after the tier row under `engine` (`tests/billing-handle.test.ts`, "deduction order"). The engine option (`org.config.deduction_order`, off unless set) is listed in `../../UPSTREAM.md`.

### Expiry rules (`policy.rulesVersion`)

Rollovers, one-time add-ons and a canceled plan's last credits lapse some months after a date. Under rules version 1 (absent from a policy, and the default) the months are counted on the UTC calendar; under `"rulesVersion": 2` on the menu's (`menu.timeZone`), the same wall-clock time some months on, so a rollover made at 11:00 in Denver in February lapses at 11:00 in Denver in March, an hour earlier in UTC than version 1 says. The handler passes the zone to the engine's `reset` as `org.config.rollover_time_zone`. A stored context keeps the version it was decided under, so a log replays unchanged; set version 2 on a school before its first event or with a new `policyVersion`. `"rulesVersion": 3` (0.11.1) is version 2 plus the lapse of an unpaid cycle: `lapseUnpaidCycle` dates the refilling rows of a member whose paid cycle ended with no renewal paid, at the cycle's end plus the grant's rollover months (no rollover: at the cycle's end), so `recordLapse` books their `credit.expired` when it passes. A renewal paid before that date takes the dating back; one paid after it finds the lapsed credits gone and grants the cycle's allowance (`UPGRADING.md`, "Lapse"). `giftSessionMonths: null` makes a session gift lapse like a one-time add-on (its grant's rollover months, or never) and a gift code's credits never lapse. buzz-school's schools use `{ rulesVersion: 2, giftSessionMonths: null }` (`UPGRADING.md`, D12).

### The school's webhook endpoint

The handler reads Stripe API version `2025-10-29.clover` only. `createCloverEndpoint({ secretKey, fetch, url })` creates a school's endpoint on its own Stripe account at that version, with `STRIPE_WEBHOOK_EVENTS` (the 10 types the handler takes) and `v=clover` on the URL, and returns `{ id, secret, … }` (the secret is shown once: seal it). `checkCloverEndpoint(await retrieveWebhookEndpoint({ secretKey, fetch, id }))` names anything wrong with an endpoint, and `retireWebhookEndpoint({ …, id, action: "disable" | "delete" })` retires the old one after the handover; it refuses an endpoint at clover. Every call goes through the `fetch` passed in, with the school's key; nothing is read from the environment. The two-endpoint handover is in `UPGRADING.md` (D12).

### Credit events that are not a balance change

`credit.expiration_changed` says a row's credits stay but their end date moved (a cancelled plan's rows stop refilling and lapse at the last cycle's end plus the rollover months). It carries the row, `previous_expires_at`, `expires_at` and `refills_ended`, has no postings, and is emitted only when the date changes without a balance change in the same write.

`credit.low` ("N visits left") and `credit.depleted` ("pack used up") say a draw by the family took a holder's available balance of a feature across a line. The Trifold engine emits them; the family service delivers the mails. Only a `track` (a booking's hold) or a `finalize` makes them: never the rules' own take-backs (a refund or lost-dispute clawback is an `applyBillingPlan`, labelled `credit.adjusted`), an `updateBalance`, `deleteBalance` or `recalculateBalance` by hand, or a reset, so `handleStripeEvent` makes none. `credit.depleted` is a balance that goes from above 0 to 0; `credit.low` is one that goes from above `policy.lowCreditThreshold` (default 2; 0 turns it off) to at most it, and not to 0 (a draw straight from 5 to 0 is only `credit.depleted`). Each is made once per crossing, never while the balance stays below, and never when it does not go down (a grant, a refund, a reset). The balance is the sum over all the feature's live rows and rollovers, so a pack on top of a tier counts, and it is the balance after holds: a booking's hold is the draw, a cancel (`credit.released`) gives the credits back with no event, and booking again crosses, and alerts, again. It does not remember that it already alerted: the family service dedupes its notices per holder, feature and grant or cycle. The labels have `feature` but no `plan` (the crossing is judged on the feature's total over every plan). The payload is `feature`, `available`, `threshold` (null on `credit.depleted`) and `previous_available`, beside the command and mutation; there are no postings; the idem is `<prefix>:<mutation id>:low:<feature>` or `...:depleted:<feature>`. `mutationToEvents` makes them only when the context has `lowCreditThreshold` (the caller passes the policy's on its `track` and `finalize` events) and the `before` state.

A pack that lapses unused is "pack used up" too. `lapseAlertEvents` (beside `lapsedRows`/`lapseEvent`; the cron calls it with the state it read, and `drawnAfter`) returns a `credit.depleted` for a feature whose total over every plan goes from above 0 to 0 or below at an instant rows lapsed: one event per instant, so two rows lapsing together (or a rollover with its grant) make one, and none when other credits remain. It has `source: "cron"`, no postings, the payload `feature`, `available`, `threshold: null`, `previous_available` and `cause: "expired"` (no command or mutation), and the idem `lapse:<key>:depleted:<feature>:<instant>`, so a re-run books nothing new. The state holds balances as of now and no draw times, so a cron that runs late would judge a past instant on credits the family has since drawn from another live row (a false depletion): the required input `drawnAfter(t)` is the units of the feature the holder drew strictly after `t` and up to `atMs`, from the cron's ledger or journal (draws only; a refund take-back or reset is counted only if the caller folds it in; it is called once per lapse instant, with `instant - 1`, so it counts a draw at the lapse instant itself, which could not have used the lapsed row), and each instant is judged with them added back. `() => 0` is right only when the state is as of the lapse. Give it the `revision` you give the `credit.expired` events of the same instant (the highest, if they differ): the alert is made at `revision + 1`, so it sorts after them in every order the ledger has (replay, journal, month files) while its `eventMs` stays the instant; a revision that is not a whole number, or is 16777215 or more, throws. It is opt-in by being called (`lapseEvent` is unchanged, so a cron that does not call it gets the events it always got), and no `credit.low` is made on a lapse, on purpose.

### Logging the family service's own commands

Only the handler writes `ledger_outbox`, so a log shipped by `tfd ship` holds the money and the grants but not what the family service runs itself (holds, finalizes, spends, refunds, the expiry cron): `bal credits:` cannot match what members used, and `replayEvents`, which needs every command the engine ran, stops. `recordEngineCommand` and `recordLapse` append those to the same outbox, with the same ids, `idem` and ordering as the handler's. They take the caller's `SqlDatabase` and open no transaction: the caller wraps them with its row write, one transaction per command, in this order:

1. run the engine command on the subject's rows as stored (`runEngineCommand`, or `runOnState`);
2. write the rows, checking the revision (`rowChangesFromMutation` gives the writes; a stale revision rolls everything back);
3. `recordEngineCommand({ db, mutation, before, context })`: `mutation` is what the engine returned, `before` the state it ran on, `context` how the events are booked (`tz`, `feature`, and as the command needs `service`, `as: "refunded"`, `reason`, `settleAs`, `lowCreditThreshold`).

```ts
db.transaction(() => {
	const mutation = runEngineCommand({ subject, command });
	writeRows(rowChangesFromMutation({ mutation, rows, revision })); // revision-checked
	recordEngineCommand({ db, mutation, before: state, context: { tz, feature: "visit", service: "massage-90" } });
});
```

Call it after every engine command, with a `commandId` of its own for each command, unique across the school (`idem` is `engine:<commandId>:<kind>`, one per school, so an event the outbox already holds is left as it was). Recording the same mutation again books nothing twice; a command id that is already in the outbox for another subject or another revision (a second command under a booking's id, a retry that ran the engine again on rows that moved on) throws, and the caller's transaction rolls its rows back. A `reset` or an `applyBillingPlan` throws too. A command the engine rejected or decided nothing for writes no event and no rows; one that moves no credits is a `plan.changed`, as in the handler. The expiry cron calls `recordLapse({ db, state, featureOf, feature, atMs, tz })` where it reads the state (idempotent by holder, row and expiry; `drawnAfter` opts in to `credit.depleted`).

`payload.complete` is a claim by the writer that it logs every command it runs, so a replay may step over a revision that has no event (a write of the grants row alone). The handler sets it; these functions set it only with `logsEveryCommand: true`, which a caller says only if it records every command for the subject. `replayEvents` reads it only for commands named `<ULID>:<step>` (the handler's names), so a caller whose command ids are anything else needs nothing. One call is for a command that moves one feature (`track`, `finalize`, `confirmExpiredLock`, `updateBalance`); the multi-feature commands (`reset`, `applyBillingPlan`) are the handler's and are not recorded here.

### Membership status

`incomplete` means the first payment is not finished (Stripe `incomplete`); the other values are `active`, `past_due`, `ended` and `inactive` (`status.ts`).

### Bookings, paid bookings and codes (0.8.0)

The Trifold engine prices what a booking or an event costs and spends the credits for it; the caller stores the rows and talks to Stripe. What to call, in the order a booking goes:

- `validateBilling(billing, menu)` checks an item's price tag: `free`, `included { featureId, credits, tierIds? }`, `price { amount, currency }` or `included_or_price` (credits for the tiers in `tierIds` that can afford it, the price for the rest).
- `quoteBooking(...)` gives the cost for one member: nothing, credits to hold, or a price, or a typed refusal.
- `holdBooking`, `confirmBooking`, `releaseBooking`, `cancelBooking`, `noShowBooking`, `expiredHolds`, `settleExpiredHold` hold credits on an engine lock (the balance's `held`), then spend them or give them back. `cancelBooking` and `noShowBooking` follow `policy.cancelCutoffHours`, `policy.lateCancel` and `policy.noShow`. Each takes the subject's rows and returns one write and its events, like `handleStripeEvent`; the events include `credit.low` and `credit.depleted` at `policy.lowCreditThreshold`.
- `bookingCheckoutParams(...)` makes a payment-mode Checkout Session for a paid booking; `handleStripeEvent` answers `checkout.session.completed`, `.expired` and the refund of its charge with a `booking` outcome (`paid`, `expired`, `refunded`, `partly_refunded`). A paid booking and its refund also book money lines (below, "Money lines"): a booking has no invoice, so its payment is paired with Stripe's payment intents by `reconcile`.
- Member codes are `menu.codes` (percent off tiers; `menuToStripe` makes the coupon and promotion code, `checkoutParams` allows or applies a code); `dollarGiftOps` makes a one-use dollar gift's Stripe steps; `createSessionGiftCode` and `redeemSessionGiftCode` make and redeem a code that grants credits, once, with no Stripe.
- A discount never changes the credits an invoice grants.

What the caller has to store and handle, with the order of calls and every refusal: `UPGRADING.md`, "Moving to 0.8.0 from 0.6.0". The design and what is not built: `ROADMAP.md`.

### Revenue share (0.9.0)

A school that pays B4 Uni a share of what it collects sets `revenueShare: { "percent": 2.5 }` in its `catalog/policy.json` (`null`, the default, is none). `handleStripeEvent` then books a `share.accrued` after each payment it books (an invoice's or a paid booking's, on the amount collected before Stripe's fee) and a `share.reversed` after each refund, in the school's ledger (`expenses:billing:b4uni-share`, `liabilities:b4uni`); the caller records a payment to B4 Uni as a `share.settled` event. `shareStatement({ events, school, month })`, or `tfd share --root <folder> --school <id> --month YYYY-MM`, is the month's statement (rows per payment, totals, what is owed), which B4 Uni invoices from outside the Trifold engine. A school with no rate makes none of it. Detail: `docs/financial-reports.md`, "Revenue share".

### Stored inputs (new in 0.10.0)

The reference handler (`handleStripeWebhook`) now keeps what it needs to decide each Stripe event again, so that a later what-if can replay the grant rules (`tfd simulate --inputs`, below; the design is `docs/simulate-from-inputs.md`). Nothing changes for a caller except four more tables.

- **What is stored.** One row in `atm_event_inputs` per `(env, Stripe event id)`, written in the same transaction as the rows, the outbox rows and the claim's done mark (a storage error rolls all of it back: 500, Stripe retries). The row holds the *trimmed fact* the rules decided on (the normalized event without its `source`, an invoice's number and bearer links, and with `metadata` cut to `b4u_school` and `family_id`), the fee and payment refs the fact does not hold, the SHA-256 of the verified raw body, the revisions before and after, `atm_version`, and the menu and policy in force (`atm_input_contexts`, one row per distinct content). Never the raw event: no name, email, address, card detail, receipt link or free-form metadata, and no `://` anywhere in the database (a test reads the file and its write-ahead log). A holder that already had rows gets them as a *seed* (`atm_input_seeds`) at its first stored input.
- **What is stored, and what is not.** Stored: every delivery the handler applies (including one that books only money, and `non_usd`), an `invoice_payment.paid`, and a 422 refusal as a `refused` row with its reason (a retry counts `attempts`; the delivery that is applied later replaces it and takes a new `applied_order`). Not stored: a 409 wait, another product's event, a type the Trifold engine does not map, a refusal before the claim, an event that does not normalize. `applied_order` is the order the handler applied the inputs in (the order of its 200 answers), which differs from Stripe's `created` order whenever the handler made Stripe wait.
- **Where.** The handler's own SQLite, created by `db.exec(HANDLER_DDL)` (every statement is `IF NOT EXISTS`; an existing database gets the new tables from it, nothing is rebuilt, `migrateHandlerSchema` has nothing to do for them). A handler on a database without them stops with an error that names `HANDLER_DDL`. Read them with `inputsStatus(db, { env?, school? })`, `readInputs(db, { env, school })` or `sqliteInputsSource(db)`. Shipping them off the disk is `tfd inputs ship` (next section).
- **Erasure.** When you book `subject.erased` for a holder, call `eraseStoredInputs(db, { env, school, subjectKey, nowMs })` in the same transaction (the Trifold engine books no `subject.erased` itself). Every stored input of the holder becomes a tombstone (`body`, `subject_key`, `payment_refs`, `booking_refs`, `fee` and `raw_sha256` cleared, `erased_at` set), its seed is deleted, and the shipped objects that held its facts are queued in `atm_input_erasures` for the shipper to rewrite. Other holders' inputs and the ledger's money events stay. It returns `{ inputs, seeds, queued }` and is idempotent.
- **A booking's events** are decided and stored by your own endpoint, because the reference handler never sees them. After its rows and `appendToOutbox`, in the same transaction, the endpoint calls the exported `recordInput(db, args)`; it answers `"stored"` or `"existing"`. The recipe is in `UPGRADING.md`, "Storing the inputs of a booking".

### Shipping the stored inputs (new in 0.10.0)

`tfd inputs ship` copies the stored inputs off the handler's disk to a folder (or, by the same library call, an R2 bucket), the way `tfd ship` copies the outbox. The design and its reasons are `docs/simulate-from-inputs.md`, "Shipping the inputs".

```bash
tfd inputs ship --db <handler.sqlite> --school <id> --env live|test --root <folder>            [--json]
tfd inputs ship --db <handler.sqlite> --school <id> --env live|test --r2-bucket <b> --r2-endpoint <url> [--r2-prefix <p>] [--json]
```

- **Run order.** `tfd inputs ship` before `tfd ship`, in the same schedule, so that every event in the log already has its input shipped (a decision with no shipped input is `not_replayable` for a what-if). Both are safe to rerun.
- **What ships.** Under `schools/<id>/inputs/<env>/` (never inside `events/`): `date=<UTC day of the commit>/batch-<first applied_order, 12 digits>-<16 hex>.jsonl` (one object per commit day, a line per input in `applied_order`, canonical JSON), `contexts/ctx-<context hash>.json` (the menu and policy in force) and `seeds/seed-<16 hex of the holder's hash>.json` (a holder's rows before its first stored input). Created create-only; the name comes from the content, so a rerun, a crash between put and mark, and two shippers put the same key with the same bytes. A key that already holds different bytes is a conflict: reported, never overwritten, its rows left unshipped. Only committed rows ship. A refused input is never shipped, not even erased. An erased input ships as a tombstone line (no fact, holder key, refs, fee or raw hash), never as a fact. The day is UTC, whatever the process time zone.
- **What it writes in the database.** Only `batch_key` and `shipped_at` on `atm_event_inputs`, `shipped_at` on the contexts and seeds, and the erasure queue. `batch_key` is written just before the put (with `shipped_at` still null), so that an erasure that comes between the put and the mark still finds the object.
- **Erasure.** After `eraseStoredInputs`, the next `tfd inputs ship` settles the queue first: each shipped batch that held the holder's facts is rewritten under a new key with the holder's lines as tombstones (create-only; nothing is ever overwritten), the rows are pointed at the new key, the old object is deleted, and the queue row is closed; the holder's seed object is deleted (also one whose put landed but whose mark did not). Until then the old object still holds the facts: the window is one ship run. The command exits 1 while a queue row is open (and prints `erasure pending`), so a schedule alerts. `inputsShipStatus` reports the count and the age. **Deployment precondition:** versioning, replication and backups must be off for the `inputs/` prefix (or purged as part of the erasure); a versioned bucket keeps the deleted object. On a folder, a process killed inside a put can leave a `.atm-tmp-*` file beside the key with the batch's bytes; the store never lists it and an erasure does not reach it, so remove stale ones (`find <root> -name '.atm-tmp-*' -mmin +60 -delete`). The SQLite file's own backups keep the facts until they expire.
- **Flags and environment.** `--root` must be an existing folder (a typo would otherwise ship into a new one); `--school` must have rows in `atm_event_inputs`. Give exactly one destination. The flags win; the non-secret R2 values also come from `TFD_R2_ENDPOINT`, `TFD_R2_BUCKET` and `TFD_R2_PREFIX` when `--root` is not given. **R2 credentials come from the environment only** (`TFD_R2_ACCESS_KEY_ID`, `TFD_R2_SECRET_ACCESS_KEY`, optional `TFD_R2_SESSION_TOKEN`). Each is also read by its old name (`ATM_R2_*`) when the `TFD_R2_*` one is not set (`src/environment.ts`); there is no flag for them, and a flag named like one is refused. **The R2 path has not been run against R2** (nor against SeaweedFS); `R2Store` takes the same `shipInputs` call and the contract suite has never run against staging R2.
- **Exit codes.** 0 done (also with nothing to ship), 1 a conflict (a `conflict <key>: ...` line on stderr) or an erasure still pending, 2 any other error (one line on stderr, no stack trace). `--json` prints one line: `{ok, school, env, batches, shipped, contexts, seeds, conflicts: [{key, message}], erasuresSettled, erasuresPending, unshipped, oldestUnshippedAgeMs}`.
- **Library.** `shipInputs({ db, store, school, env, nowMs })` for any `Store`, `settleInputErasures`, `inputsShipStatus`, the pure `planInputs` and `inputObjectKey`, and the readers `folderInputsSource(root)` and `storeInputsSource(store)`, which return the same `InputsRead` as `sqliteInputsSource` (a tombstone line beats a fact line for the same input; ordered by `applied_order`); `inputOrderGaps(read)` lists the missing orders (a refusal takes an order and is not shipped, so a gap is not always a loss).

### Receipts and seals (new in 0.10.0)

A family has no proof of a payment that survives an edit to the school's books, and a closed month can be changed without a trace. The Trifold engine now gives each paid or refunded payment a receipt signed with Ed25519 that the family keeps and anyone can check, and each closed month a signed seal chained to the one before it. A receipt is a pure function of its event and Ed25519 is deterministic, so nothing is stored: the books make the family's copy again byte for byte, and an edited or deleted event no longer makes it. No table, no worker, no change to the webhook transaction.

```bash
tfd keys new --out <dir> [--id <key_id>]                                              # <id>.private.pem (0600), <id>.public.pem; adds to keys.json
tfd receipt --root <folder> --school <id> --key <private.pem> --key-id <id> [--event <event_id>]   # JSON lines
tfd verify receipt <file|-> --keys <keys.json> [--root <folder> --school <id>]       # exit 0 valid, 1 not
tfd seal --root <folder> --school <id> --month <YYYY-MM> --key <private.pem> --key-id <id>         # appends to ledger/seals.jsonl, under a lock
tfd verify seals --root <folder> --school <id> --keys <keys.json>                    # exit 1 when a seal fails
```

```ts
import { receiptOf, signReceipt, verifyReceipt, checkReceiptAgainstEvents, sealOf, signSeal, verifySeals } from "atm";

const receipt = receiptOf(event); // null unless payment.succeeded or payment.refunded
const signed = signReceipt(receipt, { keyId: "trifold-2026-11", privateKeyPem }); // attach to the payment email
verifyReceipt(untrusted, keys); // { ok: true } or { ok: false, reason: "malformed" | "unknown_key" | "bad_signature" }
checkReceiptAgainstEvents(signed, events); // ... "missing_event" | "event_changed" | "not_receipted"
```

- **The receipt** (`AtmReceipt` v1, `schema/receipt.v1.json`): school, the family's timeline `key`, the event's id, type, time and date, `amount` in cents (`amount_paid` on a payment, `amount` on a refund), `currency`, `stripe_id` (the invoice id, or the refund's id), `cause` (a refund's payment) and `event_hash`, the sha256 of the event's canonical form. No name or email: a receipt may be shown to anyone. `receiptOf` throws naming a missing or wrongly typed payload field, and never guesses one. Disputes get no receipt.
- **Canonical v1 is frozen.** `event_hash` is `sha256(canonicalize(event))`, the same form `buildJournal`'s `inputsHash` uses, so a receipt can be checked from any copy of the events. A golden test (`tests/golden/receipt/`) pins the event's bytes and hash, the receipt's bytes and the signature; a change to `canonicalize` needs receipt v2, and v1 receipts must keep verifying.
- **Signing and checking.** `sig` is Ed25519 over `canonicalize(receipt)`, base64url without padding; `key_id` names the public key in `keys.json` (`{ key_id: SPKI PEM }`; keep old keys there so old receipts still verify). Any other key type throws: there is no fallback. `verifyReceipt` takes `unknown` (a family's file is untrusted) and never throws.
- **What a receipt proves**: the school's key signed these facts, the books held this exact event when it was made, and which Stripe object to look up. Not that Stripe moved the money (Stripe matching is a later milestone): say "signed receipt", not "verified by Stripe".
- **Seals** (`AtmSeal` v1, `schema/seal.v1.json`): the ids of the month's events in the folder when it was sealed (`event_ids`, sorted), their count, transactions and `events_hash` (the `inputsHash` formula), and `prev_seal_hash`, the sha256 of the previous signed seal's canonical form. Membership is by id, not by `ingest_time`: the handler stamps `ingest_time` before `tfd ship` puts the event in the folder, so an event stamped before a seal can reach the folder after it. `sealed_at` is passed in (the CLI uses its clock; the library reads none). `schools/<id>/ledger/seals.jsonl` holds one chain per school, one signed seal per line, append-only; `tfd seal` holds `seals.jsonl.lock` while it reads the last seal and appends, so two at once cannot fork the chain (the second exits 2; a lock left by a crash is removed by hand).
- **Late events.** An event that reaches the folder after its month was sealed (a late Stripe delivery, or an outbox row shipped after the seal) still lands in that month. The earlier seal keeps verifying (it names its events); `verifySeals` lists the event in `unsealedLate`, and sealing the month again covers it. `verifySeals` gives each seal `ok`, `malformed`, `bad_signature`, `unknown_key`, `broken_link` (a missing or reordered seal) or `events_changed` (an event it names was edited or deleted).
- **Limits of this milestone.** The open month is not sealed until it closes, and an event inserted into a sealed month later looks like a late event (it is listed in `unsealedLate`, not hidden). Closing that needs a per-event chain written at ingest. One platform key: if it leaks, receipts can be forged until it is rotated.

## Release

B4 Uni's family service depends on the Trifold engine (the package `tfd`; releases through 0.10.0 were `atm`) by a pinned release URL, not a vendored bundle: `"atm": "https://github.com/justbry/atm/releases/download/tfd-v<version>/tfd-<version>.tgz"` (the key `atm` keeps its `import … from "atm"` working; see `UPGRADING.md`) in its `packages/family-service/package.json`, with the tarball's sha512 in its `bun.lock`. The tarball holds `package/package.json`, `package/dist/index.js`, `package/dist/index.d.ts`, `package/dist/types.d.ts`, `package/dist/worker.js`, `package/dist/worker.d.ts`, `package/LICENSE.md`, `package/LICENSING.md`, `package/LICENSES/Apache-2.0.txt` and `package/README.md`, and nothing else (the engine is inlined, so no dependencies).

1. Bump `version` in `packages/atm/package.json` (the workspace package stays `"private": true`; it is never published to npm), commit and push.
2. `just release-dry` (`bun run --cwd packages/atm release --dry-run`) builds from that commit, runs the dist checks, packs, and prints the file list, sha256 and the sha512 integrity bun.lock will record. It prints, without stopping, what a real run would refuse on.
3. `just release` (`bun run --cwd packages/atm release`, after a confirmation) does the same and creates the GitHub release `tfd-v<version>` at HEAD with the tarball. It refuses unless the working tree is clean, HEAD is on origin, neither the tag nor a release for it exists, and the bun running it is the one the repo pins (`packageManager`), because the bundle and the pack are part of the bytes. The same commit on that bun gives the same tarball.
4. Pushing a tag `tfd-v*` runs `.github/workflows/release-atm.yml`, which builds the tag and creates the release if it is missing, or checks that an existing release's asset is exactly this build.
5. In buzz-school, change the URL in `packages/family-service/package.json` and run `bun install`; `bun.lock` gets the new sha512.

Local development: `bun link` here and `bun link tfd` in the family service. `bun install` there undoes the link. Never commit while linked.

## Ledger (slices 1-5)

- `tfd journal --root <folder> --school <id> --month YYYY-MM`: events under `<folder>/schools/<id>/events/` to `ledger/b4u/YYYY-MM.journal`, `ledger/accounts.journal`, `main.journal`, `ledger/build.json`; a file is rewritten only if its bytes change. `--json` prints one line instead of the sentence. An error is one line on stderr and exit 2.
- `tfd report --root <folder> --school <id> --month YYYY-MM [--report income-statement|balance-sheet|credits|all] [--format table|csv]`: builds that month's journal as `tfd journal` does, then prints hledger's `is`, `bs` and `bal credits: --flat` from the school's `main.journal` (the reports the golden-year tests check), to date over every month journaled so far. Needs `hledger` on `PATH`: without it, it says so and exits 2, writing nothing. See "Running it".
- `tfd ship --db <handler sqlite file> --root <folder> --school <id>`: the folder shipper. `--root` must be an existing folder and `--school` must have rows in the outbox, or it exits 2 and ships nothing (a typo in either would otherwise ship into a new folder, or ship nothing and exit 0). Moves the school's unshipped `ledger_outbox` rows (what the webhook handler decided) to `<folder>/schools/<id>/events/date=YYYY-MM-DD/batch-<first event id>-<16 hex>.jsonl`, one object per event date, then marks the rows (`batch_key`, `shipped_at`). The name comes from the content, so a rerun, a crash between put and mark, or a second shipper that read the same rows puts the same key with the same bytes (create-only; an equal object already there is success). If rows arrived for that day in between, the rerun puts a second, overlapping batch under another key (the reader drops the repeated events by `idem`). A key that holds different bytes, and a day that already has a `day.jsonl` (the reader keeps only `late-*` beside it, so a `batch-*` there would never be read), are reported and left alone, their rows unshipped (exit 1). With it the path works end to end on a plain folder: webhook handler, `ledger_outbox`, `tfd ship`, `tfd journal`. Library: `shipOutbox({ db, store, school, nowMs })` for any `Store` (call it after the handler, with the handler's `SqlDatabase`) and the pure `planOutbox`. **Not built**: R2 batches (the same call takes an `R2Store`, untested), the `day.jsonl` combine and `late-*` batches, the signed manifest, Parquet.
- Library: `mutationToEvents`, `ledgerEvent`, `lapsedRows`/`lapseEvent`/`lapseAlertEvents`, `validateEvent`, `replayEvents`, `simulate`, `buildJournal`. The folder and ledger helpers the CLI uses are public too (below).
- Replay: `replayEvents` runs each event's command through the engine at the event's time and requires the mutation it decides, and the events derived from it, to equal the recorded ones. It runs a subject's commands in revision order (`replayOrder`), not id order: a reset runs at the start of the period it refills, so its id can sort before the plan at payment time that came first. The log must hold every command the engine ran, once, with its whole mutation: `handleStripeEvent` records every event of a command with the whole mutation (`payload.slice` lists the positions in `mutation.changes` an event is made from, when one mutation is booked as several events by feature and plan), a command that moves no credits as a `plan.changed` with no postings, and `payload.complete: true` on all of them. A stored revision that moved without an engine command (a write of the grants row alone) is read from the next mutation's `revision.before` when the writer marked `complete`. `complete` is trusted, not checked: a forged marker, or an event deleted from the middle of a `complete` log, is not reported. `lastEventId` and `snapshot.lastEventId` are places in the replay order. **Logs written by 0.3.0** (no `slice`, no `complete`, no `plan.changed`; each event holds only its own part of the mutation) are read too: the mutation is reassembled from the events that share its `mutation.id`, the engine runs the recorded command, and the changes the log holds must be among the engine's. A command 0.3.0 never logged (the cycle-end update after a renewal) is not recoverable, and a revision gap cannot be told from a write of the grants row alone, so replay stops there with `ReplayGapError` (event, gap, and `prefix`: the replay up to it) rather than guess; a log with no gap replays, and the result's `lossySubjects` names the subjects whose last command may be missing. See `UPGRADING.md` ("Replaying a log").
- `schema/`: `envelope.v1.json`, `payload/<event_type>.v1.json`, `duckdb/envelope.v1.sql` (regenerate with `bun run schema`).
- `fixtures/`: a seeded year of one member (`bun run fixtures -- --seed 1 --out <dir>`); `fixtures/vibes-year` is seed 1.
- `fixtures/vibes-multi`: a second golden fixture, twelve families of one school over four months (November 2026 to February 2027, two tiers, written by the same `bun run fixtures`; `--only year|multi` writes one). It is there for what the one-family year cannot show: a year boundary and payments at the school's midnight (23:30 and 23:59:59 on a month's last day are the next month in UTC, and the journal keeps them in the school's), a dispute lost and one won, a partial refund, a fundraise received and paid out, a cancel, an erasure, `credit.low` and `credit.depleted`, and a payment that reached the log late (a `late-*.jsonl` batch under its day, dated in a month already journaled). Its `expected.json` is the generator's own ledger, never `buildJournal`'s output. `tests/hledger-multi.test.ts` runs hledger over it (goldens in `tests/golden/multi`, `UPDATE_GOLDEN=1` rewrites them), reconciles it against a Stripe side the generator decided, and builds 400 families by 12 months through the handler. Not covered: Stripe's dispute fee (the generator's disputes carry none; the handler books it, `tests/handler-disputes.test.ts`), a currency other than USD, more than one school.
- **A credit's commodity is its feature id in capitals, letters only** (`commodityOf`: `visit` is `VISIT`, `light-60` is `LIGHT`). So a feature id needs a letter, and its letters must differ from every other feature's in the menu: `light-60` and `light-90` would be one commodity and add up into one balance. Nor may they spell `USD`, the money commodity (`usd`, `u-s-d`, `usd-2`): the credits would add up with the dollars. `validateMenu` refuses such a menu (`problems` `features.<n>.id`, with a sentence naming both ids in `messages`) and `menuCatalogRows` throws. `commodityOf` itself does not change: renaming a commodity would rewrite the journals already built.
- The engine reads the process time zone for rollover expiry; ledger runs pin UTC around each engine call.

### Reconciling with Stripe

Stripe is the system of record for money. `reconcile({ events, stripe, period, timeZone?, mode? })` (pure, no Stripe call) and `tfd reconcile` compare a school's events with Stripe's records for one period and report every difference, so a nightly job can alert on a non-empty `differences` (the CLI exits 1).

- **Stripe's side** is the `data` of each `stripe <resource> list` for the school's connected account, as plain arrays: `invoices`, `refunds`, `disputes`, `payouts`, `balanceTransactions`, and `paymentIntents` for a school that takes paid bookings (the fields read are `StripeInvoiceRecord` and its siblings in `types.ts`; a whole Stripe object is fine). A list left out is `notSupplied` and its checks do not run. `paymentIntents` is different: a school whose log holds a booking's `payment.succeeded` must supply it (else it is `notSupplied`, exit 2), and any other school never needs it, so a school with no booking payments reconciles exactly as before. The Trifold engine's own webhook handler writes credit events and `plan.changed`, never `payment.*`, `dispute.closed` or `payout.paid` (the family service books those), so a log made by the handler alone reports every Stripe record as `missing_in_log`; and the handler's own refund fact carries the Stripe event id, not the refund's `re_`, so a caller that books a refund from it must put the `re_` in `payload.id`. Charges are not read: on API `2025-10-29.clover` a charge names neither its invoice nor an event, so nothing in the log can be matched to one.
- **Period**: `{ month: "2026-02" }` or `{ from, to }` (inclusive days), in the school's zone. An event is in the period by its own `date` (the one `buildJournal` uses); a Stripe record by its instant in the school's zone (`timeZone`, default the latest event's `tz`): an invoice's `status_transitions.paid_at` (else `created`), a refund's, dispute's and payout's `created`. A pair is compared when either side is in the period; an invoice, refund or dispute the two sides date either side of the boundary is `period_differs`.
- **What is compared**, matching by Stripe's id (the event's `payload.id`, else its `idem` without `stripe:`): paid invoices with `payment.succeeded` (`amount_paid`, currency, once); a booking's payment with the Stripe payment intent that carries its id (`pi_...`; `payment.succeeded` that names a `booking` is paired with `paymentIntents`, never with invoices: `amount`, currency, once; the kinds are the invoice's, as `object: "payment"`; the date only picks the period, as the intent is created when the customer pays and a delayed method books later, so there is no `period_differs` for it, and `counts.payment` appears only for a school that has one); refunds with `payment.refunded` (by the `re_...` id when the event has one; an event labelled with a Stripe event id (`evt_...`) that names a `payment_intent` or `charge`, as the handler's does, is paired with Stripe's refunds of that payment intent, else that charge, by amount: refunds of one payment are a multiset in time order, so two equal refunds pair one to one, a refund on one side only is `missing_in_log` or `missing_in_stripe`, and one whose amount changed is `amount_differs`. Equal refunds of one payment cannot be told apart, only counted. A Stripe refund record needs `charge` and `payment_intent`, which `stripe refunds list` prints, for this; a booking's refund is paired the same way, with no new input; an `evt_...` event with neither, from a handler before these fields, cannot be paired and is reported on both sides); disputes with `payment.disputed` (amount) and `dispute.closed` (won or lost against Stripe's `status`, else `outcome_differs`; an open dispute needs no closing event); payouts with `payout.paid`. Then two totals: the balance transactions' fees against the `expenses:billing:stripe-fees` postings (a total, since a fee cannot be tied to its invoice), and the net of Stripe's balance transactions against the `assets:stripe` postings, payouts apart (their own check). A `net` difference carries `stripeNetByType` to show where the gap is. The fees total counts both `expenses:billing:stripe-fees` and `expenses:billing:dispute-fees` (the handler books Stripe's dispute fee there); a log whose disputes were written without the fee shows it in the fees and the net.
- **Kinds**: `missing_in_log`, `missing_in_stripe`, `amount_differs`, `duplicate_in_log` (two events with one Stripe id), `outcome_differs`, `period_differs`, `not_in_log`. A log with no fee postings in the period (or no `payout.paid` at all) gets one `not_in_log` record for the class, not one per payment; the net is then compared before fees. Each record has the Stripe id, the event ids, both sides' amounts and dates, and the period.
- **Ignored, and counted in `ignored`**: Stripe objects whose `livemode` disagrees with `mode` (default `live`; refunds and balance transactions carry no `livemode`, so the key that listed them decides); invoices not `paid`, or paid for 0; refunds `failed`, `canceled` or `requires_action`; disputes still a `warning_*` inquiry or `prevented` (no money moved); payouts not `paid` (a payout the log paid and then reversed with `payout.failed` is left out of the log's side too, so a failed payout is no difference; one the log reversed and Stripe still calls `paid` is `missing_in_log`); payment intents with no `metadata.booking_id` (the ones that paid invoices) or not `succeeded` (`payment_intent_not_booking`, `payment_intent_not_succeeded`); balance transactions not in USD.

```bash
# One school's files. The Stripe CLI reference documents `stripe <resource> list`, --limit, --starting-after, --stripe-account
# and --live. `created[gte]` and `created[lte]` are the API's list filters, passed with -d (not run against Stripe here).
# The window starts a month early (an invoice's `created` is when it was made, and reconcile keeps only those paid in the period)
# and ends a day and a half late (here 2026-03-02T00:00Z): the end of the month in the school's zone is up to 12 hours after midnight UTC, and a
# window that stops at 23:59:59 UTC leaves out a Denver school's 17:00-23:59 on the last day, which reads as `missing_in_stripe`.
# Records the window brings in from outside the period are ignored, or `period_differs` where the log dates one inside it.
ACCOUNT=acct_...   # the school's connected account
for resource in invoices refunds disputes payouts balance_transactions payment_intents; do
  stripe "$resource" list --live --stripe-account "$ACCOUNT" --limit 100 \
    -d "created[gte]=1767225600" -d "created[lte]=1772409600" > "stripe/$resource.json"
done
# payment_intents.json is needed only by a school whose log holds a booking's payment (leave the line out for any other).
tfd reconcile --root <folder> --school <id> --month 2026-02 --stripe stripe   # --json for JSON; --from/--to for a range
```

`tfd reconcile` reads each `stripe/<resource>.json` as a bare array or as the list object the CLI prints. A page with `has_more: true` is refused (exit 2): past 100 records, page with `--starting-after <last id>` and join the `data` arrays (`jq -s '{object:"list", data: (map(.data) | add), has_more:false}'`). Not confirmed: that the CLI has no auto-pagination flag (none is in its reference). Exit 0 when nothing differs, 1 when something does, 2 with a one-line message for input it cannot use (a missing option, a bad month or zone, an unreadable file, an events file that is not JSON, a `--school` that is not one folder name). A folder that lacks any of the five files (or `payment_intents.json`, for a log that holds a booking's payment) also exits 2, after printing the result (with `notSupplied` in the JSON) and naming the files on stderr: those checks did not run, so exit 0 would read as "agrees" when part was never compared. `stripe <resource> list` prints an empty `data` for a resource with nothing in the window, so a complete fetch always has all five files (and the sixth when it is needed); the function `reconcile` still takes any subset. Amounts and times must be whole numbers (a record with `129.99` is bad input). The `stripe` flags above: `--live`, `-d`/`--data`, `--limit` (1 to 100) and `--starting-after` are in the CLI reference (the last two under `stripe get`); that `--stripe-account` and the resource names `balance_transactions`, `disputes`, `payouts`, `refunds` and `invoices` work on `list` was not confirmed against the reference (`stripe resources` lists them). `--mode test` reads test-mode objects instead; `--time-zone` is needed when the school has no events.

### What if (simulate)

`simulate({ events, catalog | menu (+ school), candidate: { catalog | menu, policy }, asOf?, month? })` and `tfd simulate` run the log's recorded commands again under a candidate menu (or catalog rows) and policy, and set the result against the log: balances per holder and feature, posting totals per month, account and commodity, the commands the candidate decides differently (which row changes differ), and the commands its engine refuses (a feature that is gone, a spend the smaller allowance cannot cover; the replay goes on from the state before it). It writes nothing and changes no input. A change that leaves the engine's reads alone (a price, a name) gives no difference.

```bash
tfd simulate --root <folder> --school <id> --current-menu menu.json --menu candidate-menu.json [--policy policy.json] [--month 2026-05] [--json]
```

- **Input.** The menu or catalog rows the log was written under (`--current-menu` or `--current-catalog`: the log does not store them), and a candidate: `--menu` or `--catalog` (rows as `menuCatalogRows` makes them), `--policy` (over the defaults, as `resolvePolicy` reads it; only `deductionOrder` is read, and it sets the draw order of every command that carries an `org`, which is every command that draws; a policy file that names other keys alone still sets the order to the default, `expiry`, over what the log's commands carried), or both. A candidate that is not valid (a menu that fails `validateMenu`, a policy `resolvePolicy` refuses) exits 2.
- **Exit codes.** 0 no difference, 1 differences (a CI check can gate a menu or policy change on it), 2 input it cannot use (one line on stderr, `{"ok":false,"error":...}` with `--json`; a log `replayEvents` refuses is one of these). `--json` prints one line without the candidate's events (the library result has them, to build the candidate's journal from).
- **What it can answer.** What the engine does with the same commands under another catalog or draw order: refills and rollovers (`reset`), which row a spend draws from, whether a spend is covered, the postings and balances that follow. The journals are compared as postings totals by account and month (`transactions` counts the transactions `buildJournal` makes for each side).
- **What it cannot.** (1) What Stripe charged: payments, refunds, payouts and disputes are carried over unchanged, and nothing in the USD totals moves. (2) The grant rules (`policy.upgradeGrant`, the rollover and gift amounts, the first grant of a plan, what an invoice grants): they are decided from Stripe invoices before the command is logged, and the command carries its amounts (an `applyBillingPlan` holds its balances), so a menu allowance reaches the refills, not the first grant. The log keeps the decisions, not the raw events: a what-if on the grant rules needs the raw Stripe events kept by the caller, replayed through `handleStripeEvent` with the candidate menu and policy. Not built. (3) `lowCreditThreshold`: alerts are made again at the threshold the log recorded. (4) The cron's expiries: an expiry the log booked is judged again on the candidate's row, and a row the candidate holds lapsed that the log's rows had not (a rollover the log's menu never made) is booked at its expiry, before the subject's next command and at `asOf`; a row both hold lapsed is left as the log has it (booked or not), so a log whose cron never ran stays as unbooked as it was. (4b) After a refused command the replay goes on from the state before it, so the subject's later commands run on a state the log never had; the refusals are listed, and everything after the first one of a subject is the candidate's own history, not the log's. (5) Entity-level states and a starting snapshot (as `replayEvents`).
- **For the golden fixtures** it is a regression gate and a reviewable diff: `tests/golden/simulate/` holds what a draw-order change, a smaller allowance and a larger allowance do to `fixtures/vibes-year` (rewrite with `UPDATE_GOLDEN=1`), and the same catalog and policy must give no difference on every log `replayEvents` accepts.

#### What if, from the stored inputs (`--inputs`)

`simulate` above re-runs the log's recorded commands, so it cannot answer a what-if on the grant rules: they are decided from Stripe invoices before a command is recorded. The reference handler now stores each input it handles (see "Stored inputs"), and `simulateFromInputs` / `tfd simulate --inputs` decide those inputs again through the same rules, with the menu and policy each one was handled under and then with a candidate, and set the two against the log. The 0.6.0 mode is unchanged.

```bash
tfd simulate --root <folder> --school <id> --inputs <handler.sqlite | shipped folder> --env live|test \
  [--menu candidate-menu.json] [--policy candidate-policy.json] [--effective-from 2026-03-01T00:00:00Z] \
  [--current-menu menu.json] [--current-policy policy.json] [--month 2026-05] [--allow-baseline-drift] [--json]
```

- **What it does.** (1) The baseline: every stored input is decided again, in the order the handler applied them (`applied_order`, not Stripe's `created`), at its own `created`, with the menu and policy it was decided under, and the holder's rows evolving from their seed. The result must equal the log, event by event (`idem` and body); if it does not, nothing after it can be trusted, so the command exits 2 and says which input differs, unless `--allow-baseline-drift`, which goes on and reports the drift without counting it. (2) The candidate: the same replay with the candidate menu and policy from `--effective-from` (default: the start). No `--menu` and no `--policy` is the identity: exit 0 if the baseline holds. A candidate `--policy` is the whole candidate policy over the defaults, not an overlay on the recorded one. A candidate menu finds the invoices' lines again by product and interval, so a changed price or allowance applies to the same purchases.
- **What it shows.** Per delivery: `same`, `changed`, `newly_refused` (the candidate's rules refuse an input that was applied), `newly_applied` (a stored 422 refusal the candidate accepts) or `no_longer_applied`, with the credit units granted and taken back per feature; the balance per holder and feature; the posting totals by month, account and commodity. The family service's own commands between the inputs (spends, holds) run again on the candidate's rows.
- **Exit codes.** 0 no difference, 1 a difference, 2 input it cannot use: one line on stderr (`{"ok":false,"error":...}` with `--json`), among them a missing `--env`, a database with no stored inputs for the school and env, a menu or policy that does not validate, a log that cannot be replayed, a baseline that does not reproduce the log, and a candidate that changes only `cancelCutoffHours`, `noShow` or `lateCancel` (the booking calls decide them and are not stored, so there is nothing to simulate; beside another change they are listed as `notSimulated`). `--json` prints one line: `ok, school, env, baseline, deliveries` (the changes only), `balanceChanges, postingChanges, transactions, notReplayable, replayed, refused, notSimulated, unaffected, differences, asOf, summary`. The command opens the database read-only and writes nothing.
- **What it cannot do.** What Stripe charged: payments, refunds, payouts and disputes come out as they were in USD (a candidate invoice the rules refuse still books its payment line, since Stripe collected the money; the line's income account moves from the tier's or add-on's to `income:billing:other`, because the refused invoice's lines are not on the candidate menu, and the USD total is unchanged). Events before the inputs were stored: the handler stores them from the first delivery after the upgrade, a holder that already had rows starts from a seed of them, and what was decided earlier is carried over unchanged and counted (`notReplayable`, with the first stored delivery named in the summary). Also carried and counted, by reason: `erased` (a holder whose inputs are tombstones), `context_missing` (the menu and policy an input was decided under are not in the source), `non_input_writes` (the holder's rows moved by a write that is neither a stored input nor a logged command), `booking_writes` (from a full refund or lost dispute that follows a credit hold: the booking records it reads are not reproduced; a holder with a hold and no such refund replays whole). A changed mapping (`schema/mapping/`) cannot be replayed from the stored facts. The cron's expiries are carried as recorded. An invoice refused before it was applied, or refused more than once, has booked its payment line under the menu of its first refusal, which is not kept: that line is carried as the log has it, in the baseline and in the candidate (`baseline.carriedPayments`). A holder the replay stops at (a refund or lost dispute after a credit hold) is listed under `notReplayable` also when that input decided nothing (`decisions: 0`). A price the candidate menu adds has no Stripe price id until it is published: give it as `candidate.priceIds` in the library (the CLI cannot).
- **From a library.** `simulateFromInputs({ events, inputs, env, school, candidate: { menu?, policy?, priceIds? }, effectiveFrom?, current?, month?, asOf?, allowBaselineDrift? })` takes `inputs` from any `InputsSource.read` (`sqliteInputsSource(db)`); it throws `InputsSimulateError` where the CLI exits 2. `replayInputs` is the replay it is made of. `tests/golden/simulate/inputs-*.json` hold the what-ifs (rewrite with `UPDATE_GOLDEN=1`); each has its numbers worked out by hand in `tests/simulate-inputs-whatif.test.ts`.

### Running it

What the family service runs, in order, and what an operator does. Paths are buzz-school's, read for this recipe (the Trifold engine changes nothing there). The release tarball holds the library only: `shipOutbox` and `outboxStatus` run inside the service; `tfd ship`, `tfd journal` and `tfd report` run from a checkout of this repository (`bun packages/atm/src/bin.ts <command>`). buzz-school (on `atm-v0.10.0` as of 2026-11-08) already has the outbox and a shipper for its own money events, so steps 2 and 3 are in place there; moving its grants onto the handler (pin, policy, the clover endpoint beside the old one, compare first) is `UPGRADING.md`, "Moving buzz-school's grants onto the handler (D12)".

1. **Handler.** `POST /hooks/stripe/school?school=<uuid>&v=clover` (`packages/family-service/src/routes/school-billing.ts`; the endpoint is made by `createCloverEndpoint`, and `v=clover` tells it from the school's older endpoint) finds that endpoint's sealed signing secret, then calls `handleStripeWebhook({ db, secret, schoolId, env, nowMs: Date.now, workerId, context }, { payload: rawBody, signatureHeader })` and answers `status` and `body` as they are (Stripe retries on 409, stops on 422 and 200: see `UPGRADING.md`). `db` is a `SqlDatabase` over the service's own handle; create `HANDLER_DDL`'s tables in the same SQLite file as the service (`DB_PATH`, `/data/family.db` on the Fly volume `family_data`, started by `packages/family-service/start.sh`), so the outbox is inside what Litestream replicates (`deploy/fly/family/litestream.yml`). `ledger_outbox` is already there (migration `0138`, a copy of `HANDLER_DDL`'s); its `IF NOT EXISTS` leaves it as it is.
2. **Outbox.** The handler writes the decided events to `ledger_outbox` in the same transaction as the credits. In buzz-school its own money events (`src/ledger-export/money.ts`, through `appendToOutbox`) go to the same table; for a school the handler serves, that booking stops, because the handler books the money itself.
3. **Ship on a schedule.** buzz-school already ships the outbox: `shipLedger` (`src/ledger-export/ship.ts`, every 10 minutes, behind the `ledger_export` switch, refusing a row of the other Stripe mode) calls `shipOutbox` for each school, and ships the handler's rows with the rest. A service with no shipper does it this way. The service has one job registry (`packages/family-service/src/jobs/`; `scheduleJob(jobs, { name, everyMs, firstAfterMs, run })`, run by the Bun driver on Fly and by Durable Object alarms later, which deliver at least once: `shipOutbox` is safe to run twice). Register one job that calls it for each school with outbox rows, every 5 minutes:

   ```ts
   const root = join(dirname(config.dbPath), "ledger"); // /data/ledger: a folder on the volume, created at boot
   scheduleJob(jobs, {
     name: "atm-ship",
     everyMs: 5 * 60_000,
     firstAfterMs: 30_000,
     run: async () => {
       const schools = sqlDatabase.all<{ school_id: string }>("SELECT DISTINCT school_id FROM ledger_outbox");
       for (const { school_id: school } of schools) {
         const { conflicts } = await shipOutbox({ db: sqlDatabase, store: new FolderStore({ root }), school, nowMs: Date.now });
         for (const conflict of conflicts) logMsg("error", "school_billing.ledger_ship_conflict", `${conflict.key}: ${conflict.message}`);
       }
     },
   });
   ```

   Where the service is not the host (a box with the database file and a checkout of this repository), cron does the same, and tells the three outcomes apart by exit code:

   ```sh
   */5 * * * * cd /opt/atm && out=$(bun packages/atm/src/bin.ts ship --db /data/family.db --root /data/ledger --school "$SCHOOL" --json 2>>/var/log/atm-ship.err); code=$?; echo "$out" >>/var/log/atm-ship.jsonl; [ "$code" -eq 0 ] || alert "tfd ship exit $code: $out"
   ```

4. **Alert on a conflict.** `tfd ship` exits 0 when done (also with nothing to ship, and on an outbox with no row yet), 1 when a batch conflicts, 2 on any other error (a bad `--root` or `--school`, an unreadable database, a missing option: one line on stderr, no stack trace). Each conflict is also a line `conflict <key>: <message>` on stderr. With `--json` stdout is one line: `{"ok":false,"school":"sch_x","batches":1,"shipped":1,"conflicts":[{"key":"schools/sch_x/events/date=2026-01-15/batch-...jsonl","message":"..."}],"unshipped":2,"oldestUnshippedDate":"2026-01-15","oldestUnshippedAgeMs":86400000}` (on exit 2 from a failed run: `{"ok":false,"error":"..."}`; a refused option exits 2 with commander's one stderr line and prints nothing on stdout). The family service has no pager: its alerts are `log("error", ...)` lines (`packages/family-service/src/log.ts`), and a monitor check goes beside `litestream_fresh` in `packages/scripts/ci-watchdog/prod-monitor.ts`.
5. **Health.** A conflict is loud; a shipper that stopped is silent. `outboxStatus({ db, school, nowMs: Date.now })` returns `total`, `shipped`, `unshipped`, `lastShippedAt`, `oldestUnshippedDate`, `oldestUnshippedId` and `oldestUnshippedAgeMs` and writes nothing. Alert when `unshipped > 0` and `oldestUnshippedAgeMs` is past three schedule periods (15 minutes for the job above) and still past it at the next check. The age counts from the event's own instant (the ULID in the row's id; the outbox keeps no insert time), so it is an upper bound: an event Stripe redelivers days late starts old. `tfd ship --json` carries the same `unshipped`, `oldestUnshippedDate` and `oldestUnshippedAgeMs` after its run.
6. **Monthly report.** After a month closes, on a machine that has bun, hledger and a checkout of this repository (the Fly image has no hledger), against a copy of the ledger folder: `bun packages/atm/src/bin.ts report --root <copy> --school <id> --month YYYY-MM` builds that month's journal and prints the income statement, the balance sheet and the credit balances (`--report income-statement|balance-sheet|credits` for one, `--format csv` for csv; with `all` the reports follow one another, so use one at a time to parse csv). `main.journal` includes every month journaled so far and the reports are to date over them: journal each earlier month once (`tfd journal ... --month <m>`) when starting. It builds only what it is asked to, so a month never built is not in the report. The folder's `ledger/` files are generated and rebuilt from `events/` by every run.

**Back up** two things. The SQLite file: Litestream replicates `DB_PATH` to R2 under `litestream/family` in `LITESTREAM_BUCKET` (it is off on staging while `LITESTREAM_SKIP=1`; `docs/runbooks/family-service.md` in buzz-school). And the ledger folder (`/data/ledger`): Litestream does not cover it, so copy it to a second place on a schedule, adding files and never overwriting (event files are create-only and named by their content). The outbox rows stay in SQLite after they ship, marked with `batch_key` and `shipped_at`: while they are kept, a lost folder can be rebuilt by clearing those two columns and running the shipper again (the events come back; a day that shipped in several batches comes back as one, under another key).

**On a conflict** a batch's key already holds bytes other than the batch's, or its day already has a `day.jsonl`. Nothing was written, its rows stay unshipped in SQLite, and no event is lost; shipping of the other days goes on. Never overwrite or delete the file to make the shipper pass. Look: the key names the file (`<root>/<key>`). A `batch-<first id>-<16 hex>.jsonl` name holds the first 16 hex digits of the sha256 of its bytes, so `sha256sum <file> | cut -c1-16` against the name says whether the file on disk is damaged or hand-edited (no match: restore it from the backup copy, and the next run finds an equal object and marks the rows), and `SELECT id, body FROM ledger_outbox WHERE school_id = ? AND date = ? AND shipped_at IS NULL ORDER BY id` shows the rows it was meant to hold. A file that matches its name while the rows differ means a stored row changed after insert, which nothing here does: stop and ask. For a `day.jsonl`, leave it: the combine that decides how a combined day takes later rows is not built (`ROADMAP.md`; detail in `docs/log-and-r2.md`).
