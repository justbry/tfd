# Upgrading the Trifold engine

The sections for past releases keep the name the engine had then, `atm`.

## On `dev` since 0.10.0

Changes merged to `dev` after the `atm-v0.10.0` tag. Nothing here is in a release yet.

- **The package is named `tfd`, and releases are `tfd-v<version>` with `tfd-<version>.tgz` (nothing to change until you move the pin).** The published `package.json` now says `"name": "tfd"` and `"license": "SEE LICENSE IN LICENSING.md"` (it said `Apache-2.0`, which was wrong: the bundle holds the FSL-1.1-ALv2 engine). The tarball carries `LICENSE.md` (FSL), `LICENSING.md` and `LICENSES/Apache-2.0.txt` in place of `LICENSE`. Releases stay on `justbry/atm`; old `atm-v*` releases stay where they are. When you move buzz-school to the first `tfd-v*` release (0.10.0 and earlier are `atm-v*`), either:
  1. **keep the key**: `"atm": "https://github.com/justbry/atm/releases/download/tfd-v<version>/tfd-<version>.tgz"`. Bun installs the tarball under the key, so `import … from "atm"` keeps working (checked under Bun and Node); or
  2. **rename it**: `"tfd": "…"`, and change every `from "atm"` to `from "tfd"` in the same commit.

- **The rename window opens: `tfd` beside `atm` for the environment variables, the ledger token's audience and the type names (additive: the `atm` names keep working for one minor release, then go).** Nothing stored changes: the names in `docs/frozen-identifiers.md` stay. What to do, in order:
  1. **The environment variables are `TFD_*`; the `ATM_*` names still work.** Every variable the package reads is read as `TFD_<name>` first and as `ATM_<name>` when that is not set (an empty value counts as not set), one variable at a time, so a deployment can rename them at its own pace and a mix works; when both are set, `TFD_*` wins. The operator's: `TFD_R2_ENDPOINT`, `TFD_R2_BUCKET`, `TFD_R2_PREFIX`, `TFD_R2_ACCESS_KEY_ID`, `TFD_R2_SECRET_ACCESS_KEY`, `TFD_R2_SESSION_TOKEN` (`tfd inputs ship`). This repository's tests and scripts: `TFD_DIST`, `TFD_WEED`, `TFD_GOLDEN_E2E`, `TFD_GOLDEN_E2E_SHARD`, `TFD_GOLDEN_E2E_TZ`, `TFD_GOLDEN_E2E_REPORT`, `TFD_KILL_OP`, `TFD_KILL_AT`, `TFD_KILL_PHASE`, and for the staging-R2 contract run `TFD_R2_ACCOUNT_ID` and `TFD_R2_API_TOKEN`. The help and the refusals name the new names: `tfd inputs ship` without credentials now says `set TFD_R2_ACCESS_KEY_ID and TFD_R2_SECRET_ACCESS_KEY (the ATM_R2_* names still work; there is no flag for them)`; a caller that matched the old text changes it. `R2_ENV` holds the `TFD_R2_*` names. The `ATM_*` names are read until the minor release after the next one.
  2. **The ledger token's audience moves to `tfd-ledger`; keep minting `atm-ledger` until the ledger Worker accepts both.** `tfd/worker` (`atm/worker` under the dependency key `atm`) exports `isLedgerTokenAudience(aud)`, `LEDGER_TOKEN_AUDIENCE` (`"tfd-ledger"`), `LEGACY_LEDGER_TOKEN_AUDIENCE` (`"atm-ledger"`) and `LEDGER_TOKEN_AUDIENCES`: exactly one of the two strings, anything else (an array included) refused. The ledger Worker (`packages/ledger-worker`, S8, `plans/ledger-ui/S8-contract.md`) still accepts `atm-ledger` only. Order: switch the Worker to `isLedgerTokenAudience` and deploy it; then buzz-school's `POST /school-admin/ledger-token` mints `aud: "tfd-ledger"`; once no `atm-ledger` token can still be live (they last 5 minutes), a later release drops `atm-ledger`.
  3. **Every `Atm*` type has a `Tfd*` name; the `Atm*` names are `@deprecated` aliases.** `TfdEvent`, `TfdSubject`, `TfdCommand`, `TfdResultFor<T>` and the rest, 42 in all (`src/types.ts`). An alias is the same type, so nothing breaks; an editor strikes the old names through. Types only: no runtime export changed. Move imports at your pace; the aliases go in a later release. The library's own signatures still say `Atm*` until the identifier rename (`plans/tfd-rename.md`, step 4).
  4. **Announced for the next release: the log and stderr prefixes will say `tfd`.** This release does not change them: they say `atm` whichever name the command was run as. In the next release, `atm: non_usd: …` and `atm: fee_unknown: …` (`deps.warn` of `handleStripeWebhook`) become `tfd: non_usd: …` and `tfd: fee_unknown: …`; `atm report: …` becomes `tfd report: …`; `atm <command> failed: …` becomes `tfd <command> failed: …`; `atm reconcile: …` becomes `tfd reconcile: …`; and `atm: cannot write to stdout: …` becomes `tfd: cannot write to stdout: …`. Change a log alert or a script that matches them to accept both (`(atm|tfd)`) before you upgrade to that release.

- **`policy.rulesVersion` (additive: absent means the rules you have).** A policy may now say `"rulesVersion": 2`: every rollover, one-time add-on and canceled membership's last credits then lapse on the menu's calendar (`menu.timeZone`: the same wall-clock time some months on, across a clock change) instead of the UTC calendar, so a Denver school's March rollover lapses an hour earlier in UTC than under rules version 1. The engine's `reset` carries the zone as `org.config.rollover_time_zone` (an opt-in change to `balance-engine`, listed in `UPSTREAM.md`). Absent and `1` are today's rules, byte for byte: `DEFAULT_POLICY` and `resolvePolicy(null)` carry no `rulesVersion`, every stored context replays as it was decided, and every golden is unchanged. Set it on a school before its first event, or at a context change (a new `policyVersion`); never edit a stored context to change it. `grantsStateFromCallerRows` takes an optional `policy` so an imported member's newest lot expects the rollover the next renewal will make. One residual: a wall time the clocks skip (02:00-02:59 on the spring-forward day) is read as just after the gap, where buzz-school's `addMonthsInZone` reads it as just before; 8 quarter-hours a year in a zone with DST.
- **`policy.giftSessionMonths` may be `null` (additive).** A session gift add-on then follows its grant's own rule, as a one-time add-on does: its rollover months, or never when the grant has none; a session gift code made under it stores `creditMonths: null` and its credits never lapse. A number keeps today's rule. A TypeScript caller that reads `giftSessionMonths` or `SessionGiftCode.creditMonths` as a number handles `null`.
- **The school's webhook endpoint comes from tfd (additive: new exports).** `STRIPE_WEBHOOK_API_VERSION` (`"2025-10-29.clover"`), `STRIPE_WEBHOOK_EVENTS` (the 10 types the handler takes, the list it checks against), `cloverEndpointUrl`, `createCloverEndpoint`, `retrieveWebhookEndpoint`, `checkCloverEndpoint`, `retireWebhookEndpoint` and `StripeEndpointError`, with the types `StripeAccountAccess`, `WebhookEndpointInfo`, `CreatedWebhookEndpoint`, `CreateCloverEndpointInput` and `CloverEndpointCheck`. A caller never names the clover version itself. How to use them is in "Moving buzz-school's grants onto the handler (D12)" below.

- **Admin adjustments go through `adjustCredits` (new; D12 T4).** `adjustCredits({ commandId, kind, featureId, credits, holder, menu, menuVersion, policy, policyVersion, rows, revision, catalog, now })` is the engine's form of buzz-school's admin adjust. `kind` is `goodwill` or `gift` (positive only) or `correction` (either sign). A positive one is a new credit row, `ce_adjust_<length>_<commandId>_<feature>`, that never refills and never expires (decision 7), labelled `adjust:<kind>` in its `external_id`; a negative one takes from the feature's live credits, soonest expiry first, and is refused `insufficient_credits` (buzz-school's 409) rather than go below zero. Write `rowChanges` and append `events` (one `credit.adjusted` with `reason: <kind>`) in one transaction. `commandId` is the idempotency key: the same id with the same fields is `replayed: true` with nothing to write, other fields are `idempotency_conflict`. It names the engine command `adjust:<commandId>:1`, so keep it unique in the school. The row shape is `src/billing/adjust.ts` (`adjustRowOp`), which the importer uses for a caller's `adjust:<kind>` lots.

- **Seed the handler's claims and indexes at import: `seedHandlerIndexes(db, { at, eventIds, invoices, env })` (new; D12 T6).** Run it in the import's transaction, after the rows. `eventIds` are the Stripe event ids your own billing already finished (not your `admin:*` ids): they are marked done in `atm_event_claims`, so a redelivery is a `duplicate`. `invoices` is every invoice paid before the import, `{ invoiceId, holder: { orgId, customerId }, paymentRefs: [pi_…, ch_…] }`: they go to `atm_invoice_index` and `atm_payment_index`, so a later refund or dispute of an old invoice is decided instead of waiting for ever (409 `unmatched_payment`). A second run writes nothing; an index row that already names another holder or invoice throws.

- **Compare-only: run the handler on a shadow database and diff it nightly with `diffBalances` (new; D12 T7).** The recipe, per school (plan §5 of `plans/credits-engine/plan.md`):
  1. **A separate SQLite file**, say `shadow.sqlite` beside the main database: `db.exec(HANDLER_DDL)` on it, its own connection and write lock. Never replicate it (keep it out of Litestream), never ship it: its `ledger_outbox` is never passed to `shipOutbox`, and no reader of member balances opens it. It can be deleted and rebuilt by importing again.
  2. **Import into it** (`grantsStateFromCallerRows`, one transaction per school), then `seedHandlerIndexes` in the same transaction.
  3. **Deliver every live event to it too**, from the school's second Stripe endpoint: `handleStripeWebhook` with `db` the shadow and no `paymentFee` (fees are money, which the shadow does not compare). Answer Stripe 200 for everything except the handler's 409 waits, so Stripe retries those; record each refusal or throw (ids and kinds only) for the alert. The answer of your live endpoint never depends on the shadow.
  4. **Nightly, at one `now`**: `diffBalances({ db: shadow, school, catalog, now, importedAt, members })`, where each member is `{ customerId, balances, lots }`: `balances` your own sum per feature of `balance` over unremoved lots with `expires_at` null or after `now`, and `lots` the member's lots (the evidence for the reasons below). It returns one difference per member and feature that is not equal (`delta` is tfd's minus yours), each with `reason`: `admin_adjust` (your `adjust:*` lots since the import, which the shadow never sees), `unrenewed_cycle` (tfd holds a refilling row past its reset: the cycle ended unpaid), `upgrade_grant` (tfd granted more for an invoice since the import than your lots of it), `rollover_cap` (tfd short by at most what its renewals expired), `expiry_dst` (a lot and tfd's row or rollover lapse within an hour, `now` between), `gift_expiry` (a one-time lot and tfd's row of the same invoice lapse apart, `now` between), or `unexplained`, which should alert. Store the rows (`shadow_diffs`); the shadow is ready for cutover after 14 nights of only excused rows that cover a renewal of every member.

### Moving buzz-school's grants onto the handler (D12)

Replaces the older recipes under "Moving to 0.6.0" and "Moving an existing caller onto `handleStripeEvent`", which were written when buzz-school was on `atm-v0.3.0` and had no outbox. The stages, the owner's decisions and buzz-school's side (B1-B20) are in `plans/credits-engine/plan.md` and `decisions.md`; this is what tfd gives and expects. As read on buzz-school `origin/main` (2026-11-08):

1. **Pin.** buzz-school is on `atm-v0.10.0` under the key `atm` (`packages/family-service/package.json`). Move it to `tfd-v0.11.0` and keep the key (first item of this section), so `import … from "atm"` keeps working.
2. **The outbox and the shipper already exist: don't add a second.** Migration `0138` created `ledger_outbox` as a copy of `HANDLER_DDL`'s (`test/ledger-outbox-migration.test.ts` compares the two), and `src/ledger-export/ship.ts` (`shipLedger`, a job every 10 minutes behind the `ledger_export` switch, with its env guard) ships it with `shipOutbox`. `HANDLER_DDL` creates the table `IF NOT EXISTS`, so in buzz-school it creates only the handler's own tables and the handler appends to the same `ledger_outbox`, which the same shipper ships. Two consequences: a later tfd change to the outbox's columns is skipped there, so it has to come as a buzz-school migration too (this file will say so when one comes); and for a school the handler serves, buzz-school's own money booking (`book`, `src/ledger-export/money.ts`) must stop, or a refund in flight at the switch can be booked twice (its `payment.refunded` idem differs between the two writers). Credit events are written always and shipped only where the export is on; in production, only once D-3 allows family-keyed credit events (decision 9). The `SqlDatabase` the handler gets must take the write lock at `BEGIN`; `src/ledger-export/sql.ts`'s `sqlOf` uses the port's savepoint transaction, which suits `appendToOutbox` inside a caller's transaction but not the handler, which opens its own.
3. **Policy.** For a buzz-school school pass `{ ...policy, rulesVersion: 2, giftSessionMonths: null }`: rollovers and one-time lots lapse on the school's calendar, and a one-time add-on or gift lapses after its grant's rollover months, or never (decisions 3 and 5). The rest needs no setting: tfd applies `rollover.max` at every renewal and grants an upgrade's credits when its invoice is paid (decisions 1 and 2). The one grandfathered cycle of decision 1 is buzz-school's side: the rows it imports are uncapped.
4. **Lapse (decision 4).** A job calls `recordLapse({ db, state, featureOf, feature, atMs, tz })` per feature for each member past its cycle end, inside the transaction that reads the member's rows (it opens none). `recordLapse` books `credit.expired` for every row and rollover whose `expires_at` is at or before `atMs`; it does not end a cycle. A tier row whose cycle ended unpaid has no `expires_at` (it waits for its next invoice), so it keeps its balance and `recordLapse` books nothing for it until the subscription is canceled (`customer.subscription.deleted` dates it) or paid. Lapsing an unpaid cycle as buzz-school's lots do (at the cycle's end plus the rollover months) needs a tfd command that does not exist yet: open question 7 in plan §13, before stage 4.
5. **The endpoint: two endpoints, then one** (plan §4). An endpoint's API version cannot be changed, so each school gets a second endpoint at clover on its own Stripe account, beside its acacia one:

   ```ts
   import { createCloverEndpoint, retrieveWebhookEndpoint, checkCloverEndpoint, retireWebhookEndpoint } from "atm";

   const access = { secretKey: schoolRestrictedKey, fetch }; // the school's key (Webhook Endpoints: write), never the platform's
   const created = await createCloverEndpoint({
     ...access,
     url: `https://<host>/hooks/stripe/school?school=${schoolId}`, // `&v=clover` is added
     metadata: { school: schoolId },
     idempotencyKey: `tfd:webhook-endpoint:${schoolId}:clover`,
   });
   // seal created.secret into school_billing.webhook_secret_clover_enc and keep created.id in clover_endpoint_id: Stripe shows the secret once
   const check = checkCloverEndpoint(await retrieveWebhookEndpoint({ ...access, id: created.id }));
   if (!check.ok) throw new Error(check.problems.join("; "));
   // ...later, after the cutover and three days of the old endpoint answering 400:
   await retireWebhookEndpoint({ ...access, id: oldEndpointId, action: "delete" }); // refuses an endpoint at clover
   ```

   The endpoint sends `STRIPE_WEBHOOK_EVENTS`: buzz-school's 6 plus `invoice_payment.paid`, `charge.dispute.created`, `payout.paid` and `payout.failed` (payouts need the key's payout permission). Both endpoints get the same `evt_` id for one event (plan §4, O3), so a claim seeded from buzz-school's finished event ids (`seedHandlerIndexes`, above) dedupes across them. The route tells them apart by `v=clover` and verifies each with its own secret. While both run, the endpoint not in use answers 400, so Stripe keeps retrying it for 3 days and a revert still has its events. Creating and deleting endpoints is a production action on the school's account, with buzz-school's prod-ops rules (B8: dry run by default, one school at a time).
6. **Compare first, on the clover endpoint (stage 3).** Briefly: a separate `shadow.sqlite` created with `HANDLER_DDL`, never replicated and never shipped; each member imported into it with `grantsStateFromCallerRows` (pass the policy above); the clover endpoint's deliveries handled by `handleStripeWebhook` against the shadow, answering 200 except tfd's 409 waits; and a nightly job comparing each member's balance per feature with the lots' sums, with the excused reasons as data. The design is plan §5; the full recipe, with `seedHandlerIndexes` and `diffBalances`, is the "Compare-only" item above (T7).
7. **Cut over per school (stage 4)**: the clover endpoint becomes the live one and buzz-school's own grants stop at the same moment (plan §7).

## Moving to 0.10.0 from 0.9.0

Everything merged to `dev` after the `atm-v0.9.0` tag is in 0.10.0. A caller that reads `views/months/YYYY-MM.json` must change (the first item); the rest is additive or says what to do.

- **`MonthView.money` is removed from `views/months/YYYY-MM.json` (a reader of it must change).** The month's money (collected, refunded, fees, net) is now `money` in `views/finance/months/YYYY-MM.json`, which `runViews` writes next to the other views (finance members are `views/finance/members/<hash>.json`, KPI contributions `views/kpi/contributions/YYYY-MM.json`). A reader that took `month.money` reads the finance month instead; a TypeScript caller sees the property gone from `MonthView`. Every month object, the manifest and a committed view snapshot change bytes, so regenerate the views and any hash pinned over them. Detail: `plans/ledger-ui/S8a-hash-changes.md`.
- **The tarball now has `atm/worker` (additive).** Earlier tarballs had no `./worker` export; a pinned install of 0.10.0 can `import … from "atm/worker"` (the Worker-safe read slice: `kpiDocument`, `runViews`, `incomeStatement`, `ledgerRows`, views, `R2BindingStore`). It needs the `nodejs_compat` flag in a Worker (README).
- **`catalogPublishedEvent` is also exported from the package root (additive).** It was in `atm/worker` only. A caller that already imports it from `atm/worker` needs no change.

- **The CLI is also `tfd` (additive: nothing to change).** The docs now call the product and the managed service Trifold and this package the Trifold engine, and the CLI `tfd`. `atm` is the same command and keeps working, so scripts and cron lines that call `atm` need no change. Nothing stored changed (the package and release names changed later; see the item above): the `ATM_*` environment variables, the handler's tables, the events, the log layout and the log prefixes are as they were. The names that must never change are listed in `docs/frozen-identifiers.md`.

- **Signed receipts and sealed months (additive: new exports and commands; nothing a caller does today changes).** No table, no change to the handler, the outbox or any event. New exports: `receiptOf`, `signReceipt`, `verifyReceipt`, `checkReceiptAgainstEvents`, `sealOf`, `signSeal`, `verifySeals`, and the types `AtmReceipt`, `AtmSignedReceipt`, `AtmSigner`, `AtmPublicKeys`, `ReceiptVerdict`, `LedgerVerdict`, `AtmSeal`, `AtmSignedSeal`, `SealOfInput`, `SealReport`; new schemas `schema/receipt.v1.json` and `schema/seal.v1.json`; new commands `tfd keys new`, `tfd receipt`, `tfd verify receipt`, `tfd seal`, `tfd verify seals` (README, "Receipts and seals"). To use them, in order:
  1. **Make one platform key** with `tfd keys new --out <dir>` (default id `trifold-YYYY-MM`). Keep `<id>.private.pem` in the secret store, never in the repository; publish `keys.json`. When you rotate, run `tfd keys new --out <dir> --id <new id>` into the same folder: it adds the new public key to `keys.json` beside the old ones, which old receipts and seals still need.
  2. **Sign a receipt when you write a `payment.succeeded` or `payment.refunded`**: `signReceipt(receiptOf(event), { keyId, privateKeyPem })`, and send the JSON to the family. `receiptOf` returns `null` for every other type and throws naming the field when a payment's payload lacks `amount_paid`/`amount`, `currency` or `id`. Signing is synchronous `node:crypto` and needs an Ed25519 key (any other type throws). Nothing has to be stored: `tfd receipt` makes the same bytes again from the books.
  3. **Seal each closed month**, oldest first, with `tfd seal --month <YYYY-MM>` (it appends to `schools/<id>/ledger/seals.jsonl`; never rewrite that file), and again when late events have arrived in a sealed month (`tfd verify seals` lists them in `unsealedLate`). A seal names its events by id (`event_ids`), so an event shipped after it is late, not tampering. Run `tfd seal` from one place: a second run while one holds `seals.jsonl.lock` exits 2. Run `tfd verify seals` from the same schedule and alert on exit 1.
  4. **Do not rewrite stored events from now on.** A receipt's `event_hash` and a seal's `events_hash` cover each event's whole canonical form, `payload` with `billing_email` included. An erasure (or any repair) that edits an event in place breaks every receipt and seal over it. Which way erasure goes is an open owner decision (`ROADMAP.md`, "Signed receipts and sealed months"); until it is taken, do not edit events.

- **The handler stores each input it handles (additive: four new tables).** What to do, in order:
  1. **Run `db.exec(HANDLER_DDL)` at start**, as before. It now also creates `atm_event_inputs`, `atm_input_contexts`, `atm_input_seeds` and `atm_input_erasures` (all `IF NOT EXISTS`, plain SQL: no trigger, no `STRICT`, no generated column). Nothing is rebuilt or copied, `migrateHandlerSchema` is unchanged and does not make them, and the order of the two calls does not matter. A handler that runs on a database without them stops with an error that names `HANDLER_DDL` before it touches anything (a 5xx, so Stripe retries until you fix it). Litestream: a table with `AUTOINCREMENT` makes SQLite keep `sqlite_sequence`; check that your restore keeps it.
  2. **Nothing else changes in what a delivery answers or writes** except that, in the same transaction, it writes the input. A caller that counts the tables, or asserts that a refusal writes nothing, sees a row in `atm_event_inputs` (a 422 refusal is stored as `refused`). Deliveries from before the upgrade are not stored and are not backfilled; a holder that already has rows gets a seed at its first stored input.
  3. **The family service's booking endpoint stores a booking's events itself** (the reference handler ignores `checkout.session.*`, and a booking charge's refund waits 409 there). Storing the inputs of a booking:
     - Do it in the same write-serialized transaction (`BEGIN IMMEDIATE`, as `bunSqlite` does) that you already need: load the holder's rows and revision; call `handleStripeEvent` with `eventId: inputCauseId({ school, eventId: event.id, stripeCreated: event.created })`, your `bookingIds` and the fee you read from Stripe; write the rows (revision-checked); `appendToOutbox`; write your own booking tables; then call `recordInput(db, { env, schoolId, event: { id, type, created, apiVersion, livemode }, rawBody, normalized: normalizeStripeEvent(event, inputId), outcome: "applied", reason: null, subjectKey, revisionBefore, revisionAfter: result.rowChanges?.nextRevision ?? revisionBefore, rowsBefore, context, fee, paymentRefs: null, inputId, bookingRefs, nowMs })`. A throw rolls all of it back; Stripe retries. `inputCauseId` and `normalizeStripeEvent` are exported for this.
     - `rawBody` is the verified request body: it is hashed, never stored. `context` is the `{ menu, menuVersion, policy, policyVersion, catalog, priceIds }` you decided with (a booking's money lines now read `policy.revenueShare` through the share rule). `bookingRefs` is the entries of your booking index (payment intent or charge id to booking id) that you passed in `bookingIds` for this fact's payment intent and charge, or `null` when none (a refund the charge's own `metadata.booking_id` names needs none).
     - Call it for every session or booking refund that has a holder and that you handled, including a session that decides nothing (subscription mode, unpaid): outcome `applied`, and for a 422-type refusal (`missing_metadata`, `bad_event`, `rejected`) `outcome: "refused"` with its `reason` and `revisionAfter` equal to `revisionBefore`. Not for a wait you answer 409 (`unmatched_booking`, `unmatched_invoice`).
     - Route a booking refund to your code before the reference handler, so that one event is not decided twice. `recordInput` answers `"existing"` and writes nothing when the event is already stored as applied; the rows and the outbox are still yours to guard (the outbox drops a repeated `idem`).
  4. **Erasure.** When you book `subject.erased` for a holder, call `eraseStoredInputs(db, { env, school, subjectKey, nowMs })` in the same transaction. It tombstones the holder's stored inputs (including `booking_refs`), deletes its seed and queues the shipped objects that held its facts in `atm_input_erasures` (and the holder's seed object, shipped or not); `tfd inputs ship` (next item) settles that queue. The ledger's money events and other holders' inputs stay. Backups of the database file keep the facts until they expire.

- **`tfd inputs ship` copies the stored inputs to a folder or R2 (new command; nothing changes for a caller that does not run it).** Operator checklist, in order:
  1. **Schedule it before `tfd ship`**, with the same cadence (an hourly run is enough; a run makes one object per commit day that has new inputs, and more after a crash): `tfd inputs ship --db <handler.sqlite> --school <id> --env live --root <folder> --json`, then `tfd ship ...`. Alert on exit 1 (a conflict, or an erasure still pending) and 2.
  2. **If it ships to a bucket, turn versioning and replication off for the `inputs/` prefix** (or purge the old versions as part of every erasure). An erasure rewrites a batch and deletes the old object; a versioned bucket keeps the deleted one, with the holder's facts. This is a precondition of the erasure promise, not something the Trifold engine can check.
  3. **After `eraseStoredInputs`, run `tfd inputs ship`** (the Trifold engine books no `subject.erased` itself). It rewrites the shipped batches that held the holder's facts under new keys, deletes the old objects and the holder's shipped seed, and exits 1 until the queue is empty. Watch `inputsShipStatus(...).erasuresPending`.
  4. **R2 credentials only in the environment** (`ATM_R2_ACCESS_KEY_ID`, `ATM_R2_SECRET_ACCESS_KEY`, optional `ATM_R2_SESSION_TOKEN`); the bucket, endpoint and prefix may be flags or `ATM_R2_BUCKET`, `ATM_R2_ENDPOINT`, `ATM_R2_PREFIX`. The R2 path is untested against R2.
  5. **A service that holds an `R2Store` calls `shipInputs({ db, store, school, env, nowMs })` itself**, as it calls `shipOutbox`. The objects are under `schools/<id>/inputs/<env>/`, never inside `events/`, so `tfd journal`, `tfd report` and every reader of the log are unaffected. Existing databases need no migration beyond the tables of the stored-inputs item above.

- **A paid invoice the handler refuses is now booked as a payment.** Not additive for a caller that asserts "a refusal writes nothing" or that reads the outbox after a 422. Before, an `invoice.paid` refused with `unmatched_line`, `tier_on_other_subscription`, `addon_only_subscription` or `rejected` wrote nothing, so the books lacked a payment Stripe had already collected until the cause was fixed and the event sent again (the matrix finding D4). What a caller sees:
  - **The reference handler (`handleStripeWebhook`).** The answer is the same: 422 `refused` with the same `reason`, the claim released, the invoice not indexed, no row written, no credit granted, Stripe retrying. What is new is one event in the outbox, written in the transaction that releases the claim: the invoice's `payment.succeeded` (idem `stripe:<invoice id>`, with the fee `deps.paymentFee` gave; the income account is the tier's or the add-on's by the menu's reading of the lines, `other` for a line the menu does not know), or the `money.skipped` marker for an invoice that is not in USD. The `message` of the 422 gains a sentence that says the payment is booked (a test that compared it exactly needs `toContain`).
  - **The retry.** Stripe's next retry of the refused event, and the delivery that applies after the cause is fixed, make the same event under the same idem, and the outbox keeps the first, so the income is booked once. The first delivery's fee and income account stay, as for any invoice. The retry that applies is answered 200 `applied` (or `non_usd`) as before and grants the credits.
  - **Still unbooked, as before:** everything refused before the claim (`bad_signature`, `bad_request`, `livemode_mismatch`, `school_mismatch`, half a holder, another product's invoice), and after it `unknown_school`, `unknown_mapping`, `missing_metadata` and every `bad_event` (the amount, the holder or the fee cannot be trusted). The table is in `docs/financial-reports.md`, "A paid invoice the handler refuses".
  - **A refund, a dispute or an `invoice_payment.paid` of such an invoice still waits** (409 `unmatched_payment` / `unmatched_invoice`) until the invoice is applied, because the credits to take back do not exist before that. `tfd reconcile` therefore shows a `missing_in_log refund` for it and no longer the invoice and the fee. For an invoice that stays refused for good (a second subscription for a member whose first ended, or `tier_on_other_subscription` when the member is refunded instead of the cause fixed) the income stays booked and the refund has to be entered by hand.
  - **A caller with its own handler** gets `refused.payment` from `handleStripeEvent` (`StripeEventRefusal` gains an optional `payment: AtmEvent[]`, set for those four reasons on an `invoice.paid` only; `events` stays empty and `rowChanges` null). To have the books right, append those events with `appendToOutbox` in the transaction that releases the claim. A caller that ignores the field is exactly as before. The message of `addon_only_subscription` and `tier_on_other_subscription` no longer says "nothing was granted or recorded" (it is "no credits were granted and the invoice is not recorded as decided").
- **A payout that fails is now reversed in the books (a new Stripe event to subscribe to).** Unreleased. What to do:
  1. **Subscribe the endpoint to `payout.failed`**, as well as `payout.paid`. Without it a payout that fails stays in `assets:clearing:stripe-payouts` as if it had reached the bank. Until the endpoint is subscribed, and for a payout that failed before this change, enter the reversal by hand (clearing down, `assets:stripe` up, by the payout's amount) or re-send the `payout.failed` event from the dashboard once the endpoint is on this version.
  2. **What it books.** A `payout.failed` makes one event, a `payout.paid` with its sides swapped (`assets:stripe` up, `assets:clearing:stripe-payouts` down by the payout's amount, payload `failed: true`, idem `stripe:<payout id>:failed`, dated by the failure). No new event type, no new outcome and no change to the envelope. Fees and income do not move. A payout Stripe pays out again is a new `po_` id and books as any payout.
  3. **It waits for the payout.** A `payout.failed` whose `payout.paid` is not booked yet is answered 409 `unmatched_payment` with no claim, and Stripe retries it; the retry after the `payout.paid` is booked reverses it. A payout that failed without ever being `paid` is answered 409 until Stripe stops retrying (up to three days) and books nothing, which is right: the Trifold engine never moved it out of `assets:stripe`. A non-USD payout is answered `non_usd` as before (no new marker: the payout already has one).
  4. **Readers built before this change** still read the log: the reversal is a valid `payout.paid` (the payload schema only gains an optional `failed`), so `atm journal`, `atm report` and hledger show the right balances. What they get wrong is anything that counts `payout.paid` events as payouts: an older `reconcile` reports `duplicate_in_log` and `missing_in_stripe` for a payout that failed. Upgrade `reconcile` before subscribing to `payout.failed`. A reader of your own that counts or sums `payout.paid` events must skip those whose payload has `failed: true`.
  5. **`reconcile`** leaves a payout the log paid and reversed out of its payout comparison (Stripe lists it as failed, which is not compared), in the month of the payment and the month of the failure, and counts it in neither side. A payout the log reversed that Stripe still calls `paid` is `missing_in_log`.
  6. **Shapes.** A `payout.failed` mapping (the same `StripePayout` fact as `payout.paid`), `AtmLedgerEventInput.failed`, `payoutFailed` in `src/scenario/stripe-events.ts` and a synthetic `payout.failed.json` fixture. A test that expected `payout.failed` to be answered `ignored` now sees `applied` or 409.
- **A payment booked without its Stripe fee is now said out loud (the books are unchanged; two things can notice).** E2e finding D1. Without `deps.paymentFee`, or when it answers `null`, the handler still books the payment gross with `fee_known: false` and still does not book a fee learnt later; nothing about that changed. What changed:
  1. **The answer and a warning.** `200 applied` gains an optional `body.feeUnknown: string[]` (`["in_1 26000 cents"]`), present only when the books hold a payment of the delivery without its fee, and `deps.warn` (default stderr) gets one line per such delivery. A caller that asserts the exact body of an `applied` answer or that fails on any stderr line, with no `paymentFee`, sees the new key and line; with a fee neither appears. The fix for the line is to wire `paymentFee` (read the charge's balance transaction before calling the handler, and answer 5xx when that read fails, so Stripe retries).
  2. **A re-send now says whether it could have booked a fee.** An applied invoice sent again under another event id decides nothing (it did not before either); it now also lists the payment the outbox holds without a fee, with `fee <cents> known now, not booked` when this delivery's `paymentFee` knew one.
  3. **`ReconcileResult` gains `feeUnknown: number`** (always present, 0 when none; a caller that compares the whole result with `toEqual` adds it), `formatReconcile` prints `no fee booked: N payment(s) ...` only when N > 0, and a `fees` difference message can end with `; N payment(s) in the log have fee_known false: ...`. **`ReportRun` gains `feeUnknown: { inMonth, total }`** and `tfd report` prints a second stderr note (`feeUnknownNote`) when `total` is above 0; stdout is unchanged.
  4. **No event, payload, posting or schema changed**, so no log, golden, journal or report changes and no reader needs upgrading. Booking a late fee (`payment.fee_adjusted`) would need a new event type and is a proposal for the owner in `docs/e2e-reconciliation.md` (D1), not built.
- **`tfd simulate --inputs`: a what-if on the grant rules, from the stored inputs (additive).** `simulateFromInputs` / `replayInputs` (library) and `tfd simulate --root <folder> --school <id> --inputs <handler.sqlite> --env live|test [--menu] [--policy] [--effective-from] [--current-menu] [--current-policy] [--month] [--allow-baseline-drift] [--json]`. Nothing to change in the handler or the family service: the mode reads what the handler stores. Without `--inputs`, `tfd simulate` is the 0.6.0 command, unchanged. What a caller needs to know: (1) it reads the log from `--root` (the shipped events) and the inputs from the handler's database, so both must be of the same env: the log has no env, serve each env from its own database and folder; (2) the replay of the stored inputs must equal the log, or the command exits 2 (`--allow-baseline-drift` reports the drift instead); (3) history from before the inputs were stored, an erased holder, a holder whose rows moved by a write nothing records, and the history of a holder from a refund or lost dispute that follows a credit hold are carried over unchanged and counted under `notReplayable`; (4) a candidate that changes only `cancelCutoffHours`, `noShow` or `lateCancel` exits 2, the booking calls decide them; (5) the command opens the database read-only. `--inputs` takes the handler's database or a folder `tfd inputs ship` filled (no refused rows there, so no `newly_applied`). The family service's booking endpoint should keep passing the full `context` to `recordInput`: a replay of a booking reads the menu's time zone and `policy.revenueShare` from it. Types: `InputsSimulateInput`, `InputsSimulation`, `InputsDeliveryChange`, `DecisionSummary`, `InputsBaselineMismatch`, `NotReplayable`, `ReplayInputsOptions`, `ReplayInputsResult`; error `InputsSimulateError`.

## Moving to 0.9.0 from 0.8.0

A minor release (the number 0.7.0 stays unused: it is held by the stored-inputs design, #65, whose first step, #85, changes no behaviour). It adds B4 Uni's revenue share to the ledger and makes a paid booking's payment a money line. Nothing is removed. A school with no `revenueShare` in its policy makes no share event, and its invoice output is byte for byte what 0.8.0 made (tested against the 0.8.0 commit); a paid booking is the one place where events change for every school.

- **B4 Uni's revenue share is booked in the school's ledger (opt-in per school).** Additive for a school with no rate; a log reader built before this cannot read a log that holds the new events.
  - **To use it, set `revenueShare` in the school's policy.** `BillingPolicy` gains `revenueShare: { percent: number } | null`: `catalog/policy.json` takes `"revenueShare": { "percent": 2.5 }` (0 to 100, at most two decimals; `resolvePolicy` refuses a third decimal, a negative or a value over 100; the policy schema bounds the rate to 0..100 and no longer carries a `multipleOf`, which a plain Ajv got wrong for rates such as 0.07), and `DEFAULT_POLICY.revenueShare` is `null`. A policy stored without the field means no share; code that builds a whole `BillingPolicy` literal must add `revenueShare: null` (a type error tells you). Pass the rate in `StripeEventInput.policy` (and the booking commands' `policy`) as for any policy field; each payment is accrued under the rate in force when it is booked. Pass the policy through `resolvePolicy`: a hand-built policy with an invalid rate makes no share (it never blocks credits or payment lines).
  - **`handleStripeEvent` returns more events for a school with a rate:** a `share.accrued` after each `payment.succeeded` (invoice or paid booking, on the amount collected before Stripe's fee, when the share is at least one cent) and a `share.reversed` after each `payment.refunded` of a payment that accrued one. Append them to the outbox with the rest, as for the money lines. `validateEvent` now refuses a share event whose payload amount differs from its `liabilities:b4uni` posting. A school with no rate (or 0) gets exactly the events and rows it got before. A payment booked before the school had a rate accrues nothing and its refund reverses nothing.
  - **The grants state gains two optional fields:** `InvoiceRecord.share` and `BookingRecord.payment.share` (`{ accrued, reversed }`), written only for a payment that accrued a share. A refund of such a payment is now a write of the grants row where a partial refund of an invoice wrote none before (the revision moves; the caller's guarded write handles it as for any row change).
  - **New event types make an older log reader reject the log.** `share.accrued`, `share.reversed` and `share.settled` join the ledger's closed list (the envelope's `event_type` enum, each with a payload schema), so a reader built before this release (`validateEvent`, DuckDB over the envelope) rejects a log that holds one, as with `money.skipped`. Upgrade readers first, then set a rate.
  - **Invoicing:** `shareStatement({ events, school, month, tz? })` (or `atm share --root <folder> --school <id> --month YYYY-MM [--json]`) is the month's statement for B4 Uni to invoice from: rows per payment, totals, and the balance owed. **Recording the payment:** append a `share.settled` event (`ledgerEvent({ type: "share.settled", school, tz, eventTime, key, idem, amount, payload: { amount, month?, reference? } })`, `amount` in whole cents, a stable `idem` such as the bank reference) when the school pays; it moves `liabilities:b4uni` against `assets:clearing:b4uni-payments`. `atm journal` and hledger book all three; `reconcile` ignores them. Detail: `docs/financial-reports.md`, "Revenue share".
- **A paid booking's payment and its refund now make money lines.** Not additive for a caller that counts events per delivery, or that tested `result.events` of a booking outcome for empty.
  - **`handleStripeEvent` of a paid booking (`checkout.session.completed` or `async_payment_succeeded`) now returns a `payment.succeeded`** in `events` (gross the session's `amount_total`, income `income:billing:booking`, idem `stripe:<payment intent id>`), and a refund of a booking's charge returns a `payment.refunded`, where both returned `events: []` before (a `money.skipped` of kind `booking` or `refund` for a non-USD booking). Append them to the outbox with the rows, as for an invoice. Pass `StripeEventInput.fee` (the charge's fee) for a booking's `checkout.session.completed` to book the fee, as for an `invoice.paid`; without it the payment books the gross. A booking's refund line is each event's own amount (`amount_refunded` less `previous_attributes.amount_refunded`), and an event that arrives after a larger total also makes its line (with no row change), so a redelivery repeats a line with the same idem. A refund books only a payment the books took: a booking paid before this upgrade, or in another currency, has no `BookingRecord.payment.booked` and its refund books no `payment.refunded`.
  - **`reconcile` needs one more listing for a school that takes paid bookings:** `stripe payment_intents list` (the `data`, as `payment_intents.json` beside the others; `--live`, `--stripe-account`, and `created[gte]`/`created[lte]` as for the other lists). A log that holds a booking's `payment.succeeded` and no payment intents is `notSupplied: ["paymentIntents"]` (`atm reconcile` exits 2). A school with no booking payment needs nothing new. `ReconcileStripe` gains an optional `paymentIntents`, `ReconcileObject` gains `"payment"`, and `counts` has a `payment` entry only for a school that has one.
  - **New schema fields, additive:** `payment.succeeded` payload gains optional `booking`, `session`, `payment_intent`; `payment.refunded` gains optional `booking`; `money.skipped`'s `kind` enum gains `"booking"` (a reader built before this rejects a log that holds one, as with `money.skipped` itself). Detail: `docs/financial-reports.md`, "The money lines".

- **A non-USD dispute is answered `non_usd` too.** Not additive for a caller that tests the outcome. It extends the 0.8.0 `non_usd` outcome (an `invoice.paid`, `charge.refunded` or `payout.paid` in another currency; see "Moving to 0.8.0 from 0.6.0" below) to disputes, which the handler has booked since #66 (0.8.0). What a caller sees:
  - **A `charge.dispute.created` or `.closed` in a currency other than USD that moved money** (its `balance_transactions` is not empty) used to be answered 200 `applied` with nothing in the outbox. It is now answered 200 `non_usd`, with `body.skipped` naming `dispute <du_...> <amount> <currency>`, the claim's `outcome` `non_usd`, and `deps.warn` called. Still no `payment.disputed` or `dispute.closed`; the credits are as before (a lost dispute takes its credits back in any currency).
  - **`money.skipped` gains `kind: "dispute"`** (the payload schema's enum is closed, so a reader built before it rejects such a payload). One marker per dispute: idem `stripe:<dispute id>:non_usd`, so the created event, the closed event and a re-send under another event id leave one. Each of those deliveries is still answered `non_usd` and warns, and `reconcile`'s `result.skipped` counts the dispute once.
  - **An inquiry (empty `balance_transactions`) is still `applied`, with no marker**: no money moved. If it becomes a chargeback, the closing event is marked. Detail: `docs/financial-reports.md`, "Non-USD".

## Moving to 0.8.0 from 0.6.0

A minor release (released; tag `atm-v0.8.0`). There is no 0.7.0: the number was skipped, and the design of simulating from stored inputs (#65) is planned for the next release (number not yet chosen). Two kinds of change: what was fixed on `dev` after 0.6.0 (first block; some of it is not additive), and what 0.8.0 adds for the family service: credits that are held and spent by bookings, a price for a booking or an event, and three kinds of code (second block). Nothing is removed. A 0.6.0 caller that changes nothing and calls none of the new functions gets the same rows, keys, events and answers, except for the items in the first block.

### Changes since 0.6.0 that are not about bookings (read these first)

- **The handler's tables carry `env` in their keys: call `migrateHandlerSchema(db)` once at start.** `atm_event_claims`, `atm_invoice_index`, `atm_payment_index` and `ledger_outbox` gain an `env` column (`'live'` or `'test'`, default `'live'`) and keys that start from it (`(env, event_id)`, `(env, invoice_id)`, `(env, payment_ref)`, and `(school_id, env, id)` with `UNIQUE (school_id, env, idem)` for the outbox), so one Stripe id delivered under both envs of one database is claimed, indexed and booked once in each (it was claimed once, and the test delivery answered `duplicate`). `HANDLER_DDL` makes the new shape on a fresh database but leaves an old table alone (`IF NOT EXISTS`), and SQLite cannot change a primary key, so a database made by 0.6.0 or earlier is rebuilt by `migrateHandlerSchema(db)`: one transaction, every row copied and counted, an error rolls everything back, a no-op on a current database (call it at every start, with `HANDLER_DDL`). **Take a copy or a Litestream snapshot first, and run it while the handler is stopped** (the outbox is copied row by row). Until it has run, `handleStripeWebhook` throws, writing nothing, with a message that names it. Existing rows read as `live`, except an invoice or payment index row of a test subject (read from its subject key), so an existing test endpoint keeps finding its invoices. A claim or an outbox row of a test endpoint made before the migration reads as `live`: a test event delivered again afterwards is claimed again, decided as a replay and its outbox rows inserted a second time under `test`, which the log's reader drops by `idem`. `appendToOutbox` (internal) takes the env; `recordEngineCommand` and `recordLapse` use the command's `identity.env` (`"live"` or `"test"`, anything else throws). A caller that inserts into these tables itself (the adoption recipe's `atm_payment_index` and `atm_invoice_index` rows for payments made before the import) now passes `env` for a test endpoint; leaving it out is a live row. A caller that selects `*` from these tables sees the new column. The event id atm derives and every `idem` are unchanged.
- **A tier line of another subscription than the member's own is now refused, 422 `tier_on_other_subscription`.** A paid `subscription_cycle` or `subscription_update` invoice that has a tier line, on a subscription that is not the member's tier subscription (the one their first tier invoice named), used to be applied to the member: a renewal of a second subscription refilled the member's rows at that subscription's tier and quantity, and a plan change on it moved the member's tier and granted the difference. It is now refused with nothing written, the claim released and the invoice not indexed, so Stripe retries it and the dashboard shows it; the cause is on the Stripe side (cancel the other subscription, and refund the invoice if the member should not keep it), and re-sending gives the same refusal. A holder with no subscription yet still takes the first tier invoice it is sent, a manual invoice (no subscription) is unchanged, and a second subscription's create invoice is still answered by the engine's own state check (`rejected`). A caller that routes on `reason` has one more 422 code to expect; `StripeEventRefusal["reason"]` gains the member.
- **A feature id whose letters spell `USD` is now refused.** `usd`, `u-s-d`, `usd-2` and the like become the credit commodity `USD`, which is also the money commodity: the credits would add up with the dollars in one hledger balance (and a credit has no decimal places, where dollars have two). `validateMenu` returns `problems: ["features.<n>.id"]` with a sentence naming the id, and `menuCatalogRows` throws the same sentence (capitals too: it does not run the schema). Before upgrading, run `validateMenu` over every stored menu version. `commodityOf` is unchanged.
- **A non-USD delivery is answered `non_usd`.** Not additive for a caller that tests the outcome. What a caller sees:
  - **A new outcome, `non_usd`, with status 200.** An `invoice.paid`, `charge.refunded` or `payout.paid` in a currency other than USD used to be answered 200 `applied` with no money line. It is now answered 200 `non_usd`, with `body.skipped` (one `<kind> <Stripe id> <amount> <currency>` per line left out). The rows and credits are written exactly as before and the claim is done (its `outcome` column says `non_usd`), so Stripe does not retry. A caller that treated `applied` as the only success must accept `non_usd` as well, and should alert on it.
  - **A new event type, `money.skipped`**, one per line left out, in the outbox beside the credit events (no postings; idem `stripe:<id>:non_usd`). `atm journal` ignores it (no postings). A reader built before it rejects a log that holds one (its `event_type` enum is closed).
  - **A new optional dependency, `warn(line)`,** called once per such delivery after the commit; default is a line on stderr (a throw from it is caught and the line goes to stderr, so the answer is still 200).
  - **`reconcile` has `result.skipped`** (`{ non_usd: n }`, the markers dated in the period; `{}` when none) and prints a "skipped in the log" line; `atm report` prints the count on stderr and `reportMonth` returns `skippedNonUsd` (`{ inMonth, total }`). Detail and the reasoning: `docs/financial-reports.md`, "Non-USD".
- **The handler books a dispute and Stripe's dispute fee.** `charge.dispute.created` now makes a `payment.disputed` (`assets:stripe` -(amount + fee), `expenses:billing:disputes` +amount, `expenses:billing:dispute-fees` +fee) when Stripe withdrew money, and `charge.dispute.closed` a `dispute.closed` (lost: nothing more; won: the amount comes back, the fee does not). The fee is read from the dispute's own `balance_transactions`, not passed by the caller. Subscribe the endpoint to `charge.dispute.closed` as well as `charge.dispute.created`; a log reader built before 0.8.0 rejects a log that holds the new event types (its `event_type` enum is closed); `reconcile` counts the new fee account with the payment fees. Not built: `charge.dispute.updated`, closing statuses other than won and lost, non-USD (`docs/financial-reports.md`, "Disputes and Stripe's dispute fee").

### What 0.8.0 adds: bookings, paid bookings and codes

atm owns the rules; the family service stores rows and talks to Stripe. Everything below is pure: it takes the subject's rows and the time and returns one write (`rowChanges`, to be applied only if the stored revision is still `expectedRevision`, in one transaction with `events` appended to the outbox) or a typed refusal. None of it reads a clock. The design, with the reasons, is in `ROADMAP.md` ("0.8.0 design"); the types are in `src/types.ts`.

#### What to store

- **Nothing new for held credits.** The hold's lock row is kept by atm in the subject's `atm_grants` row (`GrantsState.bookings[<bookingId>].lock`), because the engine's own rows keep only an open lock's ids and `finalize` needs the whole row. Store the grants row as before. `GrantsState` gains two optional keys, `bookings` and `redeemed`; they are absent until used, and an old state loads and saves byte for byte (`tests/billing-state-compat.test.ts`).
- **Each bookable item's `billing`** (a booking type, an event with sign-ups): store the JSON of `Billing` and check it with `validateBilling(billing, menu)` when the item is saved. `{ kind: "free" }`, `{ kind: "included", featureId, credits, tierIds? }`, `{ kind: "price", amount, currency }` or `{ kind: "included_or_price", featureId, credits, tierIds?, amount, currency }`. `amount` is cents; `currency` must be the menu's. With `tierIds`, only those tiers spend credits and everyone else (other tiers, non-members) pays the price.
- **A booking index for paid bookings:** `bookingIds`, a map from a payment intent id (or charge id) to the booking id, read from the `booking` outcome of the paid event (below) and passed back on later events, as `invoiceIds` is for invoices. A refund names a charge, not a booking.
- **Session gift codes:** one row per code, the JSON of `SessionGiftCode`, found by its code text (compared without case) and unique on it. See "Gift codes".
- **Stripe's promotion code ids by code text**, if a member code is applied by `checkoutParams({ code })` (below): `withPriceIds(params, priceIds, promotionCodeIds)` swaps the text for the `promo_...` id.
- **Booking ids must be unique across the school and the Stripe mode.** The ledger's `idem` for a booking is made from the booking id alone, and the outbox drops a second event with the same `idem` for a school: two families whose bookings are both `"42"` lose the second family's `credit.held` from the books (found by the review). Use a UUID. The same id under the `test` and the `live` env collides the same way.
- **Policy:** three new fields, `cancelCutoffHours` (24), `noShow` (`spend`) and `lateCancel` (`spend`). A policy stored without them gets the defaults; a `policy.json` may name them (`resolvePolicy` accepts them). The menu schema gains optional `codes`, so the family service's own menu schema and editor must accept it (they refuse unknown keys today).

#### Price a booking or an event, and spend credits

1. **Quote:** `quoteBooking({ billing, menu, policy, grants, available?, tierId?, now })`, with `grants` from `grantsFromRows(rows)` and `available` the units the member can spend now (`balancesOf`'s `avail`; it leaves out what is held). It returns `{ ok: true, cost }` where `cost` is `{ kind: "free" }`, `{ kind: "credits", featureId, credits }` or `{ kind: "price", amount, currency }` (`via` says which half of `included_or_price` applied), or `{ ok: false, reason, message }`. Reasons: `invalid_billing`, `bad_input`, `not_a_member`, `membership_not_active`, `tier_not_included`, `feature_not_in_plan`, `insufficient_credits`, `currency_mismatch`. Without `available` the quote trusts the plan and the hold's own check decides.
2. **Free:** book it; nothing else.
3. **Credits:** at booking time call `holdBooking({ ...context, bookingId, featureId, credits, startsAt, expiresAt })`. The credits leave what the member can spend (the balance's `held` rises) and stay on an engine lock until `expiresAt`. Choose `expiresAt` at or after `startsAt` (a hold that lapses before the session would spend or release it early); a day after the end is a sensible choice. The lock's expiry action is `confirm` when `policy.noShow` is `spend` (an unsettled booking is a no-show) and `release` otherwise. `context` is the same as for `handleStripeEvent`: `menu`, `menuVersion`, `policy`, `policyVersion`, `rows`, `revision`, `catalog`, `now`, `env`. The same call twice is a replay: ok, `rowChanges: null`. Another call with the same id and different fields is `booking_conflict`. Not enough spendable credits is `insufficient_credits` (two holds for the last credit cannot both succeed, and a stale `revision` is refused by your own revision check).
4. **Then, per what happens to the booking:**
   - the session happened: `confirmBooking({ ...context, bookingId })` spends the held credits (`credit.spent`; `credit.low` or `credit.depleted` when the balance reaches `policy.lowCreditThreshold` or zero);
   - the member cancels: `cancelBooking(...)`. Before `policy.cancelCutoffHours` ahead of the start the credits go back to the rows they came from; between the cutoff and the start `policy.lateCancel` decides (the result says `late: true`); at or after the start it is `session_started`: use `noShowBooking`;
   - the member did not come: `noShowBooking(...)`, `policy.noShow` (`spend`: `credit.forfeited`, the credits move to `credits:forfeited`; `release`: back to the member);
   - the school cancels or declines: `releaseBooking(...)` gives everything back.
   - Every repeat of a settle is a no-op; the opposite settle is `already_settled`; an unknown booking id is `no_hold`.
5. **Expired holds are yours to sweep.** The engine never runs a lock's expiry action by itself. Run a cron: `expiredHolds({ rows, now })` lists the holds past `expiresAt`, soonest first; call `settleExpiredHold({ ...context, bookingId })` on each (`confirm` keeps the credits spent, `release` gives them back). A call on an expired hold that does what the expiry action does still works; the opposite is `hold_expired`.
6. **Draw order.** The rows that lapse soonest are drawn first (`commandOrg(policy)` is on every command), and a release returns the credits to the rows they came from.
7. **Events.** The `events` of each result go to the outbox with `rowChanges` in one transaction: `credit.held`, `credit.released`, `credit.spent`, `credit.forfeited`, `credit.low`, `credit.depleted`, each labelled with the booking id (`labels.booking`). `recordEngineCommand` is for commands you run yourself; do not also record these.

#### A booking paid in money

1. `bookingCheckoutParams({ schoolId, familyId, bookingId, name, amount, currency, forProfileId?, returnUrls })` returns the Checkout Session parameters (payment mode, one inline price, metadata `b4u_school`, `family_id`, `booking_id`, `b4u_kind: booking`, on the session and on its payment intent, because Stripe copies the payment intent's metadata to the charge and not the session's). Refusals: `bad_amount`, `bad_currency`, `no_booking_id`. Create the session on the school's Stripe account with those parameters.
2. Subscribe the school's endpoint to `checkout.session.completed`, `checkout.session.async_payment_succeeded` and `checkout.session.expired` (and `charge.refunded`, which it has). Call `handleStripeEvent` for them, with `bookingIds`. The result has a new optional field, `booking`: `paid` (confirm the booking, and store `paymentIntentId` and `chargeId` into `bookingIds`), `expired` (free the slot), `refunded` (a full refund: cancel the booking) or `partly_refunded` (cancel nothing: the school decides). The replay of a paid session decides nothing, so write the rows and act on the outcome in one transaction. A second paid session for a booking that is already paid, held or spent is refused `rejected`.
3. A refund of a booking's charge no longer comes back `unmatched_invoice`: a charge named in `bookingIds` (or whose metadata names a booking) is a booking's. A refusal `unmatched_booking` means a refund that names a booking this holder has no payment for.
4. **Booking money, since 0.9.0:** a booking's payment and refund make `payment.succeeded` and `payment.refunded` (see "A paid booking's payment and its refund now make money lines" under "Moving to 0.9.0 from 0.8.0"). **Not done:** `checkout.session.async_payment_failed` and a lost dispute on a booking's charge are not mapped. The reference webhook handler (`handleStripeWebhook`) has no booking index: through it a booking's refund still answers 409 `unmatched_payment`; call `handleStripeEvent` from your own endpoint for these. The fixtures are recorded from a test-mode sandbox with `stripe trigger` plus added metadata (`fixtures/billing/stripe/recorded/booking/`), not from a session made by `bookingCheckoutParams`; `async_payment_succeeded` is an edited copy of a recorded `completed` and is marked unverified.

#### Codes

- **Member codes** (percent off tiers only, never add-ons or gifts): the menu gains `codes: [{ id, kind: "member", code, percentOff, tierIds?, firstTimeOnly?, expiresAt? }]` (`policy.memberCode` still works for one code and keeps its coupon id). `menuToStripe` makes, for each, a coupon restricted to the tier products and a promotion code, with the same `StripeOp`s as before (a menu with no `codes` publishes exactly what 0.6.0 did). `StripeOp` `promotion_code.ensure` gains an optional `expiresAt` (ms): an executor must set Stripe's `expires_at` (seconds) from it, or the code never ends. Any change to a code (text, percent, tiers, expiry, first-time flag) deactivates the old code and archives its coupon.
- **Checkout:** `checkoutParams` sets `allow_promotion_codes: true` when the school has any member code or a dollar gift add-on (the buyer types it). With `code` it applies that member code and sends `discounts: [{ promotionCode: <text> }]` and not `allow_promotion_codes` (Stripe refuses both); refusals `code_not_found`, `code_not_applicable` (the code excludes that tier). Codes do not stack: Stripe takes one code per checkout, and atm does not combine a member code with a gift. atm cannot tell that a code has expired (it reads no clock): Stripe refuses an expired promotion code.
- **Discounts do not change credits.** An invoice line has `discount` (what discounts took off it) and the invoice has `discount`; `amount` stays the price times the quantity, before the discount (checked on real Stripe invoices, `fixtures/billing/stripe/recorded/discount/`). A discounted invoice, a 100% off one and a raise under a discount grant exactly what a full-price one does. Proration lines cannot be discounted in Stripe.
- **Dollar gift certificate:** `dollarGiftOps({ schoolId, menu, policy, giftId, code, amount, issuedAt })` returns `GiftStripeOp`s: `coupon.ensure_amount` (a fixed amount off, in the menu's currency, applies to the tier and non-gift add-on products, `duration: once`) and `promotion_code.ensure_limited` (`max_redemptions: 1` and `expiresAt` in ms, `policy.giftDollarMonths` after `issuedAt` on the school's calendar), and `promotion_code.deactivate` when you retire one. These are a separate type, `GiftStripeOp`, not a `StripeOp`: your executor must handle them. The amount is at least `policy.giftDollarMinimum` and at most 99,999,999 cents. Stripe keeps no remainder of a fixed amount that is larger than the invoice: the unused part is lost.
- **Session gift certificate:** `createSessionGiftCode({ id, code, featureId, credits, redeemBy, createdAt, menu, policy })` makes the code state to store; `redeemSessionGiftCode({ ...context, code, entered, holder })` checks the text (without case), the one-use rule against the stored `code.redeemed` and `redeemBy`, then grants `credits` as a new credit row (lapsing `policy.giftSessionMonths` after redemption on the school's calendar; a holder with no rows yet gets a subject) and returns the code's next state, the `rowChanges` and the `events`. Write the code row and the holder's rows in ONE transaction, and write the code with a guarded update (`UPDATE ... SET redeemed = ? WHERE id = ? AND redeemed IS NULL`, and abort when no row changed): atm checks the state it is given, and two holders who read the unredeemed code at once are stopped only by that write. A replay by the same holder is ok with nothing to write. Refusals: `code_mismatch`, `expired`, `already_redeemed`, `unknown_feature`. The redeem events carry no `cause` (a typed code has no stored input event) and a `gift_code` label naming the code id.
- **Who may create codes** is the family service's decision; atm has no users. Recommended: school owners and admins only, the same check as editing the menu.
- **Referral codes are not built** (`ROADMAP.md`).

#### Other things to know

- **Held credits and a refund.** Credits a booking holds are not in the balance. A full refund or lost dispute of the invoice that granted them takes back what is unused; the held part is remembered on the invoice's record (`owed`, an optional key that is absent when nothing was held) and is taken back when the booking releases it (`credit.adjusted`); a confirm keeps it spent. So holding credits and cancelling after a refund no longer gives them back.
- **Held credits across a renewal.** `BookingRecord.resetsAt` remembers when each refilling row was due to reset. A release after the row reset does not put last cycle's credits into the new cycle: with rollover they come back as a rollover that lapses with last cycle's leftovers (within the cap; the rest is booked `credit.expired`), without rollover they lapse (`credit.expired`). A release onto a row that has already lapsed also books `credit.expired`. Either way the engine and the books agree.
- **Ex-members.** A canceled membership does not stop a member from using credits that are not the membership's: packs, gifts and redeemed codes still count in `quoteBooking`; membership status and `tierIds` limit only the tier's and recurring add-ons' credits.
- **Cancel after the start.** A cancel at or after `startsAt` is refused `session_started`: use `noShowBooking`.
- Known limits (`ROADMAP.md`): a rollover cut by a refund is recreated by the engine under a new id, so units held on the old one lapse on release (the safe side); the held record whose engine lock is gone stays in `expiredHolds` and answers `no_hold` on every sweep; `holdBooking` with the id of a released booking is a replay, so check `booking.state` before treating it as held.

## Moving to 0.6.0 from 0.5.0

A minor release: it adds the pieces that turn the handler's events into financial reports, and one handler change that adds events. Nothing is removed. What a caller sees:

- **The handler writes more events per delivery.** An `invoice.paid` now also makes a `payment.succeeded`, a `charge.refunded` of a handled invoice a `payment.refunded`, and a `payout.paid` event a `payout.paid` (see "Stripe fees, refunds and payouts in the log" below). A test or a caller that counted events per delivery sees more, and an endpoint must subscribe to `payout.paid` to book payouts.
- **New exports:** `shipOutbox`, `planOutbox`, `outboxStatus`, `recordEngineCommand`, `recordLapse`, `reconcile`, and the types that go with them.
- **New CLI commands:** `atm ship`, `atm report`, `atm reconcile`; `atm journal` and `atm ship` take `--json` and exit 2 on an error that is not a conflict.
- **New optional handler dependency:** `paymentFee(event)`, the Stripe fee of a payment (without it the payment is booked gross, with `fee_known: false`).
- **A menu with colliding feature ids is now refused, and this one is a break.** A credit's commodity is its feature id in capitals with every non-letter dropped, so `light-60` and `light-90` were both `LIGHT` and their credits added up in one hledger balance, and an id with no letter (`2026`) threw when its first credit was journaled. `validateMenu` now returns `{ ok: false, problems: ["features.1.id"], messages: ["feature ids \"light-60\" and \"light-90\" both become the credit commodity LIGHT ..."] }` (`messages` is new and optional) and `menuCatalogRows` throws the same sentence, so a caller that builds its catalog from a stored menu on each webhook fails on a colliding one. `commodityOf` is unchanged, so journals already built keep their commodities (a merged balance in one cannot be split afterwards). Before upgrading, run `validateMenu` over every stored menu version, the published ones too: the family service's menu editor names a new credit `credit`, then `credit-2` (`packages/web/src/lib/school-billing/validate.ts`, `blankFeature`), which are both `CREDIT`, and a published version is not edited in place, so a school that has one needs a new version with ids whose letters differ (the family service's `docs/features/school-billing.md` says a member keeps the version they bought, so that older version would still be refused when its catalog is built). This release does not touch `buzz-school`, and the family service, still on `atm-v0.3.0`, does not call `validateMenu`.
- **`drawnAfter` is now defined at the lapse instant.** `drawnAfter(t)` is the units drawn strictly after `t`, and `lapseAlertEvents` calls it once per lapse instant `I`, with `I - 1` (it counts a draw at exactly `I`), and adds that one number to both totals it compares. In 0.5.0 (the first release with `drawnAfter`) it was called with `I - 1` for the total before the lapse and `I` for the total at it, so a draw at exactly `I` was added back on one side only and could make a false `credit.depleted`. A caller that returns draws by time needs no change (only a draw at exactly `I` is judged differently, and now correctly); one that ignored the argument gets the same answers.
- **A recurring add-on paid on a subscription atm cannot grant it from is now refused, 422 `addon_only_subscription`.** A paid invoice with a recurring add-on line and no tier line, whose subscription is not the holder's own tier subscription (or the holder has none yet), used to be answered 200 `applied` and recorded as decided with no credits: the member paid for the add-on (for example Glow on a separate subscription) and got nothing, with no error. It is now refused with nothing written, the claim released and a message that names the invoice, the subscription and the add-on. What a caller sees: a new `refused` reason in `StripeEventRefusal` (add it to a `switch` over the reasons), a 422 on the delivery, and for that invoice `invoice_payment.paid` answers 409 `unmatched_invoice` and a refund 409 `unmatched_payment`, both retried by Stripe until it gives up, because the invoice is never indexed. What to do is in Stripe: put the add-on on the member's tier subscription (cancel the add-on-only one, and refund it if the member should not keep it). Re-sending the refused `invoice.paid` does not grant it, because the invoice itself is the wrong shape and is refused again; the add-on is granted from the tier subscription's next invoice (its mid-cycle `subscription_update` invoice for the add-on is granted as before). Re-sending helps only when the member has no tier subscription yet because its invoice has not been handled: re-send after it. The refused invoice's payment is not booked in the money events either, until it is granted. Not refused: an invoice with a tier line, the add-on on the holder's own tier subscription (create, renewal, mid-cycle purchase), one-time add-ons and gifts, lines of no amount or units, a negative proration line (a removed add-on), and an invoice of a subscription that has already ended. A tier subscription's own renewal that has lost its tier line but still bills a recurring add-on is refused too (it would not refill the add-on either). One behaviour that granted before is now refused: a mid-cycle `subscription_update` invoice of a different subscription than the holder's, with an add-on line, was attached to the holder's membership; its rows would never have been retired when that subscription was cancelled. `ungrantedRecurringAddons` (in `src/billing/grants.ts`, used by `handleStripeEvent`) is not exported from the package; a caller of `invoiceToCommands` on its own still gets the old behaviour for such an invoice.
- **What the family service does, in order,** is the first section below. This release changes nothing in `buzz-school`.

### Stripe fees, refunds and payouts in the log

A log made by `handleStripeEvent` or the reference handler used to hold only credit events: `hledger is` and `bs` over it showed no money at all. It now holds the money lines too (`README.md`, "Money lines"). Caller changes:

- **Subscribe the endpoint to `payout.paid`** (a ninth event; the other eight are listed under "Events to subscribe to" below). Without it no payout is booked and the cash stays in `assets:stripe`. Not needed, and ignored if sent: `payout.failed`, `payout.created`, `payout.reconciliation_completed`. A payout carries no family or school, so it is booked to `deps.schoolId`: keep one endpoint per school, on the school's own Stripe account.
- **Pass the fee, if you want it booked.** Add `paymentFee(event)` to `WebhookDeps` (or `fee` to `StripeEventInput`): the Stripe fee in cents of the payment an `invoice.paid` is, which is the `fee` of its charge's balance transaction (invoice payment, then its charge, then `balance_transaction`; for a direct charge on a connected account, as that account). No webhook event carries it. The handler is synchronous, so read Stripe before calling it and answer from what you hold. Without it the payment is booked at its gross amount with no fee line, and its payload says `fee_known: false`. A fee not known at the first delivery is not added later.
- **Every `invoice.paid` now makes a `payment.succeeded`, and every `charge.refunded` of a handled invoice a `payment.refunded`.** A test that counted the events of an invoice or a refund sees one more. `handleStripeEvent` gives the refund's line again when it is handled again (same id and idem; the outbox drops it), so its `events` is no longer empty on that replay; the rows still are `null`.
- **Shapes.** The `charge.refunded` mapping reads `currency` and `previous_attributes.amount_refunded`; there is a `payout.paid` mapping and a `StripePayout` fact. `StripeEventInput` has two optional fields, `fee` and `school` (needed for a payout).
- **A refund line now names its charge, payment intent and invoice, so `reconcile` can pair it.** The handler's `payment.refunded` is labelled with the Stripe event id (`evt_...`; a `charge.refunded` has no refund id), and `reconcile` used to report every one as `missing_in_stripe` beside a `missing_in_log` for Stripe's `re_...`. The payload now also has the optional `charge`, `payment_intent`, `invoice` and `amount_refunded`, and `reconcile` pairs such a refund with Stripe's refunds of the same payment and amount (`StripeRefundRecord` has optional `charge` and `payment_intent`; `stripe refunds list` prints both, so `refunds.json` needs no change). Nothing to change in a caller that uses the handler. A log already written keeps `evt_...` refunds without the fields: those still cannot be paired and are reported. A family service that books its own refunds should carry the Stripe refund id (`re_...`) as `payload.id`, which `reconcile` still matches by id, or the same fields.
- Not built: money lines for disputes, a reversal of a payout that fails after `payout.paid`, and a fee added after the payment was booked.

### Shipping the outbox to a folder

Additive: nothing changes for a caller that does not call it. Until now the handler's events stayed in `ledger_outbox` and nothing wrote the files `atm journal` reads. New exports:

- `shipOutbox({ db, store, school, nowMs })` takes the school's rows with `shipped_at IS NULL` and puts one object per event date, `schools/<school>/events/date=YYYY-MM-DD/batch-<first id>-<16 hex of the text's sha256>.jsonl` (the bodies, one per line, in id order, as the handler stored them), with `putOnce`. An equal object already there counts as shipped; different bytes under the key is a `conflicts` entry and the rows stay unshipped (it never overwrites); so is a day that already has a `day.jsonl`, because the reader keeps only `late-*` beside it. It then sets `batch_key` and `shipped_at` on those rows in one transaction. It returns `{ batches, conflicts, shipped }`. It throws, before any put and for the whole school, on a row the reader could not read or would collapse (a date that is not `YYYY-MM-DD`, an id with a character other than letters, digits, `_` and `-`, a body that is not one line of a JSON object carrying the row's own `id`, `idem` and `date`); the handler never writes one, so this is a guard against a hand-edited database, since the log is create-only and a bad object could not be taken back. The `day.jsonl` check and the put are two calls: a `day.jsonl` that appears between them is not caught (nothing writes one yet). It works on any `Store`; only `FolderStore` is tested. `planOutbox({ school, rows })` is the pure plan it runs, with the types `OutboxRow`, `OutboxBatch`, `ShipOutboxInput` and `ShipOutboxResult`.
- **What a family-service caller changes.** After the handler has answered (or on a timer, or from a cron), call `shipOutbox` with the same `SqlDatabase` the handler uses and a store for the log. Any number of runs, and more than one shipper, are safe: a rerun finds nothing, a crash between the put and the mark is repaired by the next run when no row arrived for that day in between (same rows, same key, same bytes; if one did, the rerun puts a second, overlapping batch and the first stays, its events dropped by the reader by `idem`), and two shippers on the same rows write one file. Alert on a non-empty `conflicts`. Then `atm journal` (or `journalMonth`) over the folder builds the journals.
- `atm ship --db <handler sqlite file> --root <folder> --school <id>` runs it from a shell (Bun only, as the rest of the CLI; it opens the file read-write and waits up to 5 s for the handler's lock). It exits 1 on a conflict, on a `--root` that is not an existing folder (create it first: a typo in it would otherwise make a new folder and mark every row shipped into it), and on a `--school` with no rows in the outbox (it names the schools that have some).
- Not built: R2 batches (the call works against `R2Store`, untested there), the `day.jsonl` combine, the signed manifest and Parquet. A batch is named `batch-*`, never `day.jsonl` or `late-*`. The shipper does not write into a day that already has a `day.jsonl` (a `conflicts` entry), since the reader would not read the batch; once the combine exists, it has to decide how a day combined after its rows shipped takes later rows (`late-*`).

### Logging the family service's own commands

Additive: nothing changes for a caller that does not call it, and the handler writes what it wrote. New exports: `recordEngineCommand({ db, mutation, before, context, logsEveryCommand? })` and `recordLapse({ db, state, featureOf, feature, atMs, tz, drawnAfter?, labels? })`, which append to the same `ledger_outbox` the handler uses (`ON CONFLICT (school_id, idem) DO NOTHING`), so a log shipped by `atm ship` holds what the family service ran and `replayEvents` can replay it.

- **What the family service changes.** After every engine command it runs (hold, finalize, spend, refund) and in the expiry cron, call these with the same `SqlDatabase`, inside the transaction that writes the subject's rows, after the revision check: run the command, write the rows, record the events. They open no transaction. Give each command a `commandId` of its own, unique across the school: one that is already in the outbox for another subject or revision (a booking's id used for both its hold and its finalize, a retry that ran the engine again after the rows committed) makes `recordEngineCommand` throw, so the transaction rolls back, rather than drop the event while the rows change. Recording the same mutation twice adds no second event.
- **What it records.** The whole mutation on every event, a `plan.changed` for a command that moves no credits, nothing for a null or rejected result (which change no rows either). The `context` carries what the postings need that the mutation does not (`feature`, `service`, `as`, `reason`, `settleAs`, `lowCreditThreshold`, ...); the school is the mutation's `identity.orgId`.
- **`payload.complete`.** Left out unless `logsEveryCommand: true`; set it only if every engine command for the subject is recorded. A replay reads it only for commands named `<ULID>:<step>`.
- Not built: commands that move several features (`reset`, `applyBillingPlan`) are not cut by feature and plan here, and `recordEngineCommand` throws for them; a family service does not run them (the handler does). A command that makes new rollover rows (the engine's random ids) is not recorded.

### Reconciling the log with Stripe

Additive: nothing changes for a caller that does not call it. `reconcile({ events, stripe, period, timeZone?, mode? })` and `atm reconcile --root <folder> --school <id> --month YYYY-MM --stripe <dir>` compare a school's events with the arrays `stripe <resource> list` prints (invoices, refunds, disputes, payouts, balance transactions) and return typed differences (`missing_in_log`, `missing_in_stripe`, `amount_differs`, `duplicate_in_log`, `outcome_differs`, `period_differs`, `not_in_log`). The CLI exits 0 when nothing differs, 1 when something does and 2 for input it cannot use, which includes a `--stripe` folder missing any of the five files (the result is still printed; those checks did not run).

- **What a caller changes.** To be told of a lost or wrong event, run the `stripe` commands for the school's connected account (README, "Reconciling with Stripe") and call `reconcile` or `atm reconcile` nightly; alert when `differences` is not empty (or the exit is 1). Nothing is written.
- **It reads the log's conventions.** An event is matched by Stripe's id in `payload.id` (an invoice id on `payment.succeeded`, a refund `re_` on `payment.refunded`, a dispute `dp_` on `payment.disputed` and `dispute.closed`, a payout `po_` on `payout.paid`), as `schema/payload/` describes. A log whose events carry another id reports every one as missing, except a refund event the handler made: its id is the Stripe event's `evt_…`, and it names its charge and payment intent, so `reconcile` pairs it with Stripe's refunds of the same payment by amount (see "A refund line now names its charge, payment intent and invoice" above).
- **A log without fees or payouts reports them once**: one `not_in_log` record for the fees (or the payouts) of the period, not one per payment; the net is then compared before fees.
- **Not built**: no Stripe call (the caller fetches), no schedule, no per-payment fee match (a charge cannot be tied to its invoice on API `2025-10-29.clover`), no alert delivery.

### What-if replay with `simulate` (after 0.6.0)

Additive: nothing changes for a caller that does not use it. A new export, `simulate`, and a new command, `atm simulate --root <folder> --school <id> --current-menu <file> --menu <file> [--policy <file>]`, run the log's commands again under a candidate menu, catalog or policy and diff balances, posting totals and decisions against the log (exit 0 no difference, 1 differences, 2 bad input). It writes nothing. It re-decides credits only: it cannot change what Stripe charged, and the grant rules are not in the log's commands (README, "What if (simulate)"). `replayEvents` is unchanged.

## Moving to 0.5.0 from 0.4.0

A review of 0.4.0 found four ways it could grant or alert wrongly, and five smaller problems. This is a minor release, not a patch, because the handler now refuses a test-mode event sent to a default (`env: "live"`) handler. Two of the fixes change what a caller has to do (`drawnAfter`, and `env: "test"` on a test endpoint):

- **The lapse alert needs `drawnAfter`.** `lapseAlertEvents` takes a new required `drawnAfter(instantMs)`: the units of the feature the holder drew after that instant and up to `atMs`, from the cron's ledger or journal (draws only). A signature change to a function released a day ago that nothing calls yet. Without it a late cron judged a past lapse on today's balances and made a false `credit.depleted` when the family had drawn from another live row since. Pass `() => 0` only when the state is as of the lapse.
- **The engine path does not throw on a malformed proration.** `invoiceToCommands` (so the webhook) reads Stripe's lines through unchecked cores and does what 0.3.0 did, so a malformed value can no longer make the handler answer 500 and Stripe retry for days. The public `prorationPair` and `raiseUnits` still throw, but `prorationPair` checks only the lines it uses: the chosen charge and its credit, and `amount` and `periodStart` on every tier proration line (the selection compares them). A stale older pair with a bad quantity or `periodEnd` no longer makes a valid raise throw.
- **The handler refuses a `livemode` that disagrees with `env`.** An event whose `livemode` is a boolean other than `env === "live"` is answered 422 `livemode_mismatch` before any claim, and nothing is written. A test-mode endpoint must now pass `env: "test"` (the default is `"live"`, so a test-mode event sent to a default handler is refused, where 0.4.0 wrote it to the `|live|` subject). An event with no `livemode` is not refused. `handleStripeEvent` is not checked: it never sees the endpoint.
- **Same-instant ordering.** `lapseAlertEvents` books its `credit.depleted` at `revision + 1`: pass the revision you give the `credit.expired` events of the instant (the highest, if they differ) and the alert sorts after all of them in replay, the journal and the month files; its `eventMs` is still the instant and its idem is unchanged. A revision that is not a whole number, or is 16777215 or more, throws. In 0.4.0 the two shared time and revision and their order was a hash tie.
- **`credit.depleted` has two exclusive shapes.** With `cause: "expired"` the payload must not carry `command` or `mutation`; a draw alert (no `cause`) still must. A payload that mixed them validated in 0.4.0 and is now refused.
- **`raiseUnits` no longer guesses units.** 0.4.0 rejected an `at` and a cycle bound whose magnitudes differed by 100 times or more, which also rejected small synthetic instants (`at=5` with `cycleEnd=1000`). It cannot see units, so `at`, `cycleStart` and `cycleEnd` must all be milliseconds. `perUnit` stays a whole number (menu allowances are whole). `prorationPair` calls your `isTierPrice` once per proration line, where 0.4.0 called it about three times.
- **`env` is validated once** at each public entry point (`handleStripeWebhook`, `handleStripeEvent`, `menuCatalogRows` and the grants functions) and passed down resolved: a bad value throws before anything else runs, including on the grants functions' no-op paths, and can no longer be answered as `missing_metadata`.
- **One customer, several subscriptions: what atm supports (checked in the Stripe sandbox, 2026-11-05).** A person can be a member of several schools: one Stripe customer held three active subscriptions, and atm kept each school's subject apart by `b4u_school` and `family_id` in the subscription's metadata. Three limits to know:
  - **Route by school.** One `handleStripeWebhook` serves one school (`WebhookDeps.schoolId`). If several schools share one Stripe account and one endpoint, read `b4u_school` from the event's metadata and call that school's handler. An event for another school answers 422 `school_mismatch`, which Stripe retries, so a handler fed every school's events will fail every other school's. With one Stripe account per school nothing needs routing.
  - **A subscription that holds only a recurring add-on grants nothing (from 0.6.0 it is refused: 422 `addon_only_subscription`, see "Moving to 0.6.0").** An add-on is attached from the tier subscription's own create or renew invoice, or from a mid-cycle `subscription_update` invoice of that subscription. In 0.5.0 an invoice for a separate add-on-only subscription was recorded as decided with no credits (the handler answered `applied`), so the member paid and got none; from 0.6.0 the handler refuses it (422 `addon_only_subscription`, nothing written) so a human sees it. Cancelling that subscription would not retire the add-on either, because the membership follows one subscription. Put add-ons on the tier subscription.
  - **One tier subscription per school and family.** Events about another subscription of the same family and school do not change the membership, and a second tier subscription after the first ended throws "a second subscription for the same family is not supported yet". (From after 0.6.0 a cycle or update invoice of another subscription with a tier line is refused too: 422 `tier_on_other_subscription`.)
  - The Stripe billing portal lists every subscription of a customer with its own update link, but names them by product only, so two schools' `Sparkle` look alike in a shared account. A subscription with only an add-on gets "Cancel" and no update link.

## Moving to 0.4.0 from 0.3.0

Everything is additive: a 0.3.0 caller that changes nothing gets the same rows, keys and events. What is new, and what a caller has to do to use it:

- **The raise rule as functions.** `prorationPair` reads Stripe's pair of proration lines and `raiseUnits` turns a raise into the units to grant; `invoiceToCommands` calls their unchecked cores (since 0.5.0), so the webhook never throws on a Stripe value. The public functions now throw an `Error` naming the field on bad input (not a finite number, a negative or fractional count, `cycleEnd` before `cycleStart`) instead of returning a wrong number (0.4.0 also rejected a cycle in seconds against `at` in milliseconds; 0.5.0 no longer guesses units, see below). A yearly raise grants the prorated year (a raise 2 to 4 ninety days in grants 19), not 0. The baseline is `GrantsState.quantity`, what the credits reflect, not Stripe's count: pass that to `raiseUnits`.
- **`portalConfigOf(menu, { products, prices })`** makes the billing portal configuration for a tier sold in quantities (a raise billed at once, a decrease at the renewal). A member who also holds a recurring add-on is not offered the update by the portal, whatever the configuration lists (checked in the sandbox), so the caller needs its own route for them. See `README.md`, "Billing portal".
- **Importing a caller's own rows.** `grantsStateFromCallerRows` turns a caller's existing lots into atm's rows and `GrantsState` (see "Moving an existing caller onto `handleStripeEvent`" below); it throws, naming every problem, rather than guess.
- **`env`.** `handleStripeEvent`, `handleStripeWebhook` (as `WebhookDeps.env`) and `menuCatalogRows` take an optional `env` (`"live"` or `"test"`, default `"live"`; anything else throws). It is part of the subject key, `<school>|<env>|family:<id>`. A school with a Stripe test endpoint and a live one must pass it, or both land on the live subject. The family service has `billingKeyMode` and has to pass that. The handler's claim, invoice index, payment index and outbox keys carry no env: Stripe's ids differ between modes, so two endpoints sharing a database do not collide, but the same id under both would be claimed once (closing it changes the DDL; `ROADMAP.md`, and `docs/log-and-r2.md` under "Env on the handler's tables").
- **Expiry alerts.** `lapseAlertEvents` makes a `credit.depleted` (payload `cause: "expired"`) when a lapse takes a feature's credits from above 0 to 0, one per instant however many rows lapse then. Calling it is the opt-in; `lapseEvent` is unchanged. Since 0.5.0 it takes `drawnAfter(instantMs)`, the units the holder drew after an instant, because the state holds balances as of now and a late run would otherwise judge a past lapse on credits drawn from another row since (see "Moving to 0.5.0 from 0.4.0"); `() => 0` is right only when the state is as of the lapse, the state the cron gave `lapsedRows`. A row made after the lapse is still counted, since the state does not record when a row was made. There is no `credit.low` on a lapse.
- **Replay** reads logs written by 0.3.0 and stops at what they lost (see "Replaying a log" below). **Invoice links and the one-time checkout** are described under "Invoices and receipts" below. An endpoint left on an API version older than `2025-10-29.clover` has its b4u invoices refused with 422, which Stripe retries; the dashboard is the only signal.

## Moving to 0.3.0 from 0.1.0

0.1.0 was the engine as a CLI and a library: `runEngineCommand` and the engine's own types, nothing else. Everything billing-related is new to a 0.1.0 caller: the menu, Stripe mappings, grants, the webhook handler, the object store and the ledger events. `runEngineCommand` and the CLI work as before. `README.md` describes each piece; this lists what a caller has to provide and the behaviours that are easy to get wrong.

### Stripe

- **API version.** The mappings read Stripe API `2025-10-29.clover`; an event from any other version is refused (`unknown_mapping`), with a message that names the endpoint's version (`event.api_version`) and the fix, which is to recreate the endpoint with `api_version: "2025-10-29.clover"`. atm does not read a second layout (an older endpoint sends `line.price.id` and `line.proration`): the mappings are checked against the pinned version's OpenAPI spec, and a second shape would be unchecked. A school's webhook endpoint must be created with `api_version: "2025-10-29.clover"` (the endpoint's version, not the request header, decides the shape of the events it receives), and every API call should send the same `Stripe-Version`.
- **Events to subscribe to:** `invoice.paid`, `invoice_payment.paid`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`, and since the section at the top `payout.paid`. Without `invoice_payment.paid` a refund or dispute cannot find its invoice and answers 409 until Stripe gives up.
- **Checkout metadata.** Put `b4u_school` and `family_id` in `subscription_data.metadata`. On the invoice they arrive at `parent.subscription_details.metadata`; atm reads both and the invoice's own keys win.
- Shapes were checked against real payloads from a Stripe sandbox (`fixtures/billing/stripe/recorded/`). The pin is still unverified against a school's own account.

### Handling an event

- **One entry point:** `handleStripeEvent(input)` turns a raw Stripe event and the subject's stored rows into row changes and ledger events. It reads no clock and writes nothing. The caller verifies the signature, dedupes on Stripe's event id, checks the revision and writes the result in one transaction.
- **`eventId` must be a ULID**, the id of the stored input event, not Stripe's `evt_` id. Anything else comes back `refused` as `bad_event`. Derive it from the Stripe id with `deterministicUlid` (exported from `atm`) so a replay gets the same id. The reference handler uses:

  ```ts
  const eventId = deterministicUlid({ timeMs: event.created * 1000, revision: 0, seed: JSON.stringify([schoolId, event.id]) });
  ```

  `timeMs` is the event's own instant (Stripe's `created` in milliseconds); `revision` is the subject's revision, or `0` as here (it fills 24 bits of the id so events in one millisecond sort in the order they were decided); `seed` is any string that is stable for the event and unique to it across schools (the handler seeds with its canonical JSON of `[schoolId, stripeEventId]`). The same three inputs always give the same id.
- **Reference handler.** For Bun or Node, `handleStripeWebhook(deps, request)` verifies the signature, claims the event id in its own short transaction (a stale claim is taken over), then writes rows, events, the indexes and the done mark in one SQLite transaction. Create its tables with `HANDLER_DDL`. A caller with its own handler must provide the same three things: the claim, the invoice-to-subject index and the payment-to-invoice index.
- **One school per endpoint.** `deps.schoolId` is required: the school this endpoint and its signing secret belong to. An event whose `b4u_school` names another school is refused (422 `school_mismatch`) before anything is claimed.
- **Answers.** What Stripe sees decides whether it retries, so the handler sorts every outcome into one of three kinds:

  | Answer | Outcome (`reason`) | Meaning |
  | --- | --- | --- |
  | 409, retryable | `refused` (`unmatched_invoice`), `refused` (`unknown_subscription`), `unmatched_payment`, `busy`, `stale_revision` | The link or the earlier event has not arrived yet, or another delivery holds the claim. Stripe retries; nothing needs fixing. `unmatched_payment` is its own outcome (a refund or dispute whose payment is not in the payment index yet), not a refusal reason. |
  | 422, needs a human | `refused` (`unmatched_line`, `missing_metadata`, `unknown_mapping`, `bad_event`, `rejected`, `addon_only_subscription`, `tier_on_other_subscription`), `unknown_school`, `school_mismatch`, `livemode_mismatch`, `ambiguous_payment` | Retrying gives the same answer. `missing_metadata` is metadata that is half filled (for example `b4u_school` without `family_id`); `unknown_mapping` is an event from another API version; `unknown_school` is a school with no context; `livemode_mismatch` (0.5.0) is an event whose `livemode` disagrees with `env`; `ambiguous_payment` is a payment that links to more than one invoice; `addon_only_subscription` (0.6.0) is an invoice that pays for a recurring add-on on a subscription that is not the member's tier subscription, which atm would otherwise record with no credits (fix in Stripe, then re-send); `tier_on_other_subscription` (after 0.6.0) is a cycle or update invoice with a tier line on a subscription that is not the member's own tier subscription (fix in Stripe; re-sending gives the same refusal). |
  | 200, done | `applied`, `duplicate`, `ignored` | `ignored` is an event type atm does not handle, and an event with no `b4u_school` at all (not one of ours, for example another product on the same Stripe account). |

  A 401 (`bad_signature`) and a 400 (`bad_request`) answer a delivery that never reaches the rules.

### Credits

- **Deduction order.** Put `commandOrg(policy)` on every `track`, `check` and `finalize`. `policy.deductionOrder` is `expiry` (default: the row that lapses soonest first, then the oldest grant) or `engine` (Autumn's own order). A caller that sends its own org config gets the engine's order.
- **Stored state.** A subject's billing state is one JSON row (`atm_grants`) beside the engine's rows, under the same revision. It holds each grant's `holder` and `retired` flag and the subject's `membership`.
- **Membership status** has the value `incomplete` (not yet paid), and `customer.subscription.*` events record the membership without granting anything: credits still come only from paid invoices.
- **Policy.** `deductionOrder` and `lowCreditThreshold` are policy fields; a school's policy that leaves them out gets the defaults.

### Events

Ledger event types include `credit.expiration_changed` (a row's credits stay but their end date moved), `credit.low` and `credit.depleted`. Delivery of "N visits left" notices stays with the caller.

- `credit.low` and `credit.depleted` fire only for draws by `track` or `finalize`, that is customer activity (holds and spends). A refund or dispute clawback and an admin edit do not raise them. The one other source is the clock: a cron that calls `lapseAlertEvents` gets a `credit.depleted` (`cause: "expired"`) when rows lapse and the feature's total goes to 0.
- They are judged on availability including holds, so a hold can take a family under the threshold before any visit is spent.
- atm does not remember that it already alerted. The family service should dedupe its notices per holder, feature and grant or cycle.
- They are opt-in per call. `handleStripeEvent` never makes them (it runs only billing commands). The family service passes `policy.lowCreditThreshold` as `lowCreditThreshold` in the context it gives `mutationToEvents` for its own `track` and `finalize` mutations. Without it no alert is made at all; a threshold of 0 makes `credit.depleted` only.

### What surprised us on real Stripe data

These are facts about the API at `2025-10-29.clover`, checked against sandbox payloads. They are why the mappings read what they read.

- A subscription's tier and interval come from its price items (`SubscriptionFact.items`: price id, lookup key, interval), not from checkout metadata, which goes stale after a plan change in the portal.
- A real charge carries no refund list. `BillingRefund.id` is the Stripe event id and `amount` is the charge's total refunded after the event.
- A renewal invoice's own period is the previous one. The renewal's period comes from the tier line.
- With checkout's `subscription_data.metadata` the invoice's own metadata is empty; it is on `parent.subscription_details.metadata`.
- A charge or dispute does not name its invoice; `invoice_payment.paid` is what links them.

### Tier quantities

A studio sells one tier at several counts (Vibes of Light: Shine at 1, 2 or 4 sessions a month) with `quantities` on the menu tier instead of one tier per count.

- **Menu.** `MenuTier.quantities`: 1 to 6 unique whole counts from 1 to 50, ascending; absent means `[1]`. Prices and grant amounts are per unit. A price times its largest count must stay under 99,999,999 (Stripe's line cap). Editing `quantities` makes no `menuToStripe` step.
- **Checkout.** `checkoutParams` takes `quantity` (default 1). A count the tier does not offer comes back `{ reason: "quantity_not_offered", quantity }`; answer 400 with `fields: ["quantity"]`. `line_items` is now a tuple: the tier line first (at the quantity), add-ons after at 1. The subscription metadata carries `quantity` only when it is not 1, and only for information: the item's quantity at Stripe is the truth.
- **Normalized events.** Subscription items and invoice lines carry `quantity` (an integer 0 to 99,999,999; a missing one reads as 1; a negative, fractional or larger one is refused `bad_value`). A line or item with quantity 0 is dropped by the grants rules, never counted as 1.
- **State.** `GrantsState.quantity` is what the credits reflect and moves only with paid invoices; `MembershipRecord.quantity` is what Stripe says and moves with `customer.subscription.*`. A stored state from 0.2.0 loads with both at 1.
- **Credits.** Create and renewal grant the per-unit allowance times the tier line's quantity (a yearly payment on a monthly grant: times 12). A raise on the same tier grants the extra units, prorated per `policy.upgradeGrant`, counted from the quantity the credits reflect (`GrantsState.quantity`), not from Stripe's old count: after a decrease that waits for the renewal, a raise back up to the count the credits still hold grants nothing, and one above it only the units past it. A decrease grants nothing and takes effect at the renewal. Rollover `max` scales with the quantity, and the engine has one cap per row, so after a decrease the carry-over cap follows the lower count.
- **The rule without the state.** A caller that keeps its own credits and has no `GrantsState` reuses the raise rule instead of copying it: `prorationPair(lines, isTierPrice)` reads Stripe's pair of proration lines and `raiseUnits({ perUnit, oldQuantity, newQuantity, at, cycleStart, cycleEnd, policy })` gives the units to grant (README, Billing, "Quantity raises without the grants state"). `invoiceToCommands` calls both. Pass the quantity your credits reflect as `oldQuantity`.
- **The family service must:** make a raise with `proration_behavior: "always_invoice"` (otherwise Stripe bills it at the renewal and nothing is granted until then); schedule a decrease for the renewal; and read `quantity` from the subscription item, not from metadata. `portalConfigOf(menu, { products, prices })` (added after 0.3.0, so not in that tarball) makes both settings for the billing portal: post its fields to `/v1/billing_portal/configurations` and pass the id it makes as `configuration` on each portal session (`README.md`, "Billing portal"). It returns `null` for a menu without quantities, where the school's default portal applies. A caller that changes quantities through its own API calls instead must set `always_invoice` and the scheduled decrease itself.
- A tier change and a quantity change in one update grant `newAmount x newQuantity - oldAmount x oldQuantity`, not below 0. This case is not checked against real payloads.
- **A raise on a yearly plan grants too** (it does not grant 0). A monthly grant on a yearly plan counts 12 per unit, so the extra units carry a year of it, prorated per `policy.upgradeGrant` by the share of the year left (2 -> 4 of a 2-a-month tier, ten days in: 2 x 12 x 2 = 48, x 355/365, rounded up: 47; `full` 48; `none` 0). A yearly grant on a monthly plan (a retreat a year) grants nothing at a raise: its next refill is already at the new count. Only synthetic fixtures pin this; no real yearly raise payload has been recorded.

### Invoices and receipts (after 0.3.0)

What a family service caller changes:

- **Link a receipt.** `BillingInvoice` has `number`, `hostedInvoiceUrl` and `invoicePdf` (`string | null`, absent on a fact built by hand). `handleStripeEvent`'s result does not carry them (the grants state keeps no invoice facts), so read them from `normalize` of the same `invoice.paid` event (or from the raw event), then store or show the number and the two links. The URLs are bearer links: give them only to the family the invoice belongs to and keep them out of logs.
- **Selling a gift certificate or a pack with no membership.** Do not build the Checkout by hand in `mode=payment` without `invoice_creation`: Stripe then makes no invoice and no `invoice.paid` arrives, so nothing is credited. Call `oneTimeCheckoutParams` (it returns payment-mode parameters with `invoice_creation[enabled]=true` and our metadata in `invoice_data.metadata`), then `withPriceIds` and `toStripeForm`, as you do for a membership. The webhook endpoint is the same (`invoice.paid`). A one-time add-on bought together with a membership needs nothing new: it rides the subscription's first invoice, as before.
- **`checkoutParams` is unchanged.** Same output for the same input; still subscription mode only. `withPriceIds` now also accepts `oneTimeCheckoutParams`'s result (typed by overload; a membership's call still returns `CheckoutParamsWithPrices | null`).
- **School setup, not code.** The invoice shows the school's name, address, branding and tax ID from the school's own Stripe account (the connected account is the issuer of a direct charge). The EIN prints only if the school has it as a tax ID on that account (`us_ein`) and as a default account tax ID. Idaho's itemised receipt also needs the child's legal name, subject, hours and tax, which the Stripe invoice does not hold; atm does not build that receipt yet (`ROADMAP.md`; the open questions are in `docs/receipts.md`).

### Storage

- `Store` and its errors, `FolderStore` and `R2Store` (on `aws4fetch`) are exported, with a contract suite that runs against the folder and SeaweedFS. Live balances stay in the caller's SQLite; the object store holds the append-only log.
- Both stores validate keys and byte ranges strictly and refuse what they cannot serve; no caller should rely on a looser reading. `FolderStore` treats reserved names case-insensitively, as a case-insensitive filesystem does.
- `balance-engine` has one opt-in change (`org.config.deduction_order`), listed in `UPSTREAM.md`.

### Moving an existing caller onto `handleStripeEvent`

For a caller that already grants credits on its own and has paying members (B4 Uni's family service: `school_memberships`, `school_credit_lots`, rules in `src/school-billing/grant.ts`). It uses only `runEngineCommand` today; this is how to move it onto `handleStripeEvent` without regranting anything. For buzz-school today, "Moving buzz-school's grants onto the handler (D12)" at the top comes first: it has the pin, the outbox and the endpoint steps as they are now.

1. **Create each school's webhook endpoint with `api_version` `2025-10-29.clover`** (see Stripe above), with `createCloverEndpoint` beside the old endpoint, not in place of it (the two-endpoint method, in the D12 section at the top). An event from any other version is refused (`unknown_mapping`) with a message that names the endpoint's version and says to recreate it.
2. **Import each member once**, in one transaction, with the member's lots and the menu their invoices were granted against:

   ```ts
   const { state, rows } = grantsStateFromCallerRows({ membership, lots, menu, now });
   // write `rows` (engine rows and the atm_grants row) for the subject <school>|live|family:<family_id>, at one revision
   ```

   `membership` and `lots` are the `SELECT *` rows (`CallerMembershipRow`, `CallerCreditLotRow`): the membership's instants are Unix seconds, the lots' are milliseconds. `now` is the instant of the import: a lot past its `expires_at` holds nothing and is not carried over. The subject is `family:<family_id>` at the membership's school, the identity the caller already uses.
3. **Stop the caller's own grants and takebacks at the same moment** (the `grantForInvoice` and `removeForInvoice` calls), and hand `handleStripeEvent` only events the caller has not applied: an invoice the caller granted is found in `state.invoices` and grants nothing, but an event the caller handled that left no lot (an upgrade proration, a manual invoice) is not known to atm and would be decided afresh. Start from the caller's `school_stripe_events` cutoff.
4. **Pass `invoiceIds` for payments made before the import.** A refund or dispute names its charge and payment intent, not its invoice; atm learns the link from `invoice_payment.paid`, which it has not seen for the old invoices. Without it a refund of one of them is refused `unmatched_invoice` (409, retried until Stripe gives up). The caller has the link (the invoice's `payment_intent`). The reference handler finds the subject of a refund by joining two tables, so each old invoice needs a row in both: `atm_payment_index` (payment intent to invoice id) and `atm_invoice_index` (invoice id to the subject key, `<school>|live|family:<family_id>`). With only the first, the refund is answered 409 `unmatched_payment`.

What the import reads from the rows, and what it does not:

- **Read:** the holder (`school_id`, `family_id`), the subscription, the tier, interval and add-ons, the quantity the credits reflect (the newest tier lot's `allowance` over the menu's per-unit amount; the membership's own `quantity` goes to `membership.quantity`), the cycle (read back from the lots' `expires_at`, minus the rollover months on the school's calendar), each lot's balance, expiry and removal, and the decided invoices.
- **Refused, naming each problem** (one error lists them all): a tier, add-on or feature the menu does not have; a tier the menu does not price at the membership's interval; a lot that is no grant of the membership's tier, or is for an add-on the membership no longer has; a lot of another member or with a source that is not `tier` or `addon:<id>`; a tier grant or a recurring add-on with no lot (atm refills only rows it holds, so it would silently stop granting it); credit rows on different cycles (a renewal granted to some and not others); a lot that is not a whole number of the menu's per-unit amount. A membership with no lots yet imports as just the membership: the first invoice then grants as for a new member.
- **Not in the rows (the owner decides):**
  - `GrantsState.anchor` (the first invoice's period start) is `null`; no rule reads it.
  - `cycleStart` is the cycle end minus one interval, not the invoice's own start; only the proration of a mid-cycle upgrade reads it.
  - A yearly grant on a monthly plan (Shine's retreat) has no refill date in the rows: its next refill is set a year after its lot's creation. The caller's own rule gives such a lot `expires_at` = the end of the first month's period (it has no rollover), so by the second month the lot holds nothing and the import carries that balance of 0; atm then refills it a year after the first invoice. Decide whether the retreat should be restored for current members.
  - `GrantsState.tierId` is the membership row's tier. A plan change Stripe made that no invoice has paid yet cannot be told apart in the rows.

Where atm's rules differ from the caller's, so a renewal after the import is not always the same (each is pinned in `tests/billing-adopt.test.ts`):

- **Rollover cap.** The caller never caps a rollover (a lot keeps its balance until it expires); atm carries over at most the grant's `rollover.max` (times the quantity). A leftover above the cap is lost at the renewal. The imported rows themselves are not capped.
- **Rollover months on the school's calendar.** The caller adds rollover months on the school's time zone; the engine adds them on the UTC calendar. Across a clock change the rollover of a cycle lapses a whole hour from the caller's lot (Denver, a January cycle: 17:00Z against 18:00Z).
- **A cycle not renewed.** The caller's lot lapses at the cycle end plus the rollover months. atm's refilling row stays until the next invoice or the cancellation (`subscriptionEndedToCommands` sets its expiry).
- **Session gifts.** The caller's gift lot lasts until its own rollover months, or keeps if the grant has none; atm gives a gift of sessions an expiry `policy.giftSessionMonths` after payment (six months by default). Gifts imported keep the caller's expiry; a gift bought after the import gets atm's.
- **What an invoice grants.** The caller grants on `subscription_create`, `subscription_cycle` and `subscription_threshold` only. atm also grants a mid-cycle upgrade or a raise in quantity (a `subscription_update` invoice, per `policy.upgradeGrant`), which the caller does not.

### Replaying a log (after 0.3.0)

`replayEvents` now reproduces what `handleStripeEvent` writes. What a caller needs to know:

- **New events.** `handleStripeEvent` records every event of a command with the whole mutation (`payload.slice` lists the positions in `mutation.changes` an event is made from, when one mutation is booked as several events by feature and plan, so `payload.mutation.changes` is no longer the event's own part), a command that moves no credits as a `plan.changed` with no postings, and `payload.complete: true` on every one of them. The envelope and the event types are unchanged; the payload schemas gain optional `slice` and `complete`. A caller that ships `result.events` as they are changes nothing; one that reads `payload.mutation.changes` of a `credit.*` event as that event's own changes must read `payload.slice`.
- **Order.** A subject's commands replay in revision order, not id order (a reset runs at the start of the period it refills, so its id can sort before the plan at payment time). `lastEventId` and `snapshot.lastEventId` are places in that order: pass the same events each time.
- **Revision gaps.** The stored revision also moves on a write of the grants row alone (a dollar gift, a membership event). For a log whose writer marked `complete`, replay reads the next mutation's `revision.before` and steps over the gap. `complete` is a claim by the writer, not something replay can check: a log writer that sets it on a log that lost a command, or a middle event deleted from a `complete` log, replays with no `ReplayGapError` and no `lossySubjects`. Keep the log append-only and write `complete` only from `handleStripeEvent`.
- **Logs written by 0.3.0.** They have no `plan.changed`, no `slice` and no `complete`, and a mutation booked per feature holds only each event's own changes. Replay reads them: it reassembles a mutation from the events that name its `mutation.id`, runs the recorded command in the engine, and checks the changes the log holds against the engine's (all of them when the log has all, else that each is among the engine's). What it cannot do is invent a command the log does not hold. 0.3.0 did not log the cycle-end update after a renewal (an `applyBillingPlan` that puts a refilled row's next reset on Stripe's cycle end; it changes a row only after a month end, Jan 31 to Feb 28 to Mar 31, and is a no-op otherwise), and a write of the grants row alone leaves the same revision gap, so the two cannot be told apart. Therefore:
  - a log with no revision gap replays, and its result has `lossySubjects` naming each subject whose last handler command was written by 0.3.0: the command the writer ran after the last one logged, if any, is not in the replayed rows;
  - a log with a gap stops at the first event after it with `ReplayGapError` (exported from `atm`; a `ReplayError` with `eventId`, `gap: { subject, after, before }` and `prefix`, the replay of everything before the gap, snapshot and balances). The message says the log was written by 0.3.0 and cannot be rebuilt past that point. Rebuilding past it needs the rows as the handler stored them at that revision, which the log does not hold;
  - a log of 0.3.0 events followed by current ones replays through when no command was lost between them, and stops with the same error at the boundary when one was.
- Nothing rewrites stored events. Handler events of a subject that is carried on after the upgrade are the current shape from the first write on.
